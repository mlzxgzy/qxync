# v0.6.7 —— 停止/卸载前先查「谁在用」，不再假装「已停止」

> 发布日期：2026-10-19
> 上一版：[v0.6.6](发布说明-v0.6.6.md)（事件快路径修复与凭空冲突副本）
>
> **可用性修复版**：`qxync daemon stop` 有两件事让人以为「停不下来」—— 它可能在排空
> 上传 / 删除队列时卡满 120 秒，而 CLI 早在 10 秒时就已经打印「✅ 已停止」、进程其实
> 还在；挂载点被占用时又只回一句 `Device or resource busy`，不告诉你是**谁**占着。
> 本版把「停之前先查谁在用」做成硬检查，并让 CLI 等**进程真的退出**。
> **没有新功能、没有数据格式或配置变更**，`sync.db` schema 不变；IPC 的 `shutdown`
> 回包**只增字段**（`pending_uploads` / `pending_deletes`），新旧版本混跑行为不变。

## 一句话

从这一版起，`qxync daemon stop` 先看挂载点有没有被进程占用：**有就列出 pid / 程序 /
路径并拒绝停止**，干净才继续；等待也改成盯**进程**而不是盯 socket，排空队列时明说
「在等什么」。`qxync umount` 用同一套判据。

## 一、`daemon stop` 看起来停不下来：CLI 10 秒就报成功，进程还在排空队列

### 1.1 症状与取证

真机 2026-10-19 中午：

| 时间 | 发生了什么 |
|---|---|
| 12:48:40 | daemon 收到 `shutdown` 请求（日志 `收到 shutdown 请求（IPC）`） |
| 12:48:50 前后 | CLI 打印「✅ qxyncd 已停止」并退出 —— 进程其实还在（`ps` 里能看到，socket 探测也仍连得上） |
| 12:50:40 | daemon 才打完「卸载前上传队列未排空（继续卸载，标记文件保留，下次启动会重试）」并真正退出，**整整 120 秒** |

同一时刻的挂载点是**干净**的：卸载一次就成功（日志 `已卸载 …/qxync/default/qsync`）。
也就是说「停不下来」不是挂载点被占用，而是**退出前要先排空上传/删除两个队列**
（各自最长等 120 秒），队列里压着一个没发出去的作业（12:39 创建的
`HTML 文件.html` 上传）时，退出就会慢到让人以为卡死。

### 1.2 根因

两层原因叠加：

1. **退出的等待语义**：`shutdown` 的 IPC 回包是**先回包、再退出**（避免对端拿不到回
   包），而真正的退出在后台：先排空上传队列（最长 120s）→ 再排空删除队列（最长
   120s）→ 再逐个 `fusermount3 -u`。队列卡住时，退出会明显变慢。
2. **CLI 的等待是假的**：旧 CLI 发完 `shutdown` 后只轮询 **socket 连不连得上**
   （`for _ in 0..40 { available(socket) … sleep 250ms }`，共 10 秒），然后**无条件**
   打印「✅ 已停止」。而 socket 直到进程快退完才删，前 10 秒里 `connect()` 成功、
   循环跑满、照样报成功 —— 用户看到的是「说停了，其实还在」。

### 1.3 修法

* daemon 回 `shutdown` 时顺带报「此刻还有几个上传 / 几个删除没落盘」；
* CLI 收到回包后：
  * 有积压就明说 `⏳ 还有 N 个上传、M 个删除要收尾（两个队列各自最长等 120 秒；作业已入库，等不到下次启动继续）`；
  * 改成**轮询 `/proc/<pid>` 直到进程真的消失**（不再只看 socket）：5 秒时说明在
    等什么（排空上传/删除队列 + 卸载），之后每 30 秒报一次「已等 N 秒」；
  * 260 秒（120 + 120 + 余量）还没退就报错，并给出下一步（看哪个日志、必要时
    `kill -9` 之后的挂载点清理命令）；
  * 退出后**复核挂载点是否真的没了**：进程退出 ≠ 卸载成功，残留会明确提示
    `fusermount3 -uz <挂载点>`。

## 二、挂载点被占用：先查「谁在用」，占用就拒绝停止

### 2.1 症状

`fusermount3 -u` 在挂载点里有进程打开着文件 / `cwd` 在里面时只回
`Device or resource busy`。用户只知道「卸载失败」，不知道是哪个程序占着 —— 只能靠
`lsof` / `fuser` 自己找（而且这俩常常没装）。

顺带一个自伤：用户常常**就在挂载点里**敲 `qxync daemon stop`。本进程的 cwd 在挂载点
里，`fusermount` 不看「谁在扫」，cwd 在就是 `EBUSY` —— 自己挡住自己。

### 2.2 修法：`qxync-core::mountbusy`

新增模块，**只读 `/proc`**（不依赖 `lsof` / `fuser`），对每个挂载点检查四类占用：

| 占用形式 | 数据来源 |
|---|---|
| 工作目录 / 根目录在挂载点里（`cd` 进去了） | `/proc/<pid>/cwd`、`/proc/<pid>/root` |
| 打开了挂载点里的文件 / 目录 | `/proc/<pid>/fd/*` |
| `mmap` 了挂载点里的文件（fd 已关也算） | `/proc/<pid>/maps` |
| 挂载点下面还挂着别的文件系统 | `/proc/self/mountinfo`（子挂载要先卸） |

报告形如：

```text
1 个挂载点正在被使用（2 个进程、1 个子挂载）：
挂载点 /home/tester/qxync/default/qsync：
  pid 12345   wps              打开文件 /home/tester/qxync/default/qsync/2026/…docx
  pid 23456   dolphin          工作目录 /home/tester/qxync/default/qsync/2026/…
  子挂载 /home/tester/qxync/default/qsync/scratch（要卸父挂载点，得先卸它）
```

行为：

* `qxync daemon stop`：占用时不发 `shutdown`，直接报上面这段并退出非零；关掉程序 /
  退出目录后重试即可。`--force` 跳过检查强停（占用者仍会打到 stderr，不悄悄硬停）。
* 扫描排除**本进程**与 **daemon 自己**；用户就在挂载点里敲命令时，本进程先
  `chdir("/")`，不让自己的 cwd 误伤 `fusermount`。
* 停止后复核挂载点（`/proc/self/mounts`）是否还在，残留时提示清理命令。

## 三、`qxync umount` 与 GUI 用同一套判据

* `qxync umount <挂载点>`：先扫「谁在用」（本进程 cwd 也先挪出去），占用就直接列出
  pid / 程序 / 路径，不再让用户对着 `Device or resource busy` 猜；daemon 模式下由
  daemon 侧做同样的检查。
* daemon 侧 `umount`：占用时直接返回「谁在用」，**不**先把条目从挂载表里摘掉；如果
  `fusermount3` 仍然失败（检查之后、卸载之前又有人打开），把「谁在用」补进错误和
  日志里（只有 root 才能看全部进程，见「已知边界」）。
* GUI：「停止」按钮走同样的预检查，被占用时弹出占用者列表；「全部停止」遇到某条
  连接被占用只跳过它、其余照停并逐条报错；删连接 / 清数据 / 自检这些内部流程显式
  传 `force`，不因为它们要停 daemon 就被用户打开的文件挡住。

## 五、已知边界（如实写）

* **占用扫描只报「本用户能读到」的进程**：普通用户读不到别人的 `/proc/<pid>/fd` 与
  `/proc/<pid>/maps`，所以别人的进程占着挂载点时可能扫不出来（root 跑 daemon /
  CLI 才能看全）。这种情况会退化成旧行为：`fusermount3` 回 `EBUSY`；daemon 侧会把
  能看到的占用者补进错误，CLI 直连模式只报 fusermount 自己的输出。
* **检查与卸载之间有竞态**：扫描之后、`fusermount3` 之前有人打开文件，仍会 `EBUSY`；
  这时 daemon 侧会再扫一遍并把占用者写进错误，CLI 停止后也会复核挂载点是否残留。
* **排空队列仍是最长 120 秒一项**：这是有意保留的（丢一个已落盘的上传比多等两分钟
  更糟）；等不到也不会丢作业 —— 已入库，下次启动继续。本版只是把「在等什么」说清楚，
  没有缩短上限。
* **`--force` 仍可能留下死挂载**：强停时挂载点里打开着的文件会立刻失效，`fusermount`
  可能失败；停止后会复核并打印 `fusermount3 -uz` 清理命令，不会假装成功。
* 其余打包 / 平台边界（amd64、glibc ≥ 2.35、有意不 strip 约 190 MB、AUR 校验和
  发版后更新）与 [v0.6.6](发布说明-v0.6.6.md) 相同，本版没有变化。

## 六、升级须知

* **受影响的用户**：用过 `qxync daemon stop` / `qxync umount` 且「感觉卡住」的；
  需要先知道「谁占着挂载点」才能停 / 卸载的；脚本里依赖「`daemon stop` 一定成功、
  一定打印 ✅」的（本版起，占用且没 `--force` 时会**拒绝**并以非零退出，这是行为
  变化，脚本请按需加 `--force`）。
* **升级方式**：`.deb` 用户 `sudo apt install ./qxync_0.6.7-1_amd64.deb`；Arch /
  tar.gz 用户换二进制。**升级后重启 daemon**（新二进制不会替换正在跑的旧进程）。
* 与旧 daemon 混跑：新版 CLI 对旧 daemon 的 `shutdown` 回包缺字段 → 按 0 处理，
  等待逻辑仍然生效（盯 `/proc` 与进程号是 daemon 无关的）；旧版 CLI 对新 daemon
  只是看不到积压提示，行为与 0.6.6 相同。
* **回退**：装回 0.6.6 即可；`sync.db` schema 没有变化，回退不需要迁移。
