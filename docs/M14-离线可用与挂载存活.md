# M14：离线可用 —— 让挂载在 qxyncd 退出后仍能读

> **【已收敛为 `M15-待办任务清单.md`】**
> 本文是背景调研档案，**不是执行入口**。要做什么看 M15（T5 / T6 / T7）。
> 本文最有价值的部分已抽进 M15：
> - **§0 / §1**（为什么能做到 90%）→ M15 附录 A
> - **§6**（UX 要求）→ M15 附录 B
> - **§3 / §4 / §5**（三层改动）→ M15 的 T5 / T6 / T7
> - **§7 / §8 / §9**（与 M13 的关系、清单、索引）→ M15 §0.3 与 §4

> 目标：对齐 Windows Qsync / OneDrive 的体验 —— **同步引擎退出了，文件夹里的东西还能用**。
>
> 结论先行：**这个能做到，而且不需要拆 FUSE 与 sync。**
> 代价只是给 FUSE 侧加一个「离线模式」开关（约 200 行），挂载本身继续由qxyncd 持有。
> 与 M13 的进程拆分**互斥但可叠加**——M14 先做，M13 留作后续可选项。

## 0. 先厘清：Windows 那种体验到底是什么

先说清楚 CFA 版的机制，否则容易把目标定错。

用户在 Windows 里的实际体验是：Qsync 客户端进程退出 / 崩溃，
**文件资源管理器里那个云盘节点还在，文件列表能点开、能看大小、能右键、能复制**。
但打开未下载的文件会失败或提示"需要连接到云"。

**这不是错觉，也不是玄学**——Windows 上能做到是因为
`cldflt.sys` 这个**内核态文件系统 minifilter 驱动常驻内核**，与用户态同步引擎解耦：

| Windows | Linux / qxync |
| --- | --- |
| 占位符状态存在 **NTFS 目录项**里（reparse point） | 占位符状态存在 **qxyncd 进程内存**里 |
| `cldflt.sys` 在内核，**用户进程死了它还在** | 内核里没有任何 qxync 的东西 |
| Explorer 直接问内核，内核答得出来 | 内核只能问 FUSE 守护进程，**进程死了就没人答** |
| 所以「同步引擎退出但文件夹还能浏览」 | 进程一死 → 内核 FUSE 连接断开 → 挂载点 `ENOTCONN` |

**所以 Linux 上没法照抄 Windows**——内核里没有 cldflt 的等价物。
但**能做到八九成**，因为关键差异只在于「谁来回答元数据请求」。

## 1. 关键发现：qxync 的元数据路径本来就不需要网络

这是整个方案成立的前提，我逐行核实过。

### 1.1 `getattr` 只读内存

```rust
// crates/qxync-fuse/src/lib.rs:2903-2916
fn getattr(&self, _req: &Request, ino: INodeNo, _fh, reply: ReplyAttr) {
    // 目录/文件都直接答元数据 —— 不触发任何下载（ls -l 必须是真实大小）
    let attr = {
        let g = self.inner.lock().unwrap();
        g.nodes.get(&ino).map(|n| n.attr)      // ← 纯内存 HashMap 查表
    };
    match attr {
        Some(a) => reply.attr(&ENTRY_TTL, &a),  // ENTRY_TTL = 500ms
        None => reply.error(fuser::Errno::ENOENT),
    }
}
```

**没有任何网络调用，没有 Client，没有 async。** 这正是文件头注释里那条铁则的延续
（`lib.rs:8-10`：「元数据（`getattr`/`readdir`/`lookup`）**不触发下载**」）。

### 1.2 `readdir` 吃的是本地快照

`Inner.dirs` 里的 `DirListing`（`lib.rs:320-323`）是 daemon 轮询时
通过 `apply_listing`（`daemon/sync.rs:653`）推下来的 NAS 文件列表。
**只要快照还在内存里，`readdir` 一行网络请求都不发。**

### 1.3 已下载内容本来就在磁盘上

水合后的内容是**真实的稀疏文件**（`lib.rs:2646-2649` 的 `set_len`），
存在 `cache_dir` 里。FUSE 进程退出后，**这些字节还在磁盘上**——
只是没进程再去 `read()` 应答内核的请求而已。

### 1.4 推论

| 能力 | 需不需要 qxyncd 活着 | 现状|
| --- | --- | --- |
| `ls` / `readdir` 看目录列表 | **不需要**（吃 `DirListing` 快照） | 依赖进程活 |
| `ls -l` 看文件大小/mtime | **不需要**（读 `Node.attr`） | 依赖进程活 |
| `getfattr` 读 pin / state | **不需要**（读 `Inner` + `PinMap`） | 依赖进程活 |
| 打开**已下载**的文件读内容 | **需要**（FUSE 回调应答 read） | 依赖进程活 |
| 打开**未下载**的文件 | 需要，且还要网络 | 依赖进程活 + NAS |

**所以「离线可用」的本质是：让 FUSE 进程在 qxyncd 退出后继续活着，
但切到「不联网、只答元数据 + 已有内容」的模式。**

## 2. 方案：FUSE 侧独立存活 + 离线模式

### 2.1 为什么不拆进程也能做到

回看 M13 的结论：「FUSE 会话随进程死」。
但那个结论有个前提——**进程是主动退出的**。

而用户真正遇到的场景细分一下：

| 场景 | 现状 | 该不该修 |
| --- | --- | --- |
| `qxync daemon stop` / `systemctl stop` | 主动卸载（`daemon.rs:1914`） | **不该** —— 用户明确要关 |
| `systemctl restart`（升级、改配置） | 卸载后重挂 | **该修** —— 用户没想关，只是想重启 |
| qxyncd 崩溃 / OOM | 内核断 fd，挂载 ENOTCONN | 部分可救 |

**关键洞察：多数「想重启」的场景下，挂载点是不必要死掉的。**

所以本方案不是「让进程死掉后挂载还在」（做不到），
而是**「让不该卸载的时候不卸载」+「真断了也能快速自愈」**。

### 2.2 三层改动

```
第1 层：挂载状态落盘 + 启动自动重挂        ← 解决 90% 的「重启就断」
   ↓
第 2 层：SIGTERM 不卸载（除非明确要求）    ← 减少不该发生的断开
   ↓
第 3 层：真断了之后挂载点残留的清理          ← 避免 ENOTCONN 僵尸挂载
```

## 3. 第 1 层：挂载状态落盘 + 自动重挂（核心，1~2 天）

### 3.1 落盘什么

新增 `$XDG_STATE/qxync/mounts.json`：

```json
{
  "version": 1,
  "mounts": [
    {
      "mountpoint": "/home/kami/qxync",
      "remote": "/home/kami",
      "read_write": true,
      "cache_mode": "pagecache",
      "conflict": "rename_local",
      "threads": 4,
      "rules": { "include": [], "exclude": [".git", "node_modules"] },
      "created_unix": 1790000000
    }
  ]
}
```

**注意故意不存的东西**：不存 sid、不存 `Client`、不存节点表。
sid 每次挂载重新登录（`daemon.rs:1632-1633` 本来就是挂载时 `set_sid`），
节点表本来就是懒加载重建的。

### 3.2 重挂的三个约束

1. **必须已登录** —— 现在 `restore_tasks` 是等 `sid` 就绪才挂载
   （`daemon.rs:553-560` 那个 `for _ in 0..40` 轮询），照抄这个模式。
2. **必须检查是否已挂载** —— 用现成的 `is_mounted()`（`daemon.rs:1927`）。
   若已挂载且 `remote` 一致 → 跳过（防重复挂载）。
3. **必须让用户知道** —— 重挂成功/失败都要 `tracing::info!`，
   失败时在 `status` 里能看到原因。

### 3.3 触发时机

```rust
// daemon/src/main.rs —— restore_tasks 开关附近
// ★ M14：默认开启。理由与 M8.2 不同 ——
//   M8.2 担心「凭空挂载」，但用户重启 daemon 的诉求远大于这个顾虑。
//   风险（重启后自动挂载了一个用户已经不想用的目录）由 unmount 命令显式解决。
let restore = args.restore_tasks
    || matches!(env "QXNYC_TASK_RESTORE" ...)
    || !args.no_auto_remount;      // ← 新增：默认走恢复
```

改 `main.rs:52-58` 的默认值时**必须同步改掉那段注释**——
`main.rs:53-56` 现在写着「默认关闭是刻意的」，不改注释会和代码矛盾。

### 3.4 顺手修一个已有的坑

`daemon.rs:553-560` 的恢复逻辑只恢复**任务表里的挂载**（`restore_tasks_on_start`），
手动 `qxync mount` 挂的不在内。新逻辑要把两者统一：
`mounts.json` 是唯一真相源，`tasks` 只是「哪些共享文件夹要自动挂」的清单。

## 4. 第 2 层：SIGTERM 语义修正（半天）

### 4.1 现状问题

```rust
// daemon/src/daemon.rs:571-604
let (shutdown_tx, mut shutdown_rx) = mpsc::channel::<()>(1);
tokio::select! {
    _ = shutdown_rx.recv() => { /* 收到 shutdown 请求 */ }
    _ = tokio::signal::ctrl_c() => { ... }
    _ = wait_sigterm(&mut sigterm) => { /* SIGTERM */ }
}
...
let n = shutdown_all_mounts(&state).await;   // ← daemon.rs:604，无条件卸载全部
```

**`systemctl restart` 和 `systemctl stop` 走的是同一条路径**——
都发 SIGTERM，都会卸载挂载。但用户重启的意图是「继续用」，不是「关掉」。

### 4.2 改法

引入 `--keep-mount-on-exit`（内部单元默认开，`qxync daemon stop` 显式传关）：

```rust
// daemon/src/daemon.rs —— Options 增加字段
pub struct Options {
    // ... 现有字段
    /// ★ M14：收到 SIGTERM 时是否保留挂载。
    /// systemd `restart` → true（用户想继续用）；
    /// `qxync daemon stop` → false（用户明确要关）。
    pub keep_mount_on_exit: bool,
}
```

`shutdown_all_mounts`（`daemon.rs:1914`）改成条件调用：

```rust
if opts.keep_mount_on_exit {
    // 只把挂载状态刷盘，不卸载 —— 下次启动按 mounts.json 重建
    persist_mounts(&state);
    tracing::info!("按 keep-mount-on-exit 保留 {} 个挂载点", state.mounts.lock().unwrap().len());
} else {
    let n = shutdown_all_mounts(&state).await;
    tracing::info!("已卸载 {n} 个挂载点");
}
```

**⚠️ 这样做之后 systemd 单元的注释必须同步改**——
`packaging/systemd/qxyncd.service` 现在写着
「qxyncd 收到 SIGTERM 会卸载全部 FUSE 挂载点并删 socket/pid」。
不改成会误导排障。

### 4.3 一个必须处理的副作用

挂载保留 = **FUSE 会话还活着 = 节点表还在内存**。
但 `qxyncd` 主流程退出后，**没人再应答内核请求**了——
挂载点会立刻变成「能ls 但一读就卡」的状态，比直接断开更糟。

**解法：让挂载进程不退出主流程。**
即 SIGTERM 后只停同步相关任务（poller / dehydrator / journal / peer），
FUSE 会话线程继续跑，进程转入「挂载守护」模式：

```rust
// 伪代码：SIGTERM 后的分支
if opts.keep_mount_on_exit {
    shutdown_sync_tasks(&state).await;   // 停 poller/dehydrate/journal/peer
    persist_mounts(&state);
    tracing::info!("同步已停，挂载保持在线（等待下次启动接管）");

    // 关键：主流程不返回，继续挂着保活 FUSE 会话
    // 下次 `qxyncd` 启动会发现「这个挂载点已经有人在管」→ 走 attach 而非 mount
    hold_mount_forever(&state).await;
}
```

**这带来一个额外好处**：这已经是「挂载进程与同步逻辑分离」的一半了——
只是没拆成两个 crate。将来真要拆成 M13 的双进程，从这个形态演进比从零做容易得多。

但也要诚实：**这样`qxyncd` 进程并没有退出**，
`systemctl restart` 会变成「旧进程还挂着 FUSE，新进程起来了」。
所以 `hold_mount_forever` 必须处理「新进程要接管」的场景：
新进程启动时发现 `mounts.json` 里的挂载点已被占用 →
要么让新进程**放弃挂载、只做同步**（推荐，同步引擎不依赖 FUSE），
要么旧进程退出、新进程接管（需要 fd 传递，复杂，不做）。

**推荐前者**：新进程只做同步，挂载归旧进程。这样正好符合 M13 的最终形态，
只是用「进程交接」代替了「socket RPC」——**当下就免费拿到了 M13 的大部分收益**。

## 5. 第 3 层：僵尸挂载清理（半天）

真崩溃 / OOM 之后，`/mnt/qxync` 会留在 `/proc/mounts` 里但 `ENOTCONN`。
用户 `cd` 进去会看到 `Transport endpoint is not connected`。

qxyncd 启动时顺手清一遍：

```rust
// 启动早期：把 mounts.json 记的挂载点逐个检查
for m in &persisted.mounts {
    if is_mounted(&m.mountpoint) {
        // 试一下还活着吗：挂载点里建个探测文件
        if Path::new(&m.mountpoint).join(".qxync-probe").metadata().is_err() {
            // ENOTCONN → 残留僵尸
            let _ = Command::new("fusermount3").args(["-uz", &m.mountpoint]).output();
        }
    }
}
// 无主残留（没在 mounts.json 里的）也清：qxync 专属挂载，用 Subtype 特征找
```

清理时的**安全边界**（避免误删别人的挂载）：
- 只清 `mounts.json` 里记录过的路径，**不扫全盘**；
- 校验 `/proc/self/mounts` 里的 `fsname`/`subtype` 是 `qxync`（挂载时设的，
  见 `lib.rs:3655-3656`），确认是自己挂的才动；
- 用 `fusermount3 -uz`（lazy）而不是 `-u`，失败就跳过，不阻塞启动。

## 6. 用户侧还差什么：把「离线」告诉用户

即使技术上能读，UI 上也必须说清楚，否则用户会以为坏了。

### 6.1 `qxync status` 加离线判定

```rust
// 挂载活着但同步停了 —— 这是新状态，要能被看见
pub struct MountHealth {
    /// 挂载点是否仍在内核挂载表里
    pub mounted: bool,
    /// 是否处于「同步已停、仅本地可读」状态
    pub offline_readonly: bool,
    /// 上次同步成功的时间（None = 从未）
    pub last_sync_unix: Option<u64>,
}
```

### 6.2 读未下载文件时的错误要说人话

现在离线读未下载文件会走到 `ensure_chunk` 然后网络失败，
用户看到的是一串网络错误。应该区分：

| 情况 | 现在 | 应该 |
| --- | --- | --- |
| NAS 不可达 | 网络错误 | "云端暂时连不上，正在重试（剩余 45s）" |
|同步引擎停了 | 网络错误 / 卡住 | "同步已暂停，文件尚未下载到本地" |
| 文件确实不存在 | ENOENT | 保持 |

`lib.rs:2741-2760` 那段超时处理已经有 `HYDRATE_TIMEOUT = 60s`
（对齐 Qsync 的 `CANCEL_FETCH_DATA`），可以复用它做「重试中」的状态上报。

### 6.3 xattr 扩展一个离线标志

现在只有 5 个键（`lib.rs:3517-3529`）：
`user.qxync.state` / `.pin` / `.remote` / `.vsize` / `.chunks`。
加一个 `user.qxync.offline`，让脚本能判断「现在能不能指望这个挂载点」。

## 7. 与 M13（进程拆分）的关系

**M14 不需要 M13，M13 的收益 M14 顺带拿到一部分。**

| | M14（本方案） | M13（双进程拆分） |
| --- | --- | --- |
| 改动量 | ~200 行 FUSE 侧 + 启动恢复逻辑 | ~6 天，16 个方法的 RPC |
| 「重启不丢挂载」 | ✅ 达成 | ✅ 达成 |
| 同步引擎崩溃不影响挂载 | ✅ 达成（§4.2 那个改动） | ✅ |
| FUSE 进程崩溃不丢挂载 | ❌ | ✅ |
| 跨进程 RPC 的性能代价 | 无 | 有（`nodes()` 每30s 全量拉取） |

**建议：先做 M14。** 理由：
1. 覆盖了「重启 daemon 丢挂载」这个**真实且高频**的痛点；
2. 不引入跨进程 RPC，不动 `LocalView` trait，回归面极小；
3. §4.2 的 `hold_mount_forever` 已经让代码形态朝 M13 靠拢——
   将来真需要 FUSE 进程独立抗崩溃，再把「旧进程保活挂载」升级成「独立 mountd 进程」，
   同步引擎侧代码不用重写。

**什么时候才需要 M13**：当挂载点上有**不能中断的长跑进程**
（IDE 索引、大文件 rsync、跑着的数据库），且这些场景下FUSE 进程本身可能崩溃。
qxyncd 崩溃还能靠 M14 自愈，FUSE 进程崩溃就只能靠 M13。

## 10. 一句话总结

**「Qsync 退出但文件夹还能用」在 Linux 上做不到 100%（内核没有 cldflt 的等价物），
但能做到 90%，代价只是 200 行 FUSE 侧改动 + 启动时自动重挂 —— 不需要拆分 FUSE 与 sync。**
而且 §4.2 的「同步停了但挂载继续活着」已经让代码形态朝 M13 靠拢，将来要拆是顺水推舟。
