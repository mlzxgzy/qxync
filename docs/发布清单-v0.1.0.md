#### 怎么复跑清洗验证

**不要**把敏感串直接写进命令行（会进 shell 历史，也会被再次提交）。用一份**本地的**清单文件：

```bash
# 1) 建一份敏感串清单（放在仓库外，逐行写你的真实域名 / 用户名 / 设备指纹）
cat > /tmp/qxync-sensitive.txt <<'EOF'
<你的真实 DDNS 域名>
<你的本机用户名>
<你的真实 device_uid>
<你的本机计算机名>
EOF

# 2) 扫工作区
git grep -nIiF -f /tmp/qxync-sensitive.txt && echo "❌ 工作区有残留" || echo "✅ 工作区无残留"

# 3) 扫**全部历史**（关键：只扫工作区是不够的）
for rev in $(git rev-list --all); do
  git grep -lIF -f /tmp/qxync-sensitive.txt "$rev" 2>/dev/null
done | head && echo "❌ 历史有残留" || echo "✅ 历史无残留"

# 4) 口令从未进入历史
git log --all --format=%H | while read -r r; do
  git grep -l '你的口令片段' "$r" 2>/dev/null
done | head && echo "❌ 口令进过历史" || echo "✅ 口令从未进入历史"

# 5) 唯一要紧的口径：「会入库的文件」= 已跟踪 + 未跟踪但未被忽略
git ls-files -co --exclude-standard -z \
  | xargs -0 -r grep -lIF -f /tmp/qxync-sensitive.txt \
  && echo "❌ 有会入库的敏感文件" || echo "✅ 没有任何会入库的敏感文件"

# 6) 收尾：删掉清单文件
shred -u /tmp/qxync-sensitive.txt 2>/dev/null || rm -f /tmp/qxync-sensitive.txt
```

> **`docs/测试环境.local.md` 仍然留在本地且在 `.gitignore` 里**（规则 `*.local.md`）。
> 它含真实域名与口令。**绝对不要**用 `git add -f` 绕过忽略规则。

### 1.5 历史重写记录

原仓库**从未关联任何远程**（`git remote -v` 为空），所以清洗是在推送前完成的，**不需要 force-push**。

- 方法：`git filter-branch --tree-filter`，对每个提交只对**命中敏感串的文本文件**做替换
  （`grep -rlI` + `xargs sed -i`，`-I` 保证不碰二进制）。
- **重写前的完整历史已备份**：仓库**上一级目录**下的 `qxync-prepublic-backup.bundle`
  （`git bundle create --all`，已 `bundle verify` 通过）。确认新历史没问题后可以删掉它。
- 重写一共跑了**四轮**：① 清敏感串；② 清「裸片段」；③ 撤出分析报告（见 §1.6）；
  ④ **清提交信息**。每一轮之后都做了全历史扫描。
- ⚠️ **最大的一个坑：`--tree-filter` / `--index-filter` 只重写「树」，不动提交信息。**
  本仓库的清洗记录本身把原值写进了提交信息，于是内容清干净了、`git log` 里却还挂着原值。
  必须再用 `--msg-filter` 清一遍：
  ```bash
  git filter-branch --force --msg-filter 'python3 /tmp/clean-msg.py' -- --all
  ```
  验证方式是扫**提交信息**，而不只是扫文件：
  ```bash
  git log --all --format='%B' | grep -inE '<敏感串清单>'
  ```
  （另外：`filter-branch` 的 `--msg-filter` 脚本**必须有可执行权限与 shebang**，
  否则会被 `/bin/sh` 当脚本解析并**挂死** —— 本次就踩了，用 `timeout` 兜住更稳。）
- 重写后清理了 `refs/original/`、过期 reflog 并 `git gc --prune=now`，
  确认**旧对象已不可达**。
- ⚠️ **本文件曾经踩过一个自指陷阱**：初版把真实域名 / 用户名当作「搜索模式」和「映射原值」写了
  进来，导致历史里仍留有这些**裸字符串**（完整域名已被替换，但裸片段没有）。
  现已改为**只描述类别、不写原值**，并重跑了一次清洗。**以后写这类文档务必遵守这条。**

### 3.1 本地先复现发版产物（发版前自查）

不需要 Actions 也能把 Release 里的东西原样造出来（Arch 包那步要本机有 `makepkg`，
Arch 系发行版自带；没有就跳过，CI 里那步跑在 Arch 官方镜像里。`.deb` 同理，
要在 `ubuntu:22.04` 容器里打，见下方）：

```bash
CARGO_HOME=$PWD/.cargo-home cargo build --release --locked \
  -p qxync-cli -p qxync-daemon -p qxync-gui
python3 xtask/release/check-version.py v0.1.0        # 四处版本必须一致
bash xtask/release/package-linux.sh 0.1.0 x86_64-unknown-linux-gnu

# Arch 包：把占位 sha256 换成刚打出来的真实值，再让 makepkg 复用 dist/ 里的 tar.gz
# （BUILDDIR 指到临时目录：否则 makepkg 会在 packaging/arch/ 下留 src/ 与 pkg/，各有 180 MB）
sum=$(sha256sum dist/qxync-0.1.0-x86_64-unknown-linux-gnu.tar.gz | cut -d' ' -f1)
sed -i "s/^sha256sums=.*/sha256sums=('$sum')/" packaging/arch/PKGBUILD
(cd packaging/arch && BUILDDIR=$(mktemp -d) SRCDEST=$PWD/../../dist PKGDEST=$PWD/../../dist makepkg -f --nodeps)
git checkout -- packaging/arch/PKGBUILD               # 占位值要还原，别把它提交了

# Debian / Ubuntu 包（Debian 12+ / Ubuntu 22.04+ 通用）：在打包基线容器里打，推荐
# ubuntu:22.04（debian:12 亦可，两者算出的 Depends 逐字相同；更新发行版里算会把下限抬高）。
# 先把容器里的 apt 源切到清华镜像（否则 apt-get update 慢到超时）；脚本自己会装打包依赖
# （dpkg-dev + 运行库），并校验 /etc/os-release 属于 Debian 系、基线是 ubuntu 22.04 / debian 12。
# HOST_UID/HOST_GID：容器里以 root 打出来的 deb 交回宿主用户，dist/ 里不出现 root 属主文件。
docker run --rm -v "$PWD:/work" -w /work \
  --env HOST_UID="$(id -u)" --env HOST_GID="$(id -g)" ubuntu:22.04 \
  bash -lc 'bash xtask/release/apt-mirror.sh && bash xtask/release/package-deb.sh 0.1.0'
# → dist/qxync_0.1.0-1_amd64.deb（换 debian:12 打出来的 payload 与 Depends 相同）

# 校验和的口径与 CI 一致：dist/ 顶层的普通文件、按名字排序（子目录不算）
# ⚠️ 必须在 .deb 打完之后再算，否则 SHA256SUMS 里会缺这个资产
cd dist && rm -f SHA256SUMS \
  && find . -maxdepth 1 -type f ! -name SHA256SUMS -printf '%P\0' | sort -z | xargs -0 sha256sum > SHA256SUMS \
  && sha256sum -c SHA256SUMS                          # dist/ 已在 .gitignore 里
```

> ⚠️ **`.deb` 的输入必须是 CI 构建的 Release 原件**：`package-deb.sh` 只把 tar.gz 重打包、
> **不重新编译**，所以包里的 glibc 上限完全由输入 tar.gz 决定。CI 在 `ubuntu-22.04` 上构建，
> Release 原件实测只要求 **GLIBC 2.34**；在滚动发行版（例如 Arch，glibc 2.44）上自编的二进制
> 会需要 `GLIBC_2.39`，装进 `debian:12` / `ubuntu:22.04` 这些目标发行版时运行会报
> `weak version 'GLIBC_2.39' not found`（打包脚本不拦这一点，实装校验那步才会暴露）。
> 所以打 deb 时，输入请用 **Release 里的 tar.gz 原件**；
> 想在本机复现整套，就在 `ubuntu:22.04` 容器里 `cargo build`。

打包脚本是**可复现**的（tar 内 owner/group 归零、按名字排序、mtime 取 HEAD 提交时间、
gzip 不写时间戳）：同一份输入 → 同一个 sha256。想验证这一点，跑两遍比一下。

**有意不 `strip`**：release profile 带 `line-tables-only` 调试信息，是为了用户报 bug 时
贴出来的回溯可读（见 `Cargo.toml` 的 `[profile.release]` 注释），所以产物比「strip 过」的大。

### 3.3 Debian / Ubuntu 包

**只有一个产物**，Debian 与 Ubuntu 共用（都是同一份 Release tar.gz 里的三个二进制 + 桌面项 /
4 个 hicolor 图标 / 两个 systemd user 单元 / 文档），在 `ubuntu:22.04` 容器里打包：

| Release 资产 | 构建环境 | 包版本 | 适用发行版 |
|---|---|---|---|
| `qxync_<版本>-1_amd64.deb` | `ubuntu:22.04` 容器 | `<版本>-1` | Debian 12 / 13、Ubuntu 22.04 / 24.04 / 26.04（amd64） |

- **为什么合并**：合并前是 `~deb12` / `~ubuntu22.04` 两个包；实测两个包除 `Version` 串与
  `/usr/share/doc/qxync/changelog.Debian.gz`（含版本 / 发行版代号 / 构建时间）外，payload
  的 16 个文件里除 changelog 外的 15 个**逐字节相同**（含三个二进制），`Depends` 串也逐字相同 —— 所以合并成一个。
  包里的 `changelog.Debian.gz` 发行版代号取自构建环境的 `VERSION_CODENAME`
  （`ubuntu:22.04` → `jammy`）；它含构建时间，所以**重复构建的 sha256 会变** ——
  要可复现就设 `SOURCE_DATE_EPOCH`。
- **包版本就是 `<版本>-1`**，不再有 `~deb12` / `~ubuntu22.04` 标记。旧包版本
  `<旧版本>-1~deb12` / `<旧版本>-1~ubuntu22.04` 按 dpkg 版本序**小于**新的 `<版本>-1`
  （`~` 排在空串之前），所以从旧包升级直接装新包即可、apt 会正常替换；
  想先验证可以跑 `dpkg --compare-versions <版本>-1 gt <旧版本>-1~deb12 && echo newer`。

- **实测 Depends**（`dpkg-deb -f` 读出来的原文，共 11 项：
  10 项来自 `dpkg-shlibdeps` + 手工补的 `fuse3`）：
  `libc6 (>= 2.34), libcairo2 (>= 1.10.0), libdbus-1-3 (>= 1.9.14), libgcc-s1 (>= 4.2),
  libgdk-pixbuf-2.0-0 (>= 2.36.9), libglib2.0-0 (>= 2.65.1), libgtk-3-0 (>= 3.21.5),
  libjavascriptcoregtk-4.1-0, libsoup-3.0-0 (>= 3.0.3), libwebkit2gtk-4.1-0 (>= 2.41.90),
  fuse3`。`Installed-Size` **约 190 MB**（单包实测 191908 KiB；由暂存树
  `du -sk --apparent-size` 得出、不含 `DEBIAN/`，会随二进制体积变化 —— 真实 CI 用新二进制
  重打后数字还会变，别钉死）。

- **依赖来源**：`dpkg-shlibdeps` 在**打包基线 `ubuntu:22.04` 里**扫三个二进制的 `NEEDED`
  项落到具体包上
  （上面实测串里除最后的 `fuse3` 外都来自它；带不带版本下限由二进制实际引用的符号版本决定，
  例如 `libjavascriptcoregtk-4.1-0` 就没有下限）；更新发行版的库版本都 ≥ 基线，所以这些
  版本下限在 Debian 12 / 13、Ubuntu 24.04 / 26.04 上照样满足（GTK 3 改名成
  `libgtk-3-0t64` 的发行版靠 `Provides: libgtk-3-0 (= 版本)`）；
  `fuse3` 是**手工加的** —— 挂载要调 `fusermount3`，而三个二进制并不链接 `libfuse`
  （`fuser` 走纯 Rust 实现），所以这个运行时依赖 `dpkg-shlibdeps` 看不出来，必须手工补
  （因此 `fuse3` 没有版本下限）。
  全部依赖都在 Debian / Ubuntu 官方仓库里，国内清华 / 阿里等镜像源都有。
- **不 strip 的取舍**：与 Release 产物、Arch 包一致（release profile 带 `line-tables-only`
  调试信息，用户报 bug 时回溯可读），代价是装完约 190 MB。`lintian` 结果（同一个包在
  `debian:12` 的 `2.116.3+deb12u1` 与 `ubuntu:22.04` 的 `2.114.0ubuntu1.8` 各跑一次，
  两边完全一致）**只有 7 条预期项**：`E: unstripped-binary-or-object` ×3（三个二进制）+
  `W: no-manual-page` ×3（上游没有 man page）+ `W: initial-upload-closes-no-bugs` ×1
  （版本串从 `-1~deb12` 变成干净的 `-1` 后触发 lintian 的「首次上传」启发式；本包不进
  Debian 官方仓库，所以不编假 `Closes:`）；**其它告警 0 条**；CI 里没有 `--fail-on`，
  不按等级卡门。完整清单与逐条结论见
  [`packaging/debian/README.md`](../packaging/debian/README.md)。
- **实装验证**：CI 打完包后，**另起**干净的 `debian:12` / `debian:13` / `ubuntu:22.04` /
  `ubuntu:24.04` / `ubuntu:26.04` 五个容器（不复用打包容器，
  那里已经装了 `dpkg-dev` 与一堆运行库，证明不了「用户从零也能装」），先跑 `apt-mirror.sh` 切镜像、
  `apt-get update`，再 `apt-get install -y ./dist/qxync_<版本>-1_amd64.deb` 实装。
  为什么是这五个：单包要在 Debian 与 Ubuntu 两个家族的新旧两端都验证 —— `debian:12` /
  `ubuntu:22.04` 是基线附近的旧端，`debian:13` / `ubuntu:24.04` / `ubuntu:26.04` 的风险主要在
  GTK 3 改名成 `libgtk-3-0t64` 这类 `t64` 包（靠 `Provides` 满足旧名依赖）。
  断言：`qxync --version` / `qxyncd --version` 必须成功；`qxync-gui --self-test` 必须真的跑起来并
  打印含 `"ok"` 的自检 JSON（没有 daemon 时退出码非 0 属正常）；`ldd /usr/bin/qxync-gui` 里
  `not found` 数为 0；`dpkg -L qxync` 含三个二进制、桌面项与两个 systemd 单元
  （`qxyncd.service` / `qxyncd@.service`）；`dpkg -s qxync` 的 Version 等于 `<tag 去掉 v>-1`。
  任何一条失败整步 exit 1。
  整条流水线只有原来的 `linux-x86_64` 一个 job，没有新增 job：顺序是「校验 Arch 包内容 →
  打 `.deb` → 实装校验 → 生成 `SHA256SUMS` → 留档 artifacts → 发布 Release」；
  资产仍走现有的 `files: dist/*`，不额外加 upload 步骤。
- **本地 / 容器构建**：`bash xtask/release/package-deb.sh <版本> [输出目录]`
  （没有 distro-id 参数；版本不带 `v`，也可用 `VERSION=<版本>` 环境变量传；输出目录默认
  `dist/`）。脚本会校验 `/etc/os-release` 属于 Debian 系、且打包基线**只能是 `ubuntu 22.04`
  或 `debian 12`**（在更新发行版里算 Depends 会把版本下限抬高，包就装不进老发行版），
  并自己 `apt-get update` + 装 `dpkg-dev` 与运行库 —— 调用方只需先跑 `apt-mirror.sh`。
  推荐 `ubuntu:22.04`（CI 编译 Release 二进制的同一环境，依赖下限与二进制代际最匹配；
  `debian:12` 打出来的 `Depends` 与它逐字相同），见 §3.1；输出就是上表那个文件，
  `dist/` 已在 `.gitignore` 里。输入 tar.gz 的 glibc 上限要求见 §3.1 的警告。
- **国内镜像**：`apt-mirror.sh` 把容器里的 apt 源换成清华镜像（打包装依赖与 CI 实装都走它；
  否则容器里 `apt-get update` 常常慢到超时）。默认用 **http**（基础镜像还没装
  `ca-certificates`，https 源会让 apt 报证书错误）；要换别的镜像直接设 `QXNYC_APT_MIRROR`，
  或把镜像 URL 作为第一个参数传进去（**位置参数优先级更高**）。脚本幂等、会打印改了哪些文件，
  同时处理经典 `sources.list` 与 deb822 的 `URIs:` 行（实测 debian:12 是 deb822、
  ubuntu:22.04 是经典格式，两个都 `apt-get update` 通过），认不出的第三方源不动。

CI 首次运行结果（run #36962620501）：**必跑的 `build + test` 全绿**（含 `cargo build`、`cargo test`、
`#[ignore]` 守卫、`cargo clippy`），两个非阻断项如预期失败。已按结果收紧如下。

### 4.1 ★ 发现 `rust-version = "1.85"` 是错的 —— 已改为 **1.90**

**判据不是猜的**：查依赖图里各包自己声明的 `rust-version`，**49 个依赖高于 1.85，最高 1.90**：

| 声明 | 依赖 |
|---|---|
| **1.90** | Tauri 2.12 全栈（`tauri` / `tauri-runtime-wry` / `tauri-utils` / `muda` / 3 个插件 / `tray-icon`，共 14 个包） |
| 1.89 | `notify-rust 4.18.1` |
| 1.88 | `time 0.3.55`（被 `tracing-appender` 拉进来，**CLI/daemon 也依赖**）、`image`、`plist`、`darling`、`serde_with` |

→ 已把 `Cargo.toml` 的 `rust-version` 抬到 **1.90**，并同步 README / README.en / CONTRIBUTING /
发布说明里的「Rust 1.85+」与 Rust 徽章。

> 记一条常被忽略的事实：**`rust-version` 只是「声明」**，Cargo 默认**不会**自动回退到 MSRV 兼容的
> 依赖版本（那是 resolver v3 / `-Zmsrv-policy` 的行为）。所以声明写错时，用户装到低版本才会炸 ——
> CI 里这条 job 是唯一能证明声明没撒谎的地方。
