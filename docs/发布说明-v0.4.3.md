# qxync v0.4.3 —— 挂载点不再有回收站，删除也不再干等

**中文** · [English](#english)

[![License](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](https://github.com/mlzxgzy/qxync/blob/master/LICENSE-MIT)

**这一版没有破坏性变更**：配置、任务文件、缓存目录布局、命令行参数都不需要改。
升级方式就是换二进制 + 重启 daemon。删除的行为变化是**刻意的**（见下），不需要任何配置。

## 一句话

在挂载点里删文件会弹进回收站、删完要等很久 —— 这两件事其实**都不是 qxync 干的**，
这一版把两个根因都处理掉了。

## 回收站：不是 qxync 建的，是 Dolphin 建的

先澄清一件事：qxync 代码里**从来没有过回收站逻辑**（全仓库 grep `trash`/`Trash`/
`recycle` 零命中）。你看到的回收站来自桌面环境。

实测环境是 **KDE Plasma + Dolphin 26.08.1**。Dolphin 删除文件时不去调 `unlink`，
而是走 **FDO 规范的卷内回收站协议**：在**同一个卷**里造出 `.Trash-$UID/{files,info}`，
把文件「搬」进去并写一份 `.trashinfo`。

挂载点本身就是一个卷 —— 于是回收站被造在了挂载点里，内容最终落在 NAS 上。证据是
`~/qxync-mnt/.Trash-1000/info/*.trashinfo` 里记录的 `Path=qxync-test/...`
（挂载点内的相对路径）。

**能不能在配置里关掉？不能。** 旧版 KIO 曾在 `ktrashrc` 里支持 `[DisabledFor]`
逐路径禁用，但 **KIO 6.30 已经把这个键删掉了** —— 在本机 5 个 KIO 库里 grep
`DisabledFor` 全部 0 命中，插件里只剩 `UseSizeLimit` / `UseTimeLimit` /
`LimitReachedAction` / `Days` 这几个容量/时间项，没有任何「按路径禁用」的入口。
（网上那些「禁用 Linux 回收站」的文章要么过时，要么是写 GIO/Nautilus 的，不适用 Dolphin。）

**所以只能在文件系统层挡。** 现在 FUSE 的写入口对回收站命名一律回 `EPERM`：

| 入口 | 作用 |
|---|---|
| `mkdir` | KIO 建不出 `.Trash-$UID` → 无法启用卷内回收站 |
| `create` / `rename` | 挡住「搬文件进回收站」和「搬出」 |
| `unlink` / `rmdir` | 回收站本身也不许删（不留后门） |

`mkdir` 被挡是关键：KIO 必须先建出那个目录才能用回收站，建不出来就走它既定的
**「直接删除」回退路径** —— 这正是你要的效果。

判定是**段级精确匹配**（路径任一段命中即拒），所以不会误伤 `.recent`、`.trash`、
`a.Trash-1000.txt`、`@Recycled` 这类正常名字。

## 删除慢：是同步阻塞，而且每个文件要 2~3 次 NAS 往返

之前的 `remove_entry` 是 `rt.block_on(client.delete_entry(..))` —— unlink 要**等 NAS
回包才返回**。删 N 个文件就是 N 次串行 RTT。

**经 Dolphin 删更糟**：Dolphin 不调一次 unlink，而是「在 `files/` 放副本 + 写
`info/*.trashinfo`」，每一步都是一次打回 NAS 的 FUSE 调用，**每个文件 2~3 次往返**。
两件事叠起来就是你感受到的「转圈很久」。

## 现在：立刻返回 + 后台攒批

对齐了**官方客户端的形态**。Qsync 官方（Smart Delete）的语义是
*"deleted files on the local device are retained on the NAS"* ——
**本地立即生效，服务端侧异步推进**。本版就是这个形态：

- `unlink`/`rmdir` **立刻返回**，本地节点表和映射立即摘掉
- 远端删除由 `qxync-delete` worker 攒批推送
- **同目录合并成一次请求**：`qsyncsrv.cgi?func=delete` 的 `file_total` 本就是
  「本批条目数」（`stat`/`set_mtime` 硬编码成 `1` 只因那些调用每次一个文件），
  现在按目录分组、单批上限 50、攒批窗口 200ms

**收益**：删 N 个同目录文件，从 **N 次串行 RTT** 降到约 **N/50 次**；
经 Dolphin 删也不再是每文件 2~3 次往返。

**崩溃恢复**：作业落 `deletes` 状态库（与上传队列同一个 `queue.db`），语义一致 ——
**表 = 未完成作业**，daemon 重启自动重新入队。卸载时会排空 120s。

`qxync status` 新增一行：

```
删除队列  : 待删 0｜推送中 no｜已删 128｜失败 0｜重试 0｜批次 3
```

> `待删 > 0` 只应持续几百毫秒（推送中）；`失败 > 0` 表示有删除重试超限被放弃，
> 此时 NAS 上会残留文件，需要人工处理。

## 顺带修掉两个自查发现的缺陷

**`rm -rf` 父子删除冲突**：内核会**同时**把 `rmdir(dir)` 和 `unlink(dir/子)` 交给队列。
父目录删掉后再删子项必然报「不存在」，白重试到放弃、让失败计数虚高。现在发请求前
剔掉「父目录同批被删」的子项，前缀匹配按**完整路径段**判断（所以 `victim` 被删不会
影响 `victim2.txt`）。

**重试计数被重置**：原先重试时拿批内**最大**次数覆盖每项计数，已重试 4 次的项会被
打回 1 次，永远达不到放弃阈值。现在逐项 `+1`、各自判定放弃。

## 安全性：熔断没有因为异步化而放松

**`DeleteGuard`（100 项 / 60s）照旧生效，且仍然在入队之前**。大批量误删依然回
`EACCES`，不会因为改成异步就悄悄溜进队列。

需要明说的取舍：异步删除是「**本地是权威**」—— 入队即返回，远端删除失败时本地文件
已经消失了。缓解手段是失败重试到超限会记入 `status` 的失败计数与 daemon 日志，
运维可以据此发现并人工补删。这与上传队列同源。

## 验证情况

- 全量 `cargo test --workspace`：**211 passed / 0 failed**（新增 12 条，
  含回收站识别的正反用例、`rm -rf` 父子冲突、重试计数、跨重启恢复）。
- **批量删除已真机验证**：`m11_batch_delete_contract` 用真实凭据在 NAS 上跑通 ——
  5 个文件一次请求**全部**删除（验证「不漏项」，这是攒批正确性的前提），
  文件 + 目录混合批次正常，空批次是合法 no-op。
- **未在真机验证**：整体挂载体验。开发环境无 `/dev/fuse`，无法真实挂载跑一遍。
  建议本机实测：挂 `--rw` 后 `rm` 一批文件，观察是否秒回、`status` 里批次是否合理。

## English

# qxync v0.4.3 — No trash bin on the mount point, and deletes no longer block

**中文** · [English](#english)

No breaking changes: configuration, task files, cache layout and CLI arguments are all
unchanged. Upgrading means replacing the binaries and restarting the daemon. The delete
behaviour change is **intentional** (see below) and needs no configuration.

## TL;DR

Deleting a file in the mount point sent it to a trash bin, and deleting took a long time.
Neither of those was actually done by qxync — this release removes both root causes.

## The trash bin was Dolphin's, not qxync's

First, a clarification: qxync has **never had any trash logic** (grepping the whole repo
for `trash`/`Trash`/`recycle` returns zero hits). The trash bin you saw comes from the
desktop environment.

The measured environment is **KDE Plasma + Dolphin 26.08.1**. Dolphin does not call
`unlink` when deleting; it follows the **FDO per-volume trash protocol**: it creates
`.Trash-$UID/{files,info}` **on the same volume**, "moves" the file in, and writes a
`.trashinfo`.

A mount point *is* a volume — so the trash bin was created inside the mount point and its
contents ended up on the NAS. The evidence is `~/qxync-mnt/.Trash-1000/info/*.trashinfo`
recording `Path=qxync-test/...` (a path relative to the mount point).

**Can it be turned off in configuration? No.** Older KIO supported a per-path
`[DisabledFor]` key in `ktrashrc`, but **KIO 6.30 removed that key** — grepping `DisabledFor`
across the five KIO libraries on this machine returns zero hits, and the plugin only keeps
`UseSizeLimit` / `UseTimeLimit` / `LimitReachedAction` / `Days`, with no per-path opt-out.
(Articles about "disabling the Linux trash bin" are either outdated or written for
GIO/Nautilus; they do not apply to Dolphin.)

**So it has to be enforced at the filesystem layer.** FUSE write entry points now reject
trash names with `EPERM`:

| Entry point | Effect |
|---|---|
| `mkdir` | KIO cannot create `.Trash-$UID` → cannot enable the volume trash |
| `create` / `rename` | blocks "move into the trash bin" and "move out of it" |
| `unlink` / `rmdir` | the trash bin itself cannot be deleted either (no back door) |

`mkdir` being blocked is the key: KIO must create that directory before it can use the
trash, and failing to create it falls back to its built-in **direct delete** — exactly the
requested behaviour.

Matching is **exact per path segment** (any segment matching is rejected), so ordinary
names like `.recent`, `.trash`, `a.Trash-1000.txt` or `@Recycled` are unaffected.

## Why deletes were slow: synchronous blocking, 2–3 round trips per file

`remove_entry` used to be `rt.block_on(client.delete_entry(..))` — unlink waited for the
**NAS to answer** before returning. Deleting N files meant N serial round trips.

**Via Dolphin it is worse**: Dolphin does not make one unlink call, it "copies into
`files/` and writes `info/*.trashinfo`", and every step is a FUSE call that goes back to
the NAS — **2–3 round trips per file**. Stacked together, that is the spinner you saw.

## Now: return immediately, coalesce in the background

This matches the **official client's shape**. Qsync official (Smart Delete) is
*"deleted files on the local device are retained on the NAS"* — **locally effective
immediately, advanced asynchronously server-side**. This release is exactly that:

- `unlink`/`rmdir` **return immediately**; the local node table and mapping are dropped
  at once
- Remote deletes are pushed by a `qxync-delete` worker that coalesces into batches
- **Same-directory items are merged into one request**: `file_total` on
  `qsyncsrv.cgi?func=delete` was always meant to be "items in this batch" (`stat`/
  `set_mtime` hardcode it to `1` only because those handle one file per call). Items are
  now grouped by directory, capped at 50 per batch, with a 200 ms coalescing window.

**Benefit**: deleting N files in one directory drops from **N serial round trips** to
roughly **N/50**; deleting via Dolphin is no longer 2–3 round trips per file.

**Crash recovery**: jobs are persisted to a `deletes` state table (the same `queue.db` as
the upload queue) with identical semantics — **the table *is* the set of unfinished jobs**
— and the daemon re-queues them on restart. It is drained for up to 120 s on unmount.

`qxync status` gains a line:

```
删除队列  : 待删 0｜推送中 no｜已删 128｜失败 0｜重试 0｜批次 3
```

> `待删 > 0` should only last a few hundred milliseconds (while in flight); `失败 > 0`
> means a delete exhausted its retries and was abandoned, so the file remains on the NAS
> and needs manual cleanup.

## Two defects found in self-review, fixed here

**`rm -rf` parent/child delete conflict**: the kernel hands both `rmdir(dir)` and
`unlink(dir/child)` to the queue at once. Once the parent is gone, deleting the child
necessarily fails with "not found", burning retries and inflating the failure count.
Children whose parent is deleted **in the same batch** are now dropped before the request
is sent, with prefix matching on **whole path segments** (so a deleted `victim` does not
affect `victim2.txt`).

**Retry counts were being reset**: retries used to overwrite each item's counter with the
batch maximum, knocking an item that had failed 4 times back to 1 so it could never reach
the give-up threshold. Counts now increment per item and each decides independently.

## Safety: the circuit breaker was not relaxed

**`DeleteGuard` (100 items / 60 s) is unchanged and still runs before enqueueing.** A large
accidental delete still returns `EACCES` and cannot slip into the queue just because
deletes became async.

The trade-off worth stating plainly: async deletion means **local is authoritative** —
enqueue returns immediately, so if the remote delete fails the local file is already gone.
The mitigation is that retries which exhaust are reflected in the `status` failure count
and the daemon log, so they can be found and cleaned up manually. This mirrors the upload
queue.

## Verification

- Full `cargo test --workspace`: **211 passed / 0 failed** (12 new, covering positive and
  negative trash-name matching, the `rm -rf` parent/child conflict, retry counting, and
  restart recovery).
- **Batch delete verified on real hardware**: `m11_batch_delete_contract` passes against
  the NAS with real credentials — 5 files deleted in a single request **with none
  missing** (this is the precondition for batching being correct), a mixed file+directory
  batch works, and an empty batch is a valid no-op.
- **Not verified on real hardware**: the end-to-end mount experience. The development
  environment has no `/dev/fuse`, so an actual mount could not be exercised. Worth
  testing locally: mount with `--rw`, `rm` a batch of files, check that it returns
  immediately and that the batch counts in `status` look sane.
