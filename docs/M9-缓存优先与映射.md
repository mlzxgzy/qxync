# M9 —— 缓存优先 + 映射本地化（NAS → 缓存 → 映射）

> 目标：把「`ls` 要等一秒、`cat` 明明缓存过还要等几秒」消掉。
> 判据：真机 NAS + 真挂载，见文末验收表。实现集中在
> [`crates/qxync-fuse/src/lib.rs`](../crates/qxync-fuse/src/lib.rs)，
> daemon 侧只多了「定时把 NAS 文件列表推进视图」与「注入 `inval_inode`」两处接线。

---

## 1. 心智模型

```
   NAS  ──定时轮询（文件列表）──►  映射（挂载点里有什么）  ──►  ls / lookup / stat
     │
     └──按需/后台（内容字节）────►  缓存（本地内容 + 位图）  ──►  cat / read
```

* **映射**：挂载点里有哪些名字、大小、类型。**完全来自 NAS 的文件列表**，由 daemon 的
  变更轮询（默认 30s）定时刷新 —— 不刷新就还是旧的，这是刻意的（不是「每次访问都去问 NAS」）。
* **缓存**：真正的内容字节，落在 `<cache>/<hash>_<name>` 的稀疏文件里；
  「哪些区间已经就绪」记在位图 `<cache>.qxstate` 里，**跟内容一起持久化**。
* **内容更新**：NAS 上那份变了以后 ——
  * 本地**脱水**（没有内容）→ 只更新元数据（占位符），内容等读到时按需取；
  * 本地**有水**（整份在本地）→ 旧内容**先留着继续可读**，后台把新版本整份拉下来
    **原子换上**；换上的同时元数据（size/mtime）一起切。
    * 刷新落地前 `cat` 拿到的是**完整旧版本**（不是半新半旧），`stat` 也是旧的大小；
    * 刷新落地后 `cat` 拿到**完整新版本**，`stat` 同步变成新大小。

## 2. 症状与根因（修复前）

| # | 症状 | 根因（旧代码） |
|---|---|---|
| 1 | 同一会话里第二次 `cat` 很快，**换个会话/重启后 `cat` 明明文件就在磁盘上却要几十秒** | `chunks_done`（区间位图）**只活在内存里**。节点表是内存态，`insert_node` 新建节点时位图为空；`cache_file_for` 把位图初始化为全 `false` —— 于是「磁盘上有内容」不算数，`read()` 逐个区间重新问 NAS |
| 2 | `ls` 每次都要等一次网（约 0.3–1s） | `readdir` → `load_children` → `client.list()`；`lookup` → `client.stat()`。**没有任何本地清单**，每次访问都是一次 NAS 往返 |
| 3 | 远端文件一变，本地读就变慢 | `apply_remote_meta` 在 size/mtime 变化时**直接删掉缓存内容**；下次 `read()` 只能整份重新下载（阻塞在读路径上，用户看到「cat 卡住」） |

实测（真机 NAS，`/home/qxync-test/m9-4m.bin` 4 MiB，见 §5）：

| 场景 | 修复前 |
|---|---|
| 同一会话第二次 `ls` | 0.50 s |
| 重启 daemon + 重新挂载后第二次 `ls` | 0.32 s |
| 重启 daemon + 重新挂载后 `cat`（内容就在磁盘上） | **23.75 s** |

## 3. 修复

### 3.1 水合位图落盘（`lib.rs` §「水合位图落盘」）

* 格式：`magic(8) + version(4) + chunk_size(8) + size(8) + mtime(8) + nchunks(8) + bitset`。
  `nchunks` 必须与 `size/chunk_size` 自洽，否则整份作废（防损坏文件把内存撑爆）。
* 写：先 `pwrite` 内容、后写位图；位图先写 `.tmp` 再 `rename`。
  崩在中间只会「位图比内容旧」（至多重下一个区间），绝不会把稀疏空洞里的 0 当成真数据。
* **认领**（`cache_file_for`，[`lib.rs:2375`](../crates/qxync-fuse/src/lib.rs)）：
  缓存文件存在 + 位图存在 + `chunk_size/size/mtime` 与节点一致 + 文件长度对得上
  → 直接恢复区间表，`read()` 完全不用问 NAS。签名对不上（NAS 上那份变了）就整份作废。
* 落盘时机：区间水合成功、本地写入「真的让某个区间翻成就绪」、`release()` 兜底
  （把最终的 size/mtime 记下来）、认领时不重复写。
* 清理：脱水 / 冲突失效 / 远端删除 / 本地 unlink / 改名迁移，内容与位图一起处理。

### 3.2 目录清单快照（「映射」，`lib.rs` §「目录清单快照」）

* `Inner.dirs: HashMap<远端目录, DirListing>`（条目 + 抓取时间），`Arc<Vec<DirEntry>>` 共享。
* `readdir` → `dir_entries`（[`lib.rs:2065`](../crates/qxync-fuse/src/lib.rs)）：
  **有快照就直接吃**；没有才同步问一次 NAS。快照过期（默认 30s）只丢一个**后台**补拉任务，
  调用方不等。
* `lookup` → 先查节点表，再查**父目录快照**：命中就建节点，没命中直接 `ENOENT`
  （不再为「这个名字存不存在」跑一趟 NAS）。只有父目录**从没列过**的冷路径才 `stat` 一次。
* 定时刷新：daemon 的变更轮询每列完一个目录就 `FsHandle::apply_listing(dir, entries)` 推给
  挂载视图（`crates/qxync-daemon/src/sync.rs`）；目录没了就 `drop_listing`。
  这就是「映射的更新是定时的」。
* 本地改动同步进快照：`create`/`mkdir`/`unlink`/`rmdir`/`rename` 立刻 upsert/remove，
  否则 `rm a` 之后 `ls` 会把快照里的 `a` 复活成幽灵节点、新建的文件要等一轮轮询才可见。

### 3.3 远端变更语义（「有水」不阻塞 `cat`）

* `apply_remote_meta`（[`lib.rs:1064`](../crates/qxync-fuse/src/lib.rs)）：
  * **脱水**（任何区间都没就绪）→ 立刻采纳新元数据，丢掉空的稀疏文件；
  * **部分水合** → 丢掉重下（半新半旧最危险）；
  * **整份有水** → 只记 `pending = (size, mtime)`，`attr` 保持旧值（内容与元数据必须是一套），
    旧内容继续可读。
* 后台刷新 `spawn_content_refresh`（[`lib.rs:1284`](../crates/qxync-fuse/src/lib.rs)）：
  整份下载到 `<cache>.refresh` → `install_refreshed`
  （[`lib.rs:533`](../crates/qxync-fuse/src/lib.rs)）在**节点操作锁**内 `rename` 换上，
  一次切换 `attr` / 区间表 / 位图；随后让内核丢掉旧 page cache（daemon 挂载后注入的
  `Notifier::inval_inode`）。连续失败 3 次退回「丢掉旧内容、读到时按需水合」。
* 安装前会复查：节点还在、没被改脏、没被脱水、签名没又变、缓存路径没换 —— 任一不满足就作废，
  **绝不覆盖用户改动**。
* 换文件与 `read`/`write` 抢同一把节点锁，而且这次等锁在 blocking 线程池里做，
  不会把 FUSE 的 tokio worker 饿死。
* **baseline 等刷新落地再推进**（daemon `sync.rs` 的 `RefreshRemote` 分支）：
  否则用户在这段窗口里基于旧内容改文件，会被三向合并误判成「本地覆盖远端」而不是冲突。

## 5. 验收（真机 NAS，2026-10-03）

环境：`<NAS 域名，见本地 docs/测试环境.local.md>`（QXNYC_POLL_INTERVAL=5 只为缩短验收时间；默认 30s），
隔离的 `XDG_*` + 独立 socket + 独立挂载点，不去打扰正在用的实例。
被测文件：`/home/qxync-test/m9-4m.bin`（4 MiB，`/dev/urandom` 生成，验收后删除）。

| 场景 | 修复前（v0.3.0 release） | 修复后 |
|---|---|---|
| `ls` 冷（该目录第一次，必须问一次 NAS） | 0.42 s | 0.23 s |
| **`ls` 热（紧接着第二次）** | **0.50 s** | **0.001 s** |
| `cat` 冷（首次必须下载 4 MiB） | 27.53 s | 27.97 s |
| `cat` 热（同会话第二次） | 0.002 s | 0.001 s |
| 重启 daemon 后 `ls` 冷 | 0.65 s | 1.36 s（一次 NAS list，WAN 抖动） |
| **重启 daemon 后 `ls` 热** | **0.32 s** | **0.001 s** |
| **重启 daemon 后 `cat`（磁盘上已整份缓存）** | **23.75 s** | **0.115 s** |
| 等一轮轮询后再 `ls` | 0.47 s | 0.001 s |
| 缓存目录 | 只有内容文件 | 内容文件 + `<cache>.qxstate`（48 B） |

远端变更语义（同一个 4 MiB 文件，NAS 上被换成 2 MiB 的另一份内容）：

| 时刻 | 结果 |
|---|---|
| 刷新在飞期间的 `cat` | 0.002 s，sha256 = **旧版本**（完整，不是半新半旧） |
| 刷新在飞期间的 `stat` | `size=4194304`（旧值，与内容一致） |
| 刷新落地后的 `cat` | 0.002 s，sha256 = **新版本** |
| 刷新落地后的 `stat` | `size=2097152`（与内容一起切） |

单测：`cargo test -p qxync-fuse` —— **34 通过 / 0 失败**，其中 M9 新增 6 条：
位图编解码与损坏防护、重建节点后认领缓存（**用 `nas.invalid` 当 NAS：只要还问一次网络就必然失败**）、
清单快照服务 `readdir`/`lookup`（同上）、有水时的远端变更语义、原子换上的元数据一致性、
换上前节点被改动则作废、刷新连续失败退化为按需水合。

## 6. 取舍与没做的

* **部分水合**（读了一部分的大文件）在远端变更时直接丢弃重下，不保留旧内容 ——
  半新半旧的文件比「多下一次」危险得多。
* **映射不落盘**：重启后第一轮 `ls` 仍要一次 NAS list，之后靠轮询重建（默认 30s 内覆盖所有
  已知目录 + baseline 目录）。要把冷启动也做掉，需要把 baseline 灌进视图。
* **快照的新鲜度 = 轮询节奏**：远端刚建的文件在下一轮轮询前不在「映射」里，
  `lookup` 会照实回 `ENOENT`（这正是「映射有啥全靠 NAS 文件列表」的语义）。
  想要更快可以调小 `QXNYC_POLL_INTERVAL`，或关掉轮询时靠 FUSE 侧 30s 的后台补拉。
* 后台整份刷新只对**整份有水**的文件触发；大文件在远端频繁变更时会重复整份下载
  （与 Qsync/OneDrive「本地可用就跟着更新」的语义一致，但流量是真的）。
* `fuse-matrix.sh` / `m8x-matrix.sh` 等真机矩阵本次**未复跑**（需要真凭据 + 真窗口），
  已跑的判据是上面的真机前后对比 + `cargo test`。
