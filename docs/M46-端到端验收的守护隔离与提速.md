# M46 端到端验收：守护隔离、超时收尾与真机套件提速

> 背景：M45 把 19 个脚本 + 3 个 node 套件合并成一个入口后，用户给了权限「去测试吧」。
> 这一轮是**真正把所有档位跑一遍**（`--tier all`），结果又挖出四类问题：
> ① 跑验收会把用户桌面上的 daemon 顶掉；② 超时只杀子 shell，套件变孤儿继续动状态；
> ③ 真机套件挂载整棵 `/home`，新状态库首轮全量对账把套件拖到 10～30 分钟；
> ④ 若干断言停留在旧行为（M8.3 的 schema v3、M8.2 的「默认不恢复挂载」）。

## 1. 事故：跑 fuse 档会把用户守护换成测试守护

**现象**：`--tier all` 跑到 fuse 档时超时（300s），随后入口的守护保护报
「你桌面上的 qxyncd 被停掉了」。日志证据：

```
qxyncd 收到 shutdown 请求（IPC）
qxyncd 退出（IPC shutdown（qxync daemon stop），已卸载 1 个挂载点）
```

**根因**：`fuse-matrix.sh` 里有 6 处 `"$QS" daemon stop/start`，但脚本**没有隔离
`XDG_RUNTIME_DIR`**，`daemon stop` 解析到的就是用户默认 socket
（`/run/user/1000/qxync/qxyncd.sock`）。于是它停掉用户的守护，再用本脚本的
`XDG_CONFIG_HOME`（测试配置）起一台 `target/debug/qxyncd` 顶在同一个 socket 上——
用户守护再也回不来，托盘/GUI 也开始对着测试守护说话。

**修法**（与 M45 修 `gui-matrix` 同一手法）：脚本开头声明私有 runtime：

```bash
export XDG_RUNTIME_DIR="${QXNYC_TEST_RUNTIME_HOME:-$RUNDIR/fuse-runtime}"
export QXNYC_SOCKET="$XDG_RUNTIME_DIR/qxync/qxyncd.sock"
```

`cleanup()` 只停这个 socket 上的 daemon。fuse 不需要 GUI，所以不像 `gui-matrix`
那样透传 Wayland/X11 socket。

## 2. 事故：超时只杀子 shell，套件变孤儿继续跑

入口 `run_one` 原实现：

```bash
( suite_env "$name"; cd "$REPO" && suite_exec "$name" ) >"$log" 2>&1 &
...
kill -TERM "$pid"
```

`$pid` 是那层子 shell，`bash fuse-matrix.sh` 是它的**子进程**，不会被带走。
实测：10:51 的 fuse 档超时被「杀」后，孤儿继续跑了 9 分钟，最后执行到 M3 段的
`daemon stop` —— 正好用**旧脚本**的默认 socket 停掉了用户的 daemon。

**修法**：

1. 套件用 `setsid` 起在**自己的进程组/会话**里，超时 `kill -- -$pid` 带走整棵树；
2. 再按 `pgrep -P` 递归兜底；
3. 再按脚本路径 `pkill -f "$TESTS/$name.sh"` 兜底（防 daemon 自己 setsid 逃逸）；
4. 入口**开跑前**扫一遍上次中断留下的套件进程并清掉——只匹配
   「argv[0]=bash 且 argv[1]=$TESTS/*.sh」，不做任何按名字的模糊 pkill。

因为套件改在独立进程里跑，`suite_env` / `suite_exec` 与它们用到的变量改为 `export -f` / `export`。

## 3. 提速：真机套件不再挂整棵 `/home`

**现象**：`m83` 619s、`m84` 30 分钟超时、`fuse` 卡在 M2c 25 分钟无进展。
共同点：套件把任务根设成 `/home`（该 NAS 上 **5505 个目录**）。新状态库（每次开跑
`rm -rf`）首轮必须做**全量对账**，在 WAN 上要十几～几十分钟；期间 `sync --once`
（会等一轮对账）、M2c 的 30s 刷新窗口、上传后的挂载点可见性全被堵死。

**修法**：所有真机套件默认**只挂自己的夹具目录**，需要整棵树时用
`QXNYC_REMOTE_ROOT=/home` 覆盖：

| 套件 | 原根 | 现根 | 结果 |
|---|---|---|---|
| `fuse-matrix` | `/home` | `/home/qxync-test` | M2c 刷新/缓存失效 2 项从失败转通过；总时长 900s+ → 744s（仍有 5 项时序失败，见 §6） |
| `m83` | `/home` | `/home/qxync-test` | **619s → 16s**，3 失败 → 0 |
| `m84` | `/home` | `/home/qxync-test/m84` | **30 分钟超时 → 198s，99/0 全过** |

实现上用 `REMOTE_ROOT` + `REL`（夹具相对挂载根的路径）统一替换，`$MNT$RELV`
写法不变。

| `fuse` M2c-2 | 远端删除后 15s 内节点消失 | 慢链路 + 2s 轮询不够 | 窗口 15s → 60s |

## 5. 夹具：NAS 上的 `/home/qxync-test` 曾整个消失

`fuse-matrix` 第一轮全挂，日志全是「文件不存在」。查远端：
`qxync ls /home/qxync-test` → `status=5`；`/home` 列表里没有 `qxync-test`。
`xtask/probe/qs_fixture.py fixture` 可重建，但它硬编码 `USER="test1"`，且登录不带
`security_code`（2SV 账号直接被拒）。本轮用一次性包装脚本（补 TOTP 后调用
`build_fixture`）重建了 128 MiB 夹具。**待办**：给 `qs_fixture.py` 加
`QXNYC_TEST_USER` / `QXNYC_TEST_OTP` 支持，避免下次再手搓。

## 6.5 剩余 5 项的根因（全部定位，1 产品 bug + 2 测试编排 bug + 2 假通过）

上一轮把「跨目录 move 可见性」怀疑成 NAS 侧延迟。本轮先写了个真机探针
（`sync.rs` 的 `m46_move_rename_visibility_probe`，`#[ignore]`，走 `logged_in()`
脚手架）**排除**了这个假设：纯 HTTP 两步 move+rename 后，stat / list / get
全部 **0.1~0.3s** 可见。问题全在我们自己的链路上。

### ① 产品 bug：直连模式挂载的改名/删除与 NAS 分叉（跨目录 move 失败的真因）

**最小复现**（直连挂载、无 daemon）：`printf > mnt/rn-a.txt` → 等上传可见 →
`mv rn-a.txt rn-b.txt` → **NAS 上没有 rn-b.txt、rn-a.txt 原样留着**。日志实锤：

```
改名: 远端没有老副本（本地新建后未上传），只做本地改名: /home/qxync-test/rn-a.txt -> /home/qxync-test/rn-b.txt
```

**根因**：上传成功的 success hook（`mark_remote_known` / `clear_dirty` /
`note_uploaded_listing`）**只在 daemon 挂载时接线**（daemon.rs 的
`set_success_hook`）。直连模式（CLI `qxync mount`，没有 daemon）上传成功后
`remote_known` 永远停在 `false` —— 紧接着的改名/删除被判成「远端没有老副本」
走**纯本地**分支：改名不同步到 NAS（旧名字幽灵）、删除跳过远端。fuse-matrix
的 M2b 段恰好是直连挂载（M45 私有 runtime 后 M2b 时段没有 daemon），所以
「跨目录 move + 改名生效」从 M45 起稳定失败；更早的间歇失败取决于当时 socket
上有没有 daemon。

**修复**：`with_upload_queue` 里装一个**默认 success hook**（做 FUSE 侧三件事：
清单条目刷签名、`remote_known=true`、无下一版时清脏）。daemon 挂载时用带
baseline 推进的完整 hook **覆盖**它 —— daemon 行为一个字节不变，直连模式拿到
同样的三个事实。修复后复现脚本里两种改名都打到 NAS。

### ② 测试编排 bug：M2c-3/3b 的 keep1 从未存在

旧顺序：`sync --interval 0`（暂停轮询）→ put keep1-6 → **`ls`/`cat`（建节点）**
→ `sync --once`（采纳 baseline）。轮询已暂停时挂载点吃的是**暂停前的旧清单**
（没有刚 put 的 keep1-6）→ `ls` 建不出节点、`cat` ENOENT、keep1 从未水合。
熔断轮 `blocked=5` 是**对的**（baseline 里有、远端没了），断言查的却是一个
从未存在的文件。修法：`sync --once` 挪到 `ls`/`cat` **之前**（先推新清单，
再建节点）。

### ③ 测试编排 bug：M2c-4 的「冲突」永远构不出来

旧顺序：本地改 4 MiB → **等上传完成** → 改远端 → `sync --once` 期待冲突。
但上传落地时 success hook 已把 baseline 推进到本地签名，远端再变只是
RefreshRemote（日志实锤：`updating=1`，冲突计数 0）—— 这是引擎**设计好的**
语义（防「自己刚传上去的新版被误判成冲突」）。要构冲突必须让本地改动
**还在途**时远端就变。修法（§6 建议的注入点落地）：M2c 段的 daemon 带
`QXNYC_TEST_UPLOAD_HOLD_MS=20000` 启动，`cp` 后上传被 hold 摄住，窗口内
`--direct put` 改远端 → 三向判定必为 Conflict；`resolve_conflict` 会取消被
hold 的作业（`st.active` 在 pop 时置位，hold 期间 `is_active()=true`，cancel
+ drain 30s > hold 20s 接得住）、等它醒来丢弃、再重判。M2c 里走队列的只有
cf.txt（M2c-1/2/3 全是 `--direct`），hold 不影响别的段；M3 起 unset。

### ④ 假通过：陈旧产物

- `mx-mv.out` / `mx-new.out` 是 `$RUNDIR` 里的**跨轮存活**文件：get 失败时
  `cmp` 对着上一轮的旧文件报「内容一致」（真机踩过：mv 后 get 不到，cmp 对着
  10:52 的旧文件通过）。修法：get 前先 `rm -f`。
- NAS 夹具同样跨轮存活：上一轮残留的 `r (conflicted copy …).txt` 会被
  `grep 'conflicted copy'` 捞进来、`head -1` 锁死在错误名字上。修法：锚定
  `^cf (conflicted copy`。

### ⑤ 一条作业毒化三个段：M2c-4 的收尾时序（9 条失败的公共根因）

修完 ①～④ 后实跑，M2b/M2c-3/M2c-4/4b/4c 全绿，但 M2c-4d + M3-4b/4c/5b +
M23-2b/3/3b/3c/3d 共 9 条仍红。追进 daemon 日志，发现它们全是**同一条卡住的
上传作业**的下游：

```text
M2c-4 的冲突副本（4 MiB）上传在 WAN 上卡了 80s+（请求发送失败 → 队列按离线暂停）
→ M2c-4d 的 60s 窗口没等到副本（它要从远端清单物化，上传没完成就看不见）
→ M2c 收尾没等队列：卸载被在途作业拖死、挂载记录（mounts.json）没清掉
→ 后续每个 daemon 启动都把 mnt-m2c 恢复回来
→ M3 的队列里这条作业对着已删除的 mx2 无限重试（status=20）→ 队列永远排不空
   → M3-4b（排空断言）/ M3-4c（dirty 清不掉）/ M3-5b（脏文件不可脱水）连带失败
→ M23 的 Baloo 门禁检查**所有**挂载点：未排除的 mnt-m2c 把 settings_save 全拒
   → M23-2b + M23-3* 连带失败（复现实锤：门禁报错点名 mnt-m2c）
```

修法（M2c-4 段内闭环，不给下游留毒）：

1. **M2c-4e（新增断言）**：M2c-4c 之后**等队列排空**（副本真正传上去，预算
   240s——WAN 抖动时 4 MiB 也要 80s+）；
2. 排空后 `sync --once` 推一轮清单，副本才在挂载点里可见（副本节点不是本地
   建的，只能从远端清单物化）→ M2c-4d 的窗口从 60s 收窄到 30s；
3. 收尾时队列已空 → 卸载干净 → 挂载记录清掉 → 后续 daemon 不再恢复 mnt-m2c
   → M3 的队列干净、M23 的门禁只看得到自己的挂载点。

顺带修掉本轮环境里的陈旧记录（`fuse-state/…/mounts.json` 里残留的 mnt-m2c
一行——它让「起一个新 daemon」也会恢复出这个挂载点）。

## 7. 结论与建议

- **发版闸门（gate）已从「人肉按顺序敲」变成一条命令**；本机真机档从「一小时起、且会杀
  你的守护」变成「m82+m83+m84+m5+m7 合计约 6 分钟，且不碰桌面守护」。
- 以后新增/改真机套件，遵循三条：**私有 `XDG_RUNTIME_DIR`**、**任务根收窄到夹具**、
  **等待用 poll 而不是 sleep**；需要编排同步时序的用例一律走注入点
  （`QXNYC_TEST_UPLOAD_HOLD_MS`），不靠竞速。
- §6.5 的产品修复（直连模式默认 success hook）意味着 **CLI 直连挂载从此是一等公民**：
  改名/删除与 NAS 不再分叉。此前任何用 `qxync mount`（不经 daemon）做过写操作的人，
  NAS 上都可能留着旧名字的幽灵文件 —— 建议发版说明里提一句。
