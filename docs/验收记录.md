### 2026-10-18 新建任务默认路径（M18，v0.6.2 之后）

没有新增字段（回退旧版本兼容）。设计与取舍见 [`docs/M18-任务默认路径.md`](M18-任务默认路径.md)。

### 2026-10-18 两步验证（2SV / TOTP，v0.6.2）

**交付**：QNAP 两步验证的 TOTP 支持。以前 `authLogin.cgi` 只发 `user + pwd(base64)`，
账号一开 2SV 就永远登不上（CLI / daemon 自动重登 / GUI 全一样），而且报错还误导成
「检查口令编码」。真机实测（2026-10-18，账号已开 2SV）确认：**同一份表单多带
`security_code=<6 位 TOTP>` 即可 `authPassed=1` + `authSid`**（qxync 实现照 QTS Web UI 走两步：
第一次请求与旧版逐字节相同，只有 `need_2sv=1` 时才发第二次带码请求）；不带时
`need_2sv=1`，验证码错误时同样 `authPassed=0 / need_2sv=1` 且没有 `errorValue`。
实现与边界见 [`docs/M17-两步验证.md`](M17-两步验证.md) 与 `CHANGELOG.md` 的 `[0.6.2]`。

**环境**：二进制与 `cargo test` 都跑在 **0.6.2** 上；2SV 用例在**已开 2SV 的真机测试账号**上跑，
「未开 2SV 回归」在另一台测试机的 `test1`（未开 2SV）上跑。

| 判据 | 结果 |
|---|---|
| 不带第二因素登录（账号已开 2SV） | ✅ 失败并给出明确指引（提示用 `--otp-secret` / `--otp-code`），不再只回 `authPassed=0` / 不再甩「检查口令编码」 |

### M10 验收结论（2026-10-03）

**交付**：会话热更新（sid 续期 / 重登录推挂载）—— ① `Client.sid` 改成 `Arc<RwLock<..>>`，
`set_sid(&self)`/`clear_sid()` 跨 `Arc<Client>` 立刻可见；② `qxync_core::Error::is_auth()`
收口三层共用的「会话失效」判定（4/5 号 status 也算），`map_err` 据此归 `ErrorKind::Auth`；
③ `login_internal` 成功后把新 sid 推给**同账号**的挂载点（换账号只告警），`logout`
顺手清挂载点 sid；④ FUSE 注入 `SidRefresher`，`readdir`/`lookup`/区间水合/`mkdir`/
`unlink`/`set_mtime`/`rename` 遇鉴权失败 → daemon 重登 → **原地重试一次**；
⑤ 会话经纪人（FUSE 线程同步等、daemon 侧串行重登、3s 去重）；⑥ 会话保活（默认 120s，
`QXNYC_SESSION_KEEPALIVE=0` 关）+ 轮询遇 Auth 重登。设计见
[`docs/M10-会话热更新.md`](M10-会话热更新.md)。

| 判据（真机 NAS；隔离 XDG + 独立 socket + 独立挂载点；`POLL_INTERVAL=0`、`KEEPALIVE=0` 排除干扰） | 结果 |
|---|---|
| 挂载 + 列目录建立会话 | ✅ |
| IPC `logout`（服务端 sid 作废 + 挂载点 sid 清掉） | `登录状态：未登录` |

#### 🔧 附：修掉一个收口时发现的既有 bug —— 「挂载失败 → daemon worker panic」

**现象**：任何**挂载失败**都会把 daemon 的那个 IPC worker 打成 panic，客户端只看到
「daemon 提前关闭了连接」，拿不到真正的错误；日志里是 tokio 的
`Cannot drop a runtime in a context where blocking is not allowed`。触发条件不止「没有 `/dev/fuse`」——
挂载点被 `fusermount3` 拒（例如 `/proc`）同样会中招。

**根因**（`crates/qxync-fuse`）：`QxyncFs` 里握着一个自己的 tokio `Runtime`（FUSE 回调里用它
`block_on` NAS 调用）。daemon 是在 **async IPC 命令**里调 `qxync_fuse::spawn` → `fuser::spawn_mount2`；
挂载失败时 fuser 会把 `fs` **就地在那个 async worker 线程上 drop** —— 而 tokio 的 `Runtime::drop`
要等阻塞池收尾，这件事在异步上下文里被禁止，于是 `blocking/shutdown.rs` 直接 panic。

**修法**（`qxync-fuse`）：把那个 runtime 包成 `FsRuntime`，析构时按上下文选路 ——
在 tokio 上下文里用 tokio 官方推荐的 `shutdown_background()`（不等阻塞池），
在普通线程上保持原来的等待语义（正常卸载时 `fs` 是 fuser 线程析构的，行为一字不改）。
另外在 `qxync-fuse` 里加了**回归单测** `dropping_fs_inside_async_context_does_not_panic`
（修复前该测试 panic，修复后通过；`cargo test --workspace` 里常驻）。

| 同一场景（FUSE 设备不可用，`unshare -rm` + 把 `/dev/null` 绑到 `/dev/fuse`） | 修复前 | 修复后 |
|---|---|---|
| `qxync mount …` | rc=3「❌ daemon 提前关闭了连接」 | rc=5「❌ 挂载失败: Error calling mount() … EINVAL」 |
| daemon 日志 panic 条数 | **1** | **0** |
| 后续 `qxync daemon status` | 该连接已被打死 | 正常 |
