### v0.7.7 —— 修复 v0.7.6 启动即 panic（daemon 起不来）（2026-10-21）

> 用户报告 `qxync daemon start` 报「qxyncd 已派生但 socket 未就绪」且日志零
> 线索。定位：v0.7.6 的 `init_logging()` 里 `log::set_logger(&FuserLogBridge)`
> 与 `tracing_subscriber::registry().init()`（内置 `LogTracer`）抢同一个全局
> logger → `SetLoggerError` → panic；daemon 化后 stderr 指向 `/dev/null`，
> 所以完全静默。详见 [`发布说明-v0.7.7.md`](发布说明-v0.7.7.md)。

| 项 | 结果 |
|---|---|
| 复现（修复前） | `/usr/bin/qxyncd --foreground` → exit 101：`panicked at tracing-subscriber util.rs:94: failed to set global default subscriber`；修复前二进制 `--print-config` 同样 panic（exit 101） |
| `cargo test --workspace` | ✅ **526 通过 / 0 失败 / 21 忽略**（新增 2 个回归） |
| 新增 `qxync-daemon` 集成测试 | `logging_init.rs`：`--print-config` 存活（启动含日志初始化并正常退出）+ 日志目录不可写时降级 stderr、不 panic |
| `cargo fmt --all -- --check` | 0 diff |
| 真机全链路（隔离 XDG 目录 + 临时 socket） | ✅ `start` → socket 就绪 → `status` pong → `stop` 干净退出 |

**没跑的 / 未验（如实记）**：

* 本版只修「启动期必然 panic」的两条路径（log 桥冲突、日志文件建不出来）；
  「daemon 化后 stderr → `/dev/null`」这个环境事实没有改变 —— 将来若再有
  启动期 panic，仍需 `--foreground` 复现才能拿到回溯；
* 修复后二进制在**用户真机上的部署复验**（`sudo cp` 到 /usr/bin 后
  `qxync daemon start`、挂载恢复、同步继续）由用户执行，未在本环境代跑。

### 2026-10-18 大目录轮转对账（v0.6.4）

**交付**：真机反馈「目录数 228 超过单轮上限 200…本轮跳过删除判定」连续 87 轮重复。根因：
对账每轮都从排序开头只列前 `max_dirs_per_poll`（200）个目录，排序在后的目录**永远**轮不到；
「远端视图不完整 → 暂缓删除判定」因此永久生效，远端删除与这些目录里的判定永不执行。
修法见 [`docs/M2c-变更发现.md`](M2c-变更发现.md) 与 `CHANGELOG.md` 的「0.6.4」：

- **轮转扫描**：远端根每轮参与，其余目录从上一轮停下的位置之后接着列、到尾回绕；游标落在
  `sync.db` 的 `meta`（`reconcile_scan_cursor:<mountpoint>`），`qxync sync --once` 跨进程可续；
- **按目录判定**：「视图完整」从整视图收窄到单个目录 —— 只有本轮列过（列举成功，或 4/5/6
  经 `stat` 确认 `exist=0`）的目录里的候选才判定，未列到的目录里的条目一律暂不判定
  （不按缺失删本地），其它目录不陪绑；
- **改名配对**的已删侧同样要求「父目录本轮列过」，不把「没看到」配成一次改名；
- **4/5 正向确认**（复核补修）：列举回 4/5/6 时先用 `stat` 确认 —— stat 说存在 → 目录条目
  记进远端视图（防「父目录列举漏了它」时目录自身连子树被删）、内容本轮不判定；stat 也失败
  → 目录自身与内容都不判定；stat 成功不置 `auth_failed`（会话已证明有效），只有 stat 也
  auth 失败或远端根 4/5 才触发重登；
- **HTTP / 响应形状**：`get_list` / `stat` 检查 HTTP 状态与「像不像列表 JSON」（反代 502 的
  错误体、HTTP 200 的非列表 JSON 都不再被读成空目录），`list_limit` 不再把缺省
  `total=0` 当「总数 0」在第一页停止翻页。

**环境**：无真机（mock NAS 用本地 tokio HTTP 回放 `get_list` / `stat`；真实 `Client`、真实
`reconcile_view`、真实 SQLite 状态库；场景为 228 个目录各一个文件，另有 status 4/5/6、
HTTP 500、HTTP 200 非列表 JSON 与 stat 失败的模拟目录）。本轮**没有**在真机 NAS 上复跑
（不动用户数据）。

#### 🔧 附：修掉一个收口时发现的既有 bug —— 「挂载失败 → daemon worker panic」

**现象**：任何**挂载失败**都会把 daemon 的那个 IPC worker 打成 panic，客户端只看到
「daemon 提前关闭了连接」，拿不到真正的错误；日志里是 tokio 的
`Cannot drop a runtime in a context where blocking is not allowed`。触发条件不止「没有 `/dev/fuse`」——
挂载点被 `fusermount3` 拒（例如 `/proc`）同样会中招。

**根因**（`crates/qxync-fuse`）：`QxyncFs` 里握着一个自己的 tokio `Runtime`（FUSE 回调里用它
`block_on` NAS 调用）。daemon 是在 **async IPC 命令**里调 `qxync_fuse::spawn` → `fuser::spawn_mount2`；
挂载失败时 fuser 会把 `fs` **就地在那个 async worker 线程上 drop** —— 而 tokio 的 `Runtime::drop`
要等阻塞池收尾，这件事在异步上下文里被禁止，于是 `blocking/shutdown.rs` 直接 panic。

**修法**（`qxync-fuse`）：把那个 runtime 包成 `FsRuntime`，析构时按上下文选路 ——
在 tokio 上下文里用 tokio 官方推荐的 `shutdown_background()`（不等阻塞池），
在普通线程上保持原来的等待语义（正常卸载时 `fs` 是 fuser 线程析构的，行为一字不改）。
另外在 `qxync-fuse` 里加了**回归单测** `dropping_fs_inside_async_context_does_not_panic`
（修复前该测试 panic，修复后通过；`cargo test --workspace` 里常驻）。

| 同一场景（FUSE 设备不可用，`unshare -rm` + 把 `/dev/null` 绑到 `/dev/fuse`） | 修复前 | 修复后 |
|---|---|---|
| `qxync mount …` | rc=3「❌ daemon 提前关闭了连接」 | rc=5「❌ 挂载失败: Error calling mount() … EINVAL」 |
| daemon 日志 panic 条数 | **1** | **0** |
| 后续 `qxync daemon status` | 该连接已被打死 | 正常 |

> 顺带把这台的挂载点也验了：`qxync mount /proc`（非 root 必被拒）修复前同样 panic，修复后是
> `❌ 挂载失败: fusermount3: user has no write access to mountpoint /proc`，daemon 毫发无损。
