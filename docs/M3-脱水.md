# M3：脱水（释放本地缓存，只留占位符）

> 目标：**磁盘占用可控**——已水合的文件在「确认没人用」之后丢掉本地内容、变回占位符，
> 远端数据一点不动；下次 `cat` 再按需水合，数据必须还是对的。
> 状态（2026-09-30）：已实现并真机验收（`xtask/tests/fuse-matrix.sh` 的 M3 段 + 单测）。

---

## 1. 为什么这是最危险的操作（报告 12 §8）

脱水 = 主动删掉本地数据副本。做错的表现是**应用读到 0 或崩溃**：

* 内核 `page cache` 里还留着旧页，而本地缓存文件已经清了 → 应用读到**旧数据**（更糟：页被换出后再读可能是 0）；
* 还有进程 mmap 着这块数据 → 清内容后访问会 SIGBUS；
* 有未上传的本地改动 → 直接清掉 = 丢用户数据；
* 正在水合（在途写缓存）→ 和脱水打架，写出半截内容。

所以 M3 实现的是**完整安全检查链 + 固定顺序**，而不是「定时删缓存文件」。

---

## 2. 铁则：先 `inval_inode`，再清内容，再更新状态

```
① 安全检查（全部通过）
② Notifier::inval_inode(ino, offset=0, len=0)   ← 让内核丢弃这个 inode 的 page cache / attr
   └─ 失败 → 立刻中止，什么都不清（宁可占着磁盘，也不能让应用读到 0）
③ 删掉本地稀疏缓存文件
④ 更新占位符状态（chunks_done 全 false、cache=None、dirty=false）
```

代码里顺序是**固定的**：`FsHandle::dehydrate_now(remote, policy, mapped, invalidate)` 把
`invalidate(ino)` 作为参数注入（daemon 传 `Notifier::inval_inode(ino, 0, 0)`；单测传空实现），
但「先失效再清」由函数体保证，任何调用方都绕不过。

真机验证方式（矩阵 M3-2）：水合 → 脱水 → 把远端改成**同样长度、不同内容** → `cat`：
* 内核缓存已失效 → 走我们的 `read()` → 从远端拉新内容 → ✅ `ZZZZ…`；
* 若失效失败 → `cat` 会返回旧内容 → ❌。这条就是把铁则 2 变成可执行的验收项。

## 3. 安全检查链（`qxync_core::dehydrate::eligible`）

| 检查 | 判据 | 原因 |
|---|---|---|
| 是普通文件 | 目录不脱水 | 目录没有内容 |
| 有本地内容 | `hydrated_bytes > 0` | 本来就是占位符 → 无事可做 |
| pin | `pinned` / `excluded` → 跳过 | 报告 12 §8.1；`unpinned`/`unspecified` 允许 |
| 本地改动 | `dirty` | 未上传的改动不能丢 |
| 上传队列 | 该路径还有作业（含在途） | 同上 |
| 打开的 fd | `open_count > 0` | `open()`/`release()` 计数 |
| mmap | `/proc/*/maps` 扫描命中 | 报告 12 §8.1；FUSE 没有 CfAPI 的 oplock，只能自己扫。**实测补充**：Linux 下 mmap 会给映射保留 `struct file`，进程 `close(fd)` 也不会触发 FUSE `release` → 「打开的 fd」这一层其实已经拦住了 mmap；`/proc` 扫描是第二道防线（节点表重建后计数归零时仍能兜住） |
| 在途 | 节点操作锁 `try_lock` 失败 / 有在途区间下载 | 正在读写的不能动 |
| 刚访问过 | 距上次读/写 < `recent_secs`（默认 300s） | 避免「刚 cat 完就被清」 |
| 闲置阈值 | 距上次访问 < `idle_secs`（定时脱水时） | 定时策略的「耐心值」 |

其中「在途」用的是**节点级操作锁**：`read()` / `write()` / `setattr()` 全程持锁，
脱水用 `try_lock` —— 拿不到就本轮跳过。这样「读着读着被清空」在结构上不可能发生；
即使极端情况下 `read()` 在清空之后才拿到 fd，也只会走「重新水合」或按铁则 1 报 `EIO`，
绝不会返回 0 填充的假数据。

## 4. 触发方式

| 方式 | 命令/配置 | 说明 |
|---|---|---|
| 手动单文件 | `qxync dehydrate --path /home/x/big.bin` | 报告说的 `free-up-space` 等价物 |
| 手动全量 | `qxync dehydrate --all --force` | 所有挂载点里所有可清的文件 |
| 闲置定时 | `QXNYC_DEHYDRATE_IDLE=600`（或 `qxync dehydrate --idle-secs 600`） | 后台每 `QXNYC_DEHYDRATE_INTERVAL`（默认 60s）扫一次，只清闲置 ≥ N 秒的 |
| 磁盘阈值 | `QXNYC_CACHE_LIMIT=2G` / `25%`（或 `--cache-limit`） | 缓存超限 → **LRU**（最久没访问的先清）清到不超限 |
| 预演 | `--dry-run` | 只列目标与跳过原因，不动任何内容 |

> `qxync dehydrate` 不带参数 = 扫所有挂载点里「已水合且通过安全检查」的文件
> （默认仍有 300s「刚访问过」保护；`--force` 跳过它）。真实场景里手动清理通常加 `--force`
> 或等闲置阈值，避免把刚读完的文件立刻清掉。

* 限额支持 `512M` / `2G` / `1.5G` / `25%`（百分比按缓存所在文件系统总容量换算）。
* **默认不自动脱水**（`QXNYC_DEHYDRATE_IDLE=0` 且未设限额）：手动命令永远可用，
  定时/限额要显式开启——首次上线不做「用户没要求就删缓存」的事。
* 后台扫描是**常驻循环**：启动时即使没开，`qxync dehydrate --idle-secs N` 也能动态打开
  （`status` 里 `idle_secs` 会跟着变）。

## 5. 缓存模式（报告 12 §8.3）

挂载参数 `--cache-mode pagecache|direct`：

| 模式 | `open()` 返回 | 特点 |
|---|---|---|
| `pagecache`（默认） | `FOPEN_KEEP_CACHE` | 性能好（有 readahead、mmap 可用）；脱水必须严格按 §2 |
| `direct` | `FOPEN_DIRECT_IO` | 完全绕过 page cache：脱水天然安全、短读风险也消失；**没有 readahead、mmap 不可用** |

矩阵 M3-8 验证 direct 模式：`cat` 数据正确 + `mmap()` 直接失败（`FOPEN_DIRECT_IO` 生效）。

## 6. 可观测性

`qxync status` 的 `cache: CacheInfo`：

```
本地缓存  : pagecache（闲置 ≥ 600s 自动脱水），已缓存 12.3 MiB / 限额 2.0 GiB
            ｜水合文件 7 / 共 120｜累计脱水 42 次 / 释放 512 MiB
            上次扫描 12s 前｜被挡：dirty=2 pinned=1 open=1 mmap=0 在途=0
```

`qxync dehydrate` 输出「脱水 N 个 / 释放 X」+ 目标列表 + **跳过原因清单**。
xattr 仍然是真值：`user.qxync.state` 脱水后回 `placeholder`，`user.qxync.chunks` 回 `0/N`，
`user.qxync.vsize` 一直显示真实大小（`ls -l` 不受影响）。

## 9. 已知限制（留给后续）

* **mmap 判定**：主保护是 `open_count`（mmap 保留 `struct file`，`close(fd)` 后仍 >0，实测确认），
  辅以 `/proc/*/maps` 扫描（够用但慢，只覆盖本 PID 命名空间可见的进程；权限不足时是盲区）。
  报告 12 §8.1 的 `flock` 方案**挡不住 mmap**（Linux 语义），所以没采用。
* **`recent_secs=300` 的「刚访问过」保护**在「限额」驱动的清理里生效；定时清理用
  `idle_secs` 作为耐心值（不再叠加 300s），因为闲置阈值本身就是更强的保护。
* 脱水**不做** `fallocate(PUNCH_HOLE)`，直接删缓存文件（下次读重建稀疏文件）；
  少一次 syscall，效果等价。
* 空间节省按「挂载点」而不是「按目录开关」控制（Qsync 是 per-folder 的
  `QSYNC_FOLDERPAIR_USE_SPACE_SAVING`）；等 GUI/多目录模型进来再细化。
* `pin=pinned` 只做「不脱水」；**主动预水合**（打开前预取）还没做，放 M5/GUI。
* 脱水期间进程崩溃：状态在内存里，重启后节点表重建、缓存文件残留（下次读会命中它，
  或对账时被刷新）——不会丢远端数据；M5 的 SQLite 元数据会顺带把这块做严。
