# M36 —— 回放顺序显式化 + 「远端有没有副本」的持久化证据

> 状态：已实现 / 已验收（2026-10-25）
> 前置：[M20 离线缓冲区](M20-离线缓冲区.md)、[M21 离线可重启](M21-离线可重启.md)、
> [M34 清单叠加](../CHANGELOG.md)（同一次真机事故的两半）

## 0. 结论先行

M34/M35 修好了真机 `取证1` 事故的**两个直接触发点**，但留了两个「现在不疼、但排序与
记忆依赖隐式约定」的隐患：

1. `outbox_rewrite_prefix` 只改 path、不改 `seq` —— 回放顺序出现「子项排在新父目录
   mkdir 之前」是常态，靠 M35 的「等结构操作」兜底一轮轮试探；
2. 改名决策里的 `unwrap_or(!dirty)` —— 节点不在表里时用「脏不脏」猜「远端有没有」，
   两件事其实无关；重启后按持久化清单物化的本地新建文件（KIO 的 `.part`）会被当成
   远端已有，紧接着的改名发一条**永远不成立**的远端 rename。

M36 把两件事都变成显式的：

* 改写后的 outbox 行**按原相对顺序重排到队尾**（删/插同一事务），「祖先先落地」由
  seq 直接保证；
* `nodes` 表新增 `local_only` 列（schema v7）持久化「本地新建、远端还没有副本」，
  重启后按清单物化 / 改名决策都读它，`dirty` 不再参与。

## 1. 隐患一：回放顺序依赖隐式时序

真机形状（离线时同一条链）：

```text
seq1 mkdir /p/a         本地新建（先有 a）
seq2 mkdir /b           后来才建的新父目录
seq3 mkdir /p/a/sub
改名 /p/a → /b/a2       a 是本地新建 → 纯本地改名 + 回写 outbox
```

旧实现原地 `UPDATE` 保留 seq，得到回放顺序：

```text
/b/a2 (1) → /b (2) → /b/a2/sub (3)
```

子目录排在**新父目录的 mkdir 之前** → 每次回放要白烧 `stat`，直到兜底逻辑
（M35 的 `ReplayError::Pending`）一轮轮把顺序试出来。

修复：`Store::outbox_rewrite_prefix` 在一个事务里删除改写行、按原相对顺序重新插入
（`AUTOINCREMENT` 接在用过的最大 seq 之后）：

* 未被改写的行保持原 seq → 新父目录及其祖先的 `mkdir` 一定排在前面；
* 改写行之间的相对顺序不变 → 「父先于子」继承下来；
* `attempts` / `created_unix` / `is_dir` / `target` 原样保留。

排序依赖因此从「隐式约定」变成 seq 直接表达的不变量。回放的 `Pending` 兜底**保留**——
库里可能还有 M36 之前写下的老形状行（或手工/旧版本写入的行），回放不能假设行序。

## 2. 隐患二：`dirty` 猜不出「远端有没有」

旧代码：

```rust
let on_remote = ino.and_then(|i| g.nodes.get(&i))
    .map(|n| n.remote_known)
    .unwrap_or(!dirty);   // ★ 节点不在表里时用 dirty 猜
```

两个事实被混为一谈：

| 事实 | 谁回答 |
|---|---|
| 本地有没有还没上传的改动 | `Node::dirty` |
| NAS 上有没有这个名字 | `Node::remote_known` |

`Node::remote_known` **只在内存里**，而重启后节点表是空的：条目按持久化清单
（`listings` 表，M21）懒物化 —— 清单里混着 NAS 条目和 `create()` 时 `listing_upsert`
写进去的本地新建条目，**分不清来源**。于是重启后一个本地新建的 `.part`：

* 物化时被当成「远端已有」（`dirty=false`，旧代码的 guess 也是「远端有」）；
* 用户执行 KIO 的「写 `.part` → 改名成正式名」→ 在线回 `EIO` 改名失败；
  离线则 enqueue 一条永远不会成立的 rename（回放 `stat` 源/目标都查不到 → 放弃）。

修复分两层：

1. **持久化证据**：`nodes` 表新增 `local_only`（schema v7，v6 老库自动
   `ALTER TABLE` 补列）。语义只在**已知答案**的地方翻转：
   * 本地新建（`create` / 离线 `mkdir` / 硬链接复制）→ 置 1；
   * 上传成功（`clear_dirty` / `mark_remote_known`）→ 清 0；
   * 改名搬 path、删除删行 → 跟着 `nodes` 行走，不需要额外维护。
2. **消费点**：
   * `load_children` / `lookup_child` 按清单物化节点时，用
     `Store::node_local_only_under` / `node_is_local_only` 决定 `remote_known`；
   * 改名决策改成 `QxyncFs::on_remote_for`：节点在表里用 `remote_known`，不在表里
     查持久化证据，没证据才按「远端有」保守处理 —— 彻底删掉 `unwrap_or(!dirty)`；
   * 清单叠加（M34）补上第三路来源：跨重启后 `Inner::local_only`（inode 索引）是空的，
     没有 `nodes.local_only` 这一路，一次远端清单刷新就会把本地新建的文件从 `ls` 里
     抹掉（文件还在本地、上传作业还在队列里）。

### 2.1 独立复核抓到的四个必须补的洞（已修）

1. **叠加层拿到的是 `create()` 时的陈旧签名**（阻塞级）：`nodes` 行原来只在物化时
   写一次，`create()` 的 `size=0` 会一直留到上传成功。重启 + 远端清单刷新时，叠加层
   就会用 0 字节盖掉清单里正确的条目 → `read` 静默 EOF、追加写按陈旧 size
   `set_len(0)` 截断缓存（本地唯一副本）。修：`refresh_listing_entry`（release /
   setattr / 上传落地的定稿点）顺带把 `nodes` 行刷到最终签名。
2. **目录改名只搬目录自己一行 `nodes`**：`listings` 整棵子树搬、`nodes` 只搬一行，
   子项的 `local_only` 证据留在旧路径 → 新路径下缺陷复发、旧路径下清单叠加重影。
   修：新增 `Store::node_rename_subtree`（`length()` 按字符算，中文路径正确；目标冲突
   先删，唯一索引不撞），FUSE rename 与对账改名在 `is_dir` 时都走它。
3. **删除本地新建项不撤销 outbox**：离线建目录（`mkdir` 行）→ 回放前删除 → 回放 /
   清单叠加把它重新建出来/摆回 `ls`（删了又长回来、再建 EEXIST）；目录 `dirty` 恒为
   false，旧代码还会给远端发一条注定 404 的删除。修：删除时按同一套证据判 `on_remote`，
   `false` → 跳过远端删除 + `Store::outbox_forget_under` 撤销该子树的结构行；
   同一判据也覆盖文件（不再只看 `dirty`）。
4. **`outbox_rewrite_prefix` 的 DELETE 不看影响行数**：并发回放已 `outbox_done` 的行会
   被重新插回队尾（复活/重复回放）。修：`affected == 0` 就跳过插入。

顺带：`Inner::local_only`（会话内 inode 索引）现在在上传成功 / 删除时移除
（只增不减会在长会话里让每次清单安装空转遍历历史 inode）。

### 2.2 二轮复核的打磨（低概率但值得做）

* **大小写敏感的前缀匹配**：`nodes` / `outbox` 的子树 SQL 从 `LIKE` 改成
  `substr(path, 1, length(?1) + 1) = ?1 || '/'` —— SQLite 的 `LIKE` 默认大小写不敏感，
  `/home/a` 会误命中 `/home/A/...`（`node_forget_subtree` / `node_rename_subtree` 会
  误删/误搬兄弟目录的行；`outbox_forget_under` 会删掉不可恢复的回放意图）。
* **`node_rename_subtree` 的重叠防御**：目标是源的祖先 / 嵌套在源里时显式返回 0 ——
  旧 SQL 在「先删目标、再整体改前缀」的形状下会误删祖先行或撞唯一索引整事务回滚。
* **`refresh_listing_entry` 先写 `nodes` 行、且写前重读当前路径**：① 崩在两次写之间
  时不会留下「清单新、证据旧（0）」（正是阻塞问题的形态）；② 与并发 rename/unlink
  的毫秒窗口不再把行写回旧 path（幽灵行 / 同身份两行会让上传队列的身份反查变歧义）。
* **`link()` 的 O_TMPFILE 物化补记账**：这条路径手工搬节点、绕过
  `insert_node_with` 的尾部，之前不写 `Inner::local_only` 也不写 `nodes` 行 ——
  linkat→close 窗口内清单刷新会把新文件抹掉，崩溃则 M36 的改名误判对 WPS 保存路径复发。
* **`node_local_only_under` 去掉 `ORDER BY`**：`ORDER BY` 会让 SQLite 放弃局部索引
  `nodes_local_only`、退化成全索引扫（3 万行实测 1.125ms → 0.006ms，~190x；
  `find` 1 万目录从 ~11s 降到可忽略）。返回顺序不再保证，调用方本来就按 `HashSet` 用。

## 5. 兼容与迁移

* schema v6 → v7 只加一列：`ALTER TABLE nodes ADD COLUMN local_only INTEGER NOT NULL
  DEFAULT 0`。老行默认 0 = 「远端已有」，与旧行为一致（不会因为升级就把历史文件当成
  本地新建，进而误做纯本地改名）。
* 局部索引 `nodes_local_only ... WHERE local_only <> 0` 让 `readdir` 的证据查询
  不扫整张 `nodes` 表。
* 回放侧不改行为：M35 的 `Pending` 兜底保留，专门容忍 M36 之前写入的行序。

## 6. 已知限制

* `local_only` 只在「已经知道答案」的时刻翻转；如果上传成功回调本身丢了（进程在
  回调前崩溃），重启后会**多猜一次**「远端没有」—— 结果是改名只做本地 + 远端留下
  旧名字。下一次清单刷新会把远端那份当新增拿回来（冲突副本），不会丢内容，但会多
  一个重复文件。
* 跨重启的清单叠加用的是 `nodes` 行里的签名；该行现在会在 release / setattr（签名
  定稿）时刷新，所以「完全写完、正常关文件」的本地新建文件是对的。**写到一半就断电**
  的文件仍可能以旧签名（甚至 0）出现在叠加层里 —— 那本来就是未落盘的内容，语义与
  「崩溃时文件内容不完整」一致，不做额外猜测。
* 删除「本地新建项」时撤销 outbox 结构行是按 `path` 匹配的；如果删除的是**离线改名
  迁入**的路径（rename 行的 `target` 在删除子树里），那条 rename 行会留给回放处理
  （回放 `stat` 不到源/目标会按 Fatal 放弃并留 journal），不做猜测性改写。
* 回放与 FUSE 改写并发时（窗口很窄）：改写行被重插后，回放方按旧 seq 删行会 no-op，
  该行下一轮幂等重放；最坏是远端多一个旧路径，由下一轮对账收敛。不做全局串行化 ——
  那会把挂载点写路径卡在同步轮次上。
