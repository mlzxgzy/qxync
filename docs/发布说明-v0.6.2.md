# qxync v0.6.2 —— 开了两步验证（2SV）的账号终于能登录

**中文** · [English](#english)

[![License](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](https://github.com/mlzxgzy/qxync/blob/master/LICENSE-MIT)

**升级就是换二进制**：配置、任务、状态库、缓存布局都没有变；凭据文件只多一个**可选**字段
`otp_secret`，旧文件原样可读。没开两步验证的账号，登录请求与行为**一字不改**。

## 一句话

这一版补上 **QNAP 两步验证（2SV）里的 TOTP 支持**：以前 qxync 只发「账号 + 口令」，
账号一开 2SV 就永远登不上（CLI、daemon 自动重登、GUI 全部一样），而且报错还骗人说
「检查口令编码」。现在同一份 `authLogin.cgi` 表单多带一个 `security_code` 就能过第二步；
把 **TOTP 密钥**存进凭据后，daemon 每次重登录现算验证码，**长时间挂载不会因为验证码过期掉线**。

> 实现取舍（如实写）：协议上**一次请求**带 `security_code` 就够（真机实测），但 qxync 照
> QTS Web UI 的路径走**两步** —— 第一次请求与 v0.6.1 逐字节相同，只有 NAS 回
> `need_2sv=1` 时才发第二次带码请求。这样「未开 2SV 的账号行为一字不改」是**结构性**的，
> 而不是靠服务端忽略未知字段。

## 一、开了两步验证的账号以前根本登不上

**症状**：账号在 QTS 里打开「两步验证」后，`qxync login` 报
`authPassed=0 … need_2sv=1`，还跟着一句「检查口令编码：必须是 base64」——
口令明明是对的，用户只能反复怀疑自己。

**原因**：2SV 不是登录后的弹窗，`authLogin.cgi` 的**第一次请求**就决定给不给 sid。
qxync 以前只发 `user + pwd(base64)`，服务端回 `authPassed=0 / need_2sv=1`，
客户端手里没有任何续接凭据，`qsyncsrv.cgi` / `utilRequest.cgi` 全部拿不到 sid。
daemon 的自动重登（保活 / 轮询鉴权失败 / 挂载点热重试）同样卡死，挂载点从「能用」
变成持续 EIO。

**协议实测结论（2026-10-18，真机 QTS）**：在同一份表单里多带
**`security_code=<6 位 TOTP>`**，其余字段（`user` / `serviceKey=1` / `client_app=Qsync` /
`client_agent` / `remme` / `dont_verify_2sv_again=0` / `gen_client_id=1` / `pwd`）一个不动，
就能 `authPassed=1` + `authSid`（实测：直接放进第一次请求也行；qxync 的实现走
QTS Web UI 的两步流程，见上面的取舍）；sid 签发后与普通登录完全一样。
不带验证码时 `need_2_step_verification=1 / need_2sv=1`；**验证码错误时仍是
`authPassed=0 / need_2sv=1` 且没有 `errorValue`** —— 所以「没提供」和「提供了但被拒」
只能靠客户端自己是否带了字段来区分。

**现在**：

- **纯 Rust 内置 TOTP**（RFC 6238：SHA-1 / 30 秒 / 6 位；Base32 密钥；直接粘贴
  `otpauth://` URI 也认），**不新增任何依赖**；
- 凭据文件新增可选 `otp_secret`（与口令同文件、`0600`、**按连接**一份；旧文件零迁移）；
- **CLI**：全局 `--otp-secret <Base32>`（或 `QXNYC_OTP_SECRET`，随凭据保存）与
  `--otp-code <6位>`（或 `QXNYC_OTP_CODE`，一次性、不保存）；
- **daemon**：每次重登**现算**验证码（只存密钥、不缓存验证码），长时间挂载不会因为
  验证码过期掉线；`Request::Login` 支持一次性 `otp`；
- **GUI**：「设置 → 连接」新增「两步验证（可选）」输入框（填密钥=保存，填 6 位码=一次性），
  编辑连接时显示「已配置」，登录结果显示两步验证是否通过，**密钥不回显**；
- 登录失败提示不再一律甩「检查口令编码」：账号开了 2SV 时会明确告诉你怎么补
  （`--otp-code` / `--otp-secret` / GUI 位置），验证码被拒时会提示可能过期或本机时钟偏移。

## 二、升级注意

- 换掉 `qxync` / `qxyncd` / `qxync-gui` 三个二进制，并**重启 daemon**
  （`systemctl --user restart qxyncd`，或 `qxync daemon restart`；多连接的话每条连接各自重启）。
- **没开 2SV 的账号**：什么都不用做，行为与 v0.6.1 完全一致。
- **开了 2SV 的账号**：补一次密钥即可，之后 daemon 自动重登不需要人：

  ```bash
  qxync login --otp-secret '<TOTP密钥>'          # 保存密钥（推荐）
  qxync login --otp-code 123456                  # 或者只用于这一次
  ```

  地址 / 账号 / 口令沿用已保存的凭据，不需要重填。
- 凭据文件权限仍是 `0600`；密钥与口令**同级敏感**，明文存储（keyring 是后续工作）。
- 回退到 v0.6.1：2SV 账号重新登不上，其余功能不受影响；凭据文件不需要改回
  （旧版本忽略未知字段）。
- 服务端协议、`IPC_VERSION`、状态库 / 配置 / 任务格式均无变化。

## 四、已知边界（不粉饰）

- **只支持 TOTP**（authenticator app）。QNAP 还支持安全问题 / 邮件验证码 / 二维码批准 /
  设备批准，这些**一个都没实现**；遇到这类账号仍然登不上（错误提示只能说到「两步验证」
  这一层，不会假装能登）。
- **依赖本机时钟**：本机时间偏差过大时验证码会被拒；提示里会让人检查时钟（NTP）。
- **不是 OAuth / 云账号**：仍然只做「直连 NAS 的本地账号」。
- **没有恢复码、没有 keyring**：密钥丢了只能去 NAS 端重置 2SV；密钥与口令一样明文存
  `0600` 文件。
- 协议侧**没测**：`dont_verify_2sv_again=1`（记住设备）、**连续**输错验证码的账号锁定 / 限流
  （只测了单次错码：被拒、未锁定）。qxync 有意保持 `0`、每轮只尝试一次，失败把服务端原话交给用户。
- 本次没有在「大文件正在上传 + 会话跨 2SV 过期重登」的组合场景下做长时间浸泡测试。

## English

# qxync v0.6.2 — accounts with two-step verification (2SV) can finally log in

**Upgrading is just swapping binaries**: config, tasks, state store and cache layout are
unchanged; the credentials file only gains one **optional** field, `otp_secret`, and old files
stay readable. For accounts without 2SV, the login request and behaviour are **byte-for-byte
unchanged**.

## The short version

This release adds **TOTP support for QNAP two-step verification (2SV)**. qxync used to send only
"user + password", so as soon as an account enabled 2SV it could never log in (CLI, the daemon's
automatic re-login and the GUI alike) — and the error message misleadingly told you to
"check the password encoding". Now one extra field, `security_code`, on the same
`authLogin.cgi` form gets past the second step; once the **TOTP secret** is stored in
the credentials file, the daemon computes a fresh code on **every** re-login, so long-running
mounts no longer drop because a code expired.

> Implementation trade-off (stated plainly): on the wire **one** request carrying `security_code`
> is enough (measured on a real NAS), but qxync follows the QTS Web UI path and uses **two** —
> the first request is byte-for-byte identical to v0.6.1, and the second one (with the code) is
> only sent when the NAS answers `need_2sv=1`. That makes "accounts without 2SV are unchanged"
> a **structural** property rather than an assumption that the server ignores unknown fields.

## 1. Accounts with 2SV could not log in at all

**Symptom**: after enabling two-step verification in QTS, `qxync login` reports
`authPassed=0 … need_2sv=1` followed by "check the password encoding: it must be base64" —
even though the password is correct. All you can do is doubt yourself.

**Cause**: 2SV is not a post-login dialog: the **first** `authLogin.cgi` request decides whether
a sid is issued. qxync only sent `user + pwd(base64)`, so the server answered
`authPassed=0 / need_2sv=1` and the client had no continuation token of any kind;
`qsyncsrv.cgi` / `utilRequest.cgi` never got a sid. The daemon's automatic re-login (keepalive /
polling auth failure / mount hot-retry) hit the same wall, so a working mount degraded into
persistent EIO.

**Protocol conclusion (measured on a real QTS box, 2026-10-18)**: add
**`security_code=<6-digit TOTP>`** to the same form while keeping every other field
(`user` / `serviceKey=1` / `client_app=Qsync` / `client_agent` / `remme` /
`dont_verify_2sv_again=0` / `gen_client_id=1` / `pwd`) unchanged, and the response is
`authPassed=1` plus `authSid` (it also works when placed in the very first request; qxync
implements the Web UI's two-step flow, see the trade-off above); from there the session is
identical to a normal login. Without a code the response is `need_2_step_verification=1 /
need_2sv=1`; with a **wrong** code it is still `authPassed=0 / need_2sv=1` **and there is no
`errorValue`** — so "not provided" versus "provided but rejected" can only be distinguished by
whether the client sent the field at all.

**Now**:

- **A pure-Rust built-in TOTP** (RFC 6238: SHA-1 / 30 s / 6 digits; Base32 secrets; pasting an
  `otpauth://` URI also works), with **no new dependencies**;
- the credentials file gains an optional `otp_secret` (same file as the password, `0600`,
  **per connection**; no migration for old files);
- **CLI**: global `--otp-secret <Base32>` (or `QXNYC_OTP_SECRET`, saved with the credentials)
  and `--otp-code <6 digits>` (or `QXNYC_OTP_CODE`, one-shot, never saved);
- **daemon**: a fresh code is computed on **every** re-login (only the secret is stored, codes
  are never cached), so long-running mounts do not drop when a code expires; `Request::Login`
  accepts a one-shot `otp`;
- **GUI**: Settings → Connections gains a "two-step verification (optional)" field (a secret is
  saved, a 6-digit code is one-shot), editing a connection shows "configured", the login result
  shows whether 2SV passed, and the secret is **never echoed back**;
- login failures no longer always blame the password encoding: for a 2SV account the message now
  says exactly how to supply the second factor (`--otp-code` / `--otp-secret` / where in the
  GUI), and a rejected code mentions expiry and local clock skew.

## 2. Upgrade notes

- Replace `qxync` / `qxyncd` / `qxync-gui` and **restart the daemon**
  (`systemctl --user restart qxyncd`, or `qxync daemon restart`; with several connections,
  restart each of them).
- **Accounts without 2SV**: nothing to do; behaviour is identical to v0.6.1.
- **Accounts with 2SV**: store the secret once and the daemon's re-logins need no human:

  ```bash
  qxync login --otp-secret '<TOTP secret>'       # store the secret (recommended)
  qxync login --otp-code 123456                  # or use it for this login only
  ```

  Host / account / password come from the credentials already on disk; you do not re-enter them.
- The credentials file stays `0600`; the secret is **as sensitive as the password** and is
  stored in plaintext (keyring support is future work).
- Rolling back to v0.6.1: 2SV accounts stop logging in again, everything else is unaffected, and
  the credentials file needs no changes (old versions ignore unknown fields).
- Wire protocol, `IPC_VERSION`, the state store, config and task formats are all unchanged.

## 4. Known limits (no sugar-coating)

- **TOTP only** (authenticator apps). QNAP also supports security questions / email codes /
  QR-code approval / device approval — **none** of these are implemented; such accounts still
  cannot log in (the error can only say "two-step verification", it never pretends to work).
- **Depends on the local clock**: a badly skewed clock makes the code invalid; the message tells
  you to check it (NTP).
- **Not OAuth / not a cloud account**: still "a local account talking straight to the NAS".
- **No recovery codes, no keyring**: if you lose the secret, reset 2SV on the NAS; the secret is
  plaintext in a `0600` file, same as the password.
- **Not measured on the protocol side**: `dont_verify_2sv_again=1` ("remember this device") and
  account lockout / rate limiting after **repeated** wrong codes (only a single wrong code was
  tested: rejected, no lockout). qxync deliberately keeps `0` and tries once per round, handing the
  server's own words back to you.
- No long soak test of "large upload in flight + session expiring across a 2SV re-login".
