# qxync v0.5.0 —— 同步不再牵连挂载，远端改名不再多出冲突副本

**中文** · [English](#english)

[![License](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](https://github.com/mlzxgzy/qxync/blob/master/LICENSE-MIT)

**这一版没有破坏性变更**：配置、任务文件、缓存目录布局、命令行参数都不需要改。
升级方式就是换二进制 + 重启 daemon。

唯一的**行为变化**需要留意：想「重载同步但挂载点一秒不中断」，请用
`systemctl --user reload qxyncd`（或 `qxync daemon reload`），而不是 `restart`。原因见下。

## 一句话

以前 `systemctl restart qxyncd` 会把挂载点全部卸掉，用户要等几秒才能接着用；
而 NAS 上给文件改个名，本地会凭空多出一份「冲突副本」—— 明明只是改了个名字。
这一版把这两件事都从根上解决了。

## 最重要的行为变化：restart 换成 reload

**`restart` 仍然会短暂断开挂载**（由自动重挂恢复，通常 3 秒内）；
**`reload` 才是零中断**。两者语义不同，别混用。

为什么不能两全：systemd 的 `restart` 流程是「stop → **等旧进程退出** → start」。
一个「永不退出、死守挂载点」的守护进程会把这个流程卡死，
最终被 `TimeoutStopSec` 之后的 SIGKILL 杀掉 —— 挂载照样断。
这是 systemd 的语义，客户端绕不开。能做的是把「同步换代」与「进程退出」分开：
SIGHUP 只让同步引擎换代（发代次令牌，旧任务在下一个检查点自己退场），
FUSE 会话完全不动。

```bash
systemctl --user reload qxyncd   # 重载同步，挂载点一秒不中断 ★ 推荐
qxync daemon reload              # 同上，不经 systemd
systemctl --user restart qxyncd  # 仍会短暂断开（自动重挂恢复）
qxync daemon stop                # 真正卸载全部挂载并退出
```

停止守护进程请用 `qxync daemon stop`（走 IPC，会真正卸载挂载点）。

## 远端改名不再生成冲突副本

服务端 `DirEntry` 里没有 id 字段，所以 qxync 只能**本地自建**一个 16 字节身份
（由 `mtime` + `size` 推出；**刻意不含文件名** —— 含了改名后身份就变了，认不出改名）。
新增 `nodes` 表持久化它（schema v3 → v4，老库自动迁移）。

有了它，两件事成立了：

- **对账认出「远端删除 + 远端新增」其实是改名** → 本地节点跟着改名，baseline 迁移，
  **不生成冲突副本**。
- **上传队列排队期间远端改了名**，作业落地到新名字，不再产生幽灵文件。

配对是**保守**的：身份未知、类型不符、一个身份对应多个路径（有歧义）一律不配，
退回原有的增删判定。**宁可多冲突，绝不错配或丢数据。**

## 僵尸挂载自愈

真崩溃或 OOM 之后挂载点会留在 `/proc/mounts` 里但 `ENOTCONN`，
`cd` 进去报「Transport endpoint is not connected」。
现在 daemon 启动早期会对**自己记录过的**挂载点写探针试活，确认已死才懒卸载。

安全边界：只清 `mounts.json` 里记过的路径（**不扫全盘**）、校验 subtype 是 `qxync`
才动手、用 `-uz` 而非 `-u`、失败只 WARN **不阻塞启动**。

## 顺带修掉的

- **`rename_remote` 漏迁移身份索引**（本版内部校验时抓到）：远端改名迁移了本地节点，
  却没搬 `nodes` 表那一行 —— 同一身份出现两行 → 按身份反查恒判「有歧义」→
  **上传队列的按身份重定向永久失效**。已修，并补了能抓住它的回归测试
  （用变异测试确认：撤掉修复，测试立刻报红）。
- **`progress_percent` 整数溢出**：`done > total` 时会输出 `18446744073709551615`。
- `Store` 的 SQLite 连接改为 `Arc` —— FUSE 侧与同步引擎现在**共用同一个连接**，
  而不是各开一个抢写锁。

## 新命令

```bash
qxync file-states <dir>   # 逐文件看同步状态与传输进度（也有 --json）
```

`in_sync` 是**派生值**（汇总 `dirty` / 待传作业 / 待裁决冲突三个信息源），不新建状态表。

## T4 上传分片续传：验证后取消

原以为「服务端不支持分片」，实测这个前提是**错的** —— `qsyncsrv.cgi` 里分片上传
实现得很完整（5 个 func、参数表齐全）。真正的障碍是**分片通道只服务 Qbox 空间**
（`upload_root_dir` 认 `/remote:` 前缀），而 `upload.php` 的 `dest_path` 用的是
普通家目录路径 —— **两套路径空间不通**，我们够不到。探针留在
`xtask/probe/upload_chunk_probe.py`。

顺带纠正一个隐蔽的坑：该 CGI 的响应是**两段 JSON**，第一段 `"status": 0` 是框架头，
只抓第一个会误判成「所有 func 都无反应」。

## 验证状态（请注意）

- `cargo check --workspace --all-targets`：零 error 零 warning。
- `cargo test --workspace --lib --bins --tests`：**290 passed / 0 failed**
  （基线 265 + 本批新增 25）。被 `#[ignore]` 的 19 条全在 `qxync-proto-test/`，
  需要真实 NAS —— 本批**没有新增任何 ignore**。
- ⚠️ **开发环境无 `/dev/fuse`**，所以凡是「真的挂上去再操作」的验收项
  （reload 期间 `ls` 是否正常、`kill -9` 后能否自愈、SIGHUP 期间 FUSE 会话是否真没断）
  **只有逻辑层单测覆盖，没有真机验证**。建议本机实测一遍上面那四条命令。

## English

# qxync v0.5.0 — Sync no longer takes the mount down, and remote renames no longer sprout conflict copies

**中文** · [English](#english)

No breaking changes: configuration, task files, cache layout and CLI arguments are all
unchanged. Upgrading means replacing the binaries and restarting the daemon.

The one **behavioural** change worth noting: to "reload sync without interrupting the mount
for a single second", use `systemctl --user reload qxyncd` (or `qxync daemon reload`)
rather than `restart`. See below for why.

## TL;DR

`systemctl restart qxyncd` used to unmount everything, costing you a few seconds; and
renaming a file on the NAS would sprout a phantom "conflict copy" locally — even though
all that happened was a rename. This release fixes both at the root.

## The behaviour change that matters: reload, not restart

**`restart` still interrupts the mount briefly** (recovered by automatic remount, typically
within 3 seconds); **`reload` is the zero-interruption path**. They are not interchangeable.

Why not both: systemd's `restart` is "stop → **wait for the old process to exit** → start".
A guardian process that never exits (because it is holding the mount point) wedges that flow
and eventually gets SIGKILLed after `TimeoutStopSec` — so the mount dies anyway. That is
systemd's semantics, not something a client can work around. What we *can* do is decouple
"sync generation change" from "process exit": SIGHUP only rotates the sync engine (handing
out a generation token; old tasks retire at their next checkpoint) and leaves the FUSE
session completely alone.

```bash
systemctl --user reload qxyncd   # reload sync, zero mount interruption ★ recommended
qxync daemon reload              # same thing, without systemd
systemctl --user restart qxyncd  # still interrupts briefly (auto-remount recovers)
qxync daemon stop                # really unmount everything and exit
```

To stop the guardian process use `qxync daemon stop` (goes through IPC, really unmounts).

## Remote renames no longer generate conflict copies

The server's `DirEntry` has no id field, so qxync has to build a 16-byte identity locally
(derived from `mtime` + `size`; it **deliberately excludes the filename** — including it
would change identity on rename, defeating the purpose). A new `nodes` table persists it
(schema v3 → v4, old databases migrate automatically).

With that in place, two things become true:

- **Reconciliation recognises that a "remote delete + remote add" is really a rename** → the
  local node is renamed, the baseline moves with it, and **no conflict copy is generated**.
- **A queued upload whose file is renamed remotely** lands under the new name instead of
  creating a ghost file.

Pairing is **conservative**: unknown identity, mismatched type, or one identity mapping to
several paths (ambiguous) are all refused, falling back to the original add/delete decision.
**Better one conflict too many than a mis-pairing or lost data.**

## Zombie mounts self-heal

After a real crash or an OOM kill, a mount point stays in `/proc/mounts` but returns
`ENOTCONN`, and `cd`ing in says "Transport endpoint is not connected". The daemon now probes
the mount points **it recorded** early at startup and lazy-unmounts only the confirmed-dead
ones. Safety boundaries: only paths from `mounts.json` (never a full-disk scan), subtype must
be `qxync`, `-uz` rather than `-u`, and a failure only warns — it never blocks startup.

## Also fixed

- **`rename_remote` failed to migrate the identity index** (caught during this release's own
  review): the remote-rename path moved the local node but left the row in the `nodes` table
  behind, so one identity appeared twice → lookups by identity permanently reported
  "ambiguous" → **the upload queue's identity-based retargeting was dead for good**. Fixed,
  with a regression test that actually catches it (verified by mutation testing: remove the
  fix and the test fails).
- **`progress_percent` integer overflow**: with `done > total` it printed
  `18446744073709551615`.
- `Store`'s SQLite connection is now an `Arc` — the FUSE side and the sync engine **share one
  connection** instead of two fighting over the write lock.

## New command

```bash
qxync file-states <dir>   # per-file sync status and transfer progress (also has --json)
```

`in_sync` is a **derived value** (aggregating `dirty` / queued uploads / pending conflict
decisions) — no new state table.

## T4 chunked/resumable upload: cancelled after verification

The original premise was wrong: `qsyncsrv.cgi` implements chunked upload thoroughly (5 funcs,
complete parameter tables). The real obstacle is that **the chunked channel only serves Qbox
space** (`upload_root_dir` recognises the `/remote:` prefix) while `upload.php`'s `dest_path`
uses ordinary home-directory paths — **the two path spaces are disjoint**, so we cannot reach
it. The probe is kept at `xtask/probe/upload_chunk_probe.py`.

It also corrects a subtle trap: that CGI returns **two JSON documents**, and the leading
`"status": 0` is a framework header — scraping only the first makes every func look like it
did nothing.

## Verification status (please note)

- `cargo check --workspace --all-targets`: zero errors, zero warnings.
- `cargo test --workspace --lib --bins --tests`: **290 passed / 0 failed** (baseline 265 + 25
  new in this batch). All 19 `#[ignore]`d tests live in `qxync-proto-test/` and need a real
  NAS; this batch added **no new ignores**.
- ⚠️ **The development environment has no `/dev/fuse`**, so every acceptance item that
  requires actually mounting something (`ls` during reload, self-healing after `kill -9`,
  whether the FUSE session truly survives SIGHUP) is covered **by logic-level unit tests
  only — no real-machine verification**. We recommend running the four commands above on a
  real machine.
