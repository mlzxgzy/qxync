# v0.7.10 —— 回放顺序与远端副本证据

> 发布日期：2026-10-25
> 上一版：[v0.7.9](发布说明-v0.7.9.md)（重启后缓存状态恢复 + 校验和修复 + 右下角下载进度）
>
> 这一版修的是同一次真机事故（`取证1`）留下的三条老账：
>
> 1. **离线新建的目录/文件，在回放落地前从 Dolphin 里凭空消失，再建同名又报「已存在」**（M34）；
> 2. **回放把「路径不存在」当成会话失效，反复真登录（6 分钟 95 次），20 次后把离线操作
>    静默删掉**（M35）；
> 3. 前两条修好后仍留两个「依赖隐式约定」的隐患：回放顺序、以及「NAS 上到底有没有
>    这个名字」用 `dirty` 猜 —— 这次一并改成显式保证（M36）。

## 一句话

```text
升级 + 重启 daemon 后：
  → 离线建的目录/文件在同步落地前也一直看得见（ls 不再被远端列举整份覆盖）
  → 断网期间的离线操作不会再被「假重登」耗尽重试次数后丢掉
  → 恢复联网后，本地新建 → 改名/上传按正确顺序回放，不再发永远不成立的远端 rename
  → 重启后仍然看得见「本地新建、还没同步」的条目（证据落库，不靠内存）
```

## 一、离线新建的目录/文件不再从 `ls` 里消失（M34）

### 之前的现象（真机 2026-10-25）

离线时在挂载点里新建 `取证1` 目录 → 恢复联网后，Dolphin 里这个目录**凭空消失**
（`ls` 看不到），但再点「新建文件夹 → 取证1」却弹「名为"取证1"的目录已经存在」
—— 既看不见、又建不了。

### 根因

目录列表快照被「NAS 列举结果」**整份覆盖**：`取证1` 还在离线回放队列里，NAS 那次
列举当然没有它，快照就被写成空。但 `nodes` 表里它还在 —— 内核 `lookup` 命中，
`mkdir` 直接拿到 `EEXIST`（FUSE 的 `mkdir` 回调根本没进去）。

### 现在的行为

所有「快照 = 远端清单」的写入点（daemon 轮询推送 / TTL 后台补拉 / 冷路径列举 /
挂载预热）都先合并：

```text
远端全集 ∪ 本地未同步新建 − 本地待删（含待改名的旧名）
```

并且**写穿持久化的就是合并后的视图**（离线重启同样可见）。本地新建的**文件**也
覆盖（`create` 时父目录还没有快照的场景）；远端真删除仍然生效。

## 二、离线回放不再「假重登」、不再丢离线操作（M35）

### 之前的现象

同一事故里：子目录的 `stat` 因为父目录还没回放而返回 `status=5`（路径不存在），
旧分类器把它当成**会话失效** → 每 3 秒真登录一次（6 分钟内 95 次「登录成功」，会撞上
NAS 的失败登录封锁），并在 20 次重试后把 5 条离线操作**整行删掉**（其中一条改名丢了，
留下重复副本）。

### 根因

`status=5` 只说明「这个路径此刻不存在」，和「会话无效」是两件事。父目录的 `mkdir`
往往就排在后面几条，同一轮就能建出来。

### 现在的行为

- 失败路径的祖先里有还没落地的 `mkdir`/`rename` → 判为「等待自己的结构操作」：
  **不计数重登、不中断本轮**，下一轮（或同轮后续行）自然解开；
- `setmtime` 的目标还在上传队列里时直接跳过（上传落地会自己对齐 mtime）—— 这是旧
  实现的死锁：上传队列在 outbox 清空前被冻结，`set_mtime` 又只在文件已上传后才可能
  成功，只能靠「20 次假重登后放弃删行」解开。

## 三、回放顺序与「远端有没有副本」改成显式证据（M36）

### 隐患一：回放顺序依赖隐式时序

`outbox_rewrite_prefix` 旧实现只改 `path`、保留 `seq`，而改写会把行指向**新的父目录**
—— 新父目录的 `mkdir` 行可能排在原 seq 之后（真机形状：先建 `/p/a`、后建 `/b`、
再建 `/p/a/sub`，最后把本地新建的 `/p/a` 改名到 `/b/a2`），回放顺序就变成「子项排在
新父目录前面」，只能靠「等结构操作」兜底一轮轮烧 `stat`。

现在改写行在**同一个事务**里删除、按原相对顺序重插到队尾（`attempts` / `created_unix` /
`target` 原样保留），未被改写的行 seq 不变 →「祖先先落地」由 seq 直接保证。回放侧
的「等待」兜底保留（旧版本写下的行序仍要能解开）。

### 隐患二：`dirty` 猜不出「远端有没有」

改名决策里的 `unwrap_or(!dirty)` 把「本地有没有未上传改动」当成了「NAS 上有没有这个
名字」—— 两者是不同事实。重启后节点按持久化清单懒物化，而清单分不清「NAS 条目」与
`create()` 写进去的本地新建条目：一个本地新建、还没上传的 KIO `.part` 会被当成远端
已有，紧接着的改名（`.part` → 正式名）发一条**永远不成立**的远端 rename（在线 `EIO`、
离线重试到放弃）。

现在 `nodes` 表新增 `local_only` 列（schema v7，v6 老库自动 `ALTER` 补列，老行默认
「远端已有」= 旧行为不变）：本地新建置 1、上传成功清 0、改名/删除跟着行走；按清单
物化节点与改名/删除决策都读它，`dirty` 不再参与。顺带补上 M34 清单叠加的跨重启来源
—— 一次远端清单刷新不再把本地新建的文件从 `ls` 里抹掉。

### 复核抓到并补上的洞

- 重启后清单叠加原来会拿 `create()` 时的 `size=0` 节点行盖掉正确条目（`read` 静默
  EOF、追加写按陈旧 size 截断缓存）→ release / setattr 定稿时把节点行刷到最终签名；
- 目录改名只搬目录自己一行节点 → 新增子树搬迁，子项证据跟着走；
- 删除本地新建项时撤销未回放的结构操作（删掉的目录不再「复活」），也不给远端发
  注定 404 的删除；
- 树前缀匹配改成大小写敏感（`/home/a` 不再误伤 `/home/A/...`），局部索引真正生效。

## 升级

```bash
# 1. 装新二进制（替换 /usr/bin 下的三个）
sudo install -Dm755 target/release/qxync target/release/qxyncd /usr/bin/
#    若有 GUI：dist/ 或 cargo build --release -p qxync-gui 的产物按原有方式安装

# 2. 重启 daemon（会卸载并重挂 FUSE 挂载点，请先存盘）
qxync daemon stop && qxync daemon start
qxync status
```

- 数据库 schema 从 v6 升到 v7：首次启动自动 `ALTER TABLE` 加一列，**不动任何已有
  数据、不重扫缓存**，升级即完成；
- 升级前已经「看不见」的目录/文件，重启后会在下次列表刷新时自动回来；
- 事故期间被丢掉的离线改名可能留下重复副本（内容相同、只是名字不同），确认内容后
  手工删多余的那份即可，不影响后续同步。

## 已知限制（如实记）

* 如果**上传成功回调本身丢了**（进程在回调前崩溃），重启后会多猜一次「远端没有」：
  改名只做本地、远端留下旧名字，下次清单刷新会把远端那份当新增拿回来（多一个冲突
  副本，不丢内容）。
* 跨重启的清单叠加用的是节点行里的签名，该行会在 release / setattr（签名定稿）时刷新；
  **写到一半就断电**的文件仍可能以旧签名（甚至 0）出现在叠加层里 —— 语义与「崩溃时
  文件内容不完整」一致，不做额外猜测。
* 删除「本地新建项」时撤销回放结构行是按路径匹配的；如果删除的是离线改名迁入的路径
  （`rename` 行的 `target` 落在被删子树里），那条 rename 行留给回放按 Fatal 放弃并留
  journal，不做猜测性改写。
* 回放与 FUSE 改写并发时（窗口很窄）：改写行被重插后，回放方按旧 seq 删行会 no-op，
  该行下一轮幂等重放；最坏是远端多一个旧路径，由下一轮对账收敛。
* `cargo clippy` 在发版环境未安装，未运行。
