# v0.7.12 —— 「网络断开」误判修复与日志轮转

> 发布日期：2026-10-27
> 上一版：[v0.7.11](发布说明-v0.7.11.md)（休眠唤醒后守护进程不再自杀）
>
> 这一版两件事：
>
> 1. **界面一直显示「网络断开」、点「立即同步」没反应** —— 其实 NAS 与网络都正常，
>    是上传队列里一条指向已消失临时文件的作业被**误判成断网**（M38）；
> 2. **日志单文件长到 5.17 GB** —— 旧实现只按天切段、从不删除，撞上一次
>    `accept` 失败紧循环就写出 4.9 GiB（M39）。

## 一句话

```text
升级 + 重启 daemon 后：
  → 本地内容源已不存在的上传作业会立刻放弃并留痕，不再把本地 ENOENT 判成断网：
    状态栏不会再莫名其妙卡「网络断开」，点「立即同步」立刻有可见结果
  → 日志按天 + 按大小（默认 32 MiB）切段，旧文件按 14 天 / 总量 256 MiB 自动删除；
    daemon 每小时独立清一次，qxync log 可查、可手动清、改策略不用重启
  → accept 失败后 100ms 退避，不再 2 分半写出 674 MB（止血；fd 泄漏根因另案待查）
```

## 一、现象一：一直「网络断开」，点「立即同步」没反应（M38）

### 现场（真机 2026-10-26）

```text
界面   : 网络断开（NAS 本身在线，其它设备访问正常）
操作   : 点「立即同步」→ 没有任何变化
日志   : 同步 --once: events=0 ...        ← 同步其实执行了，远端确实没变化
队列   : 待上传 1
         远端 /home/.Qsync/2026/28-BM委赛/数据库备份/数据库分析报告.md
         本地 .../cache/qnap.kdajv.com/098f557762fcabbc________.md.tmp  ← 文件不存在
         attempts: 0
```

### 根因：一条「僵尸作业」把连通性状态机骗成离线

```text
10-26 20:18:26  编辑器（WPS）原子保存：
                  先写 数据库分析报告.md.tmp → 硬链接成 数据库分析报告.md → 删掉临时目录
                上传队列里留下一条「内容源指向已删除 .tmp」的作业
旧实现：qxync-client 把本地 stat/open 失败包成 Error::Transport
        → 上传队列按「网络不可用」处理：永不计失败、永不放弃
        → 每轮重试还把连通性标成「离线」→ 界面一直「网络断开」
        → 「立即同步」跑完后立刻又被这个作业翻回离线，看起来毫无反应
```

还有一条叠加伤害：那个临时文件作业按「按身份改名」落到目标路径时，会把目标文件
**内容完好、本来能传**的作业行顶掉（按路径覆盖）—— 所以这个文件的内容一直没上 NAS。

### 修复

| 层 | 改动 |
|---|---|
| `qxync-client` | 本地 `stat` / `open` 失败改报 `Error::Io`（**不是** `Error::Transport`）；只有真的网络错误才判离线 |
| `qxync-fuse` 上传 worker | 内容源不存在 → **立刻放弃并删掉队列行**（`error` 日志留痕），不再无限重试、不再污染连通性 |
| `qxync-fuse` 改名 retarget | 按身份改名前先确认内容源还在，避免顶掉新名字上能传的作业 |

回归测试 3 条：`upload_missing_local_is_io_not_transport`、
`missing_content_source_is_given_up_not_offline`、
`identity_retarget_skips_dead_content_source`。

### 现场恢复（本版发布时已做）

用目标文件的缓存副本（35 043 字节，内容校验一致）恢复了丢失的暂存文件，队列随即上传成功：

```text
已上传 /home/.Qsync/2026/28-BM委赛/数据库备份/数据库分析报告.md (35043 字节)
上传队列: 待上传 0｜完成 1（35043 字节）｜连通性 在线
远端    : exist=true  35043 B  2026/10/26 20:18:26   ← 内容没丢
```

代码修复负责「以后不再发生」；这次丢失的内容已按上面方式补传。

## 二、现象二：日志单文件 5.17 GB（M39）

### 现场

```text
~/.local/state/qxync/log/qxyncd.log.2026-10-23
  5 174 393 555 字节 / 52 266 068 行（4.9 GiB），目录合计 5.6 GiB
其中 52 265 459 行（99.998%）是同一条：
  WARN qxyncd::daemon: accept 失败: Too many open files (os error 24)
```

不是「每轮轮询打一行」，是 `accept` 失败后的**紧循环**：2026-10-27 08:34–08:36 同形状
又复发一次，**2 分半写出 674 MB**。

### 根因（两层）

1. 旧实现只有 `tracing_appender::rolling::daily`：**同一天内没有大小上限**（只在跨天切段）、
   **旧文件从不删除**（只增不减）；
2. `accept` 失败的错误分支直接落回 `select!`，下一次 `accept` 立刻又失败 —— 纯烧 CPU + 刷日志。

### 修复

| 层 | 内容 |
|---|---|
| 写路径 | 自写 `RotatingWriter`（`qxync-core/src/logcfg.rs`）：按天 **且按大小** 切段 —— 写满 `log_max_file_mb`（默认 **32 MiB**）当场改名成 `<前缀>.log.<UTC 日期>.<n>` 再开新段；命名与旧 `daily` 逐字一致（**UTC 日期**，本地 08:00 换段）；**启动时发现当天段已超限直接切**（正是「昨天写爆、今天重启」的现场） |
| 清理 | 按 **mtime** 从最旧删起，直到满足 `log_keep_days`（默认 **14 天**）与 `log_max_total_mb`（默认 **256 MiB**）；不解析文件名，外部拷进来的旧文件也能正确处理 |
| 保护活动文件 | 写入器持 `flock(LOCK_EX)`，清理前试加锁，加不上就跳过并记入 `PruneReport.in_use`（CLI / GUI 会显示「跳过（正被写入）」而不是静默不动）—— daemon 与 GUI 是两个进程，按 mtime 猜会误删；反过来 40 天前已退出的孤儿日志现在会被正常删掉 |
| 定时 | daemon 每 **3600s** 独立清理一次（`QXNYC_LOG_PRUNE_SECS` 可调，最小 5）：**不写日志也会按时删**，空转待命同样生效；`settings_save` 热应用策略并立即清一次 |
| 可见 / 可操作 | IPC `Request::Logs { prune }` → `LogsData`；CLI `qxync log` / `--prune` / `--json`；GUI **设置 →「日志」**（占用、三项策略、保存、立即清理、文件表） |
| 伴生防御 | `accept` 失败后 `sleep(100ms)` 再试（三处分支统一，文案 `accept 失败（100ms 后重试）`），一天上限约 86 万行，再被大小/总量上限兜住 |

三个设置字段（`settings.json`，改完不用重启）：

```text
log_max_file_mb    默认 32    0 = 不切段
log_keep_days      默认 14    0 = 不按天删
log_max_total_mb   默认 256   0 = 不限总量
```

## 四、升级

```bash
# 1) 换二进制（qxync / qxyncd / qxync-gui 都要换：GUI 的「设置 → 日志」在新版里）
sudo install -m755 target/release/qxync target/release/qxyncd target/release/qxync-gui /usr/bin/

# 2) 重启 daemon（正在跑的进程不会自己变）
systemctl --user restart qxyncd
# 没有 systemd 时：qxync daemon stop && qxync daemon start

# 3) 确认日志策略生效（新 daemon 启动时会先按策略清一次旧日志）
qxync log
qxync log --prune        # 想立刻清就手动清一次
```

升级窗口内（旧二进制还在跑）它**不持锁**：此时 `qxync log --prune` 可能删掉旧 daemon
正在写的文件（只丢诊断信息，不丢同步数据）。所以升级后尽快重启 daemon 再手动清。

## 已知限制（如实记）

* **fd 泄漏根因没定位**：那 5.17 GB 里 99.998% 是 `accept 失败: Too many open files`。
  本版只做「100ms 退避 + 单文件/总量上限 + 自动清理」的止血，**没有修「fd 为什么被耗光」**；
  已单独记一笔待查（复发时日志不会再无限增长，但连接仍可能抖动）。
* 二进制安装与 daemon 重启由用户在本机执行；本版发布流程只做了本地构建 + 清理真机日志。
* 总量上限不是硬上限：正在写的活动文件受保护优先，极端情况下目录会短暂超过 256 MiB。
* `flock` 是启发式：升级窗口（旧二进制不持锁）如上面「升级」一节所述需要尽快重启。
* GUI「设置 → 日志」有 `ui_spec` 断言 + DOM shim 冒烟 + 隔离 XDG 实跑，但**没有真实桌面
  环境下的活体点击与截图**（发版环境无显示环境）。
* `cargo clippy` 在发版环境未安装，未运行。
* 另外现场日志里可见「对账时间预算 15s 用完，本轮列了 152/5418 个目录，下轮从游标续扫」——
  这是既有的轮转扫描行为（M2c），不是本版引入，也不是本版修复范围。
