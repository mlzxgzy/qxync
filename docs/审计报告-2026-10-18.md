# qxync 全项目审计报告（2026-10-18）

> **触发**：用户反馈「使用起来还是不太舒服」。
> **范围**：全部 7 个 crate + GUI 前端（静态三件套）+ CLI/IPC + 文档；含上一轮未提交的
> 「冲突待裁决队列」WIP（`decisions.rs` / diff / forget / clear / 巡检）。
> **方法**：① 对**正在运行的 daemon v0.5.1** 做只读取证（日志 / `qxync status` /
> `qxync journal` / 只读拷贝的 `sync.db` / 用 CLI 递归比对远端真实树）；② 静态审计 +
> 单测；③ 多个并行 agent 分区修复 + 一轮独立 red-team 复核（含变异测试）；④ Lead 统一
> 稳定版 rustfmt + 全仓测试收口。
> **结论**：修掉 **2 个数据安全级、1 个用户裁决意图丢失级、1 个「危险的假象」级** 的
> bug，以及 30+ 个真实功能性/可靠性/UX 问题；**已随 v0.6.0 提交并发布**，详见
> [`CHANGELOG.md`](../CHANGELOG.md) 的 `[0.6.0] - 2026-10-18` 与
> [`docs/验收记录.md`](验收记录.md) 的 2026-10-18 节。

## 0. TL;DR ——「不舒服」到底来自哪

「不舒服」不是单一 bug，而是**四类问题叠加**，而且都在真机上有直接证据：

| 用户感知 | 实际发生了什么 | 根因 |
|---|---|---|
| 首页/诊断一直挂红：**「有删除被熔断挡住」**，放行后也不消失 | 同一批 526 项删除每 30s 重算一次、每轮都当新告警写 WARN + journal；`delete_block_reason` 与 `last_error` 都是「只写不清」 | 告警没有「签名去重」；陈旧状态不清 |
| 「我的待裁决冲突怎么一直在 / 我明明裁决了」 | 队列条目在**没有挂载视图**或**本地节点未物化**时会被巡检误判「任务已删 / 远端已删 / 冲突已消解」清掉；反过来真正失效的条目又永远不走 | 巡检用占位签名当事实；v0.5.1 还没有「忽略这条」出口 |
| 点「对比本地/NAS」得到的**永远是「+0 / -0，两边内容逐行相同」** | 前端读错了一层 wire 形状（嵌套 vs 平级），兜底 `{}` 不报错 | 「没比过」和「比出零差异」在界面上长得一模一样 |
| 最近错误 / 熔断 / 删除状态**看起来在说当前，其实是累计/陈旧值** | `deletes_blocked` 是累计计数（真机 69 万）；会话过期要等 120s 保活才自愈，期间每 30s 报一次错 | 计数语义没标注；轮询阶段的会话失效没有自愈路径 |

另外还挖出一批**与体感无关但会伤数据**的问题（见 §2、§3），最重的两个是：
**对账把「没列出来」当成「远端已删除」，会真删本地节点与缓存**；以及
**baseline 的删除/改名从来没落过盘**（规则排除、回收站清理、已执行删除都会「下一轮又回来」）。

## 2. 严重问题（Critical，全部已修 + 回归测试）

### C1. baseline 的删除与改名**永远落不了盘**（pre-existing）

- **位置 / 根因**：`sync.rs::persist()` 只做「取较新签名」的增量合并：本轮快照里被删掉的
  条目会被内存里旧的 `g.baseline` 复活，下一轮再写回库。
- **后果**：所有「从 baseline 删除条目」的路径都失效 —— 规则排除清理、回收站清理、已执行
  删除的 baseline、改名迁移掉的旧路径（表现为这些清理**每轮重复出现**，数量永远不降）。
- **修法**：`SyncState` 增加 `hook_touched` 标记；无并发 hook 写 → **整份替换**（删除/改名
  真正落盘），有则逐条合并。该写语义要求「同一时刻只有一轮」，因此同时给
  `run_sync_once` 加了 State 级异步 Mutex 串行化（否则后台轮询与「立即同步」并发时，
  后完成的一轮会用旧快照整份覆盖）。
- **测试**：`persist_applies_baseline_deletions_so_purges_really_land_on_disk`、
  `persist_applies_baseline_renames_when_no_hook_wrote`（重开库验证）；变异测试确认撤回
  修法即变红。

### C2. 「没列出来」被当成「远端已删除」→ 会真删本地节点/缓存（数据安全）

- **位置 / 根因**：`reconcile_view` 里目录列举失败只记一条 error，`remote_map` 因此缺项；
  「候选 - remote_map」被 `decide()` 判 `DeleteLocal` → `remove_remote()` 删本地节点 +
  缓存，**还会无条件清 baseline**。默认删除保护只挡 >50 项或 >25%，小批量时**静默执行**。
- **同类逃逸（red-team 复核补上）**：目录数超过 `max_dirs_per_poll`（默认 200）时只扫排序
  前 200 个，第 201 个之后的目录**每轮都轮不到**（顺序固定）→ 同样被判「远端已删」。
  这种截断**没有报错、没有失败计数**，是最容易漏判的一种「远端视图不完整」。
- **修法**：本轮只要有「非 404 列举失败」或「目录被截断」→ `defer_deletes`，**暂缓该视图
  的删除判定**并在 note 里说明原因；下一轮列全再删。404/2/6 是确定的「不存在」，照常删。
- **测试**：`reconcile_never_deletes_locals_when_listing_failed`（用 `127.0.0.1:1` 造真实
  connection refused，跑真实 `reconcile_view`，断言节点与 baseline 都还在）；
  `delete_verdict_requires_a_fully_listed_remote_view`（含 201/2001/边界 200/两因叠加）。
- **补充（2026-10-18 晚，真机复发后修复）**：上面的修法把「目录被截断」当成临时状态，但
  顺序固定使截断**每轮都成立** —— 真机 228 个目录时「本轮跳过删除判定」连续重复 87 轮，
  删除判定被**永久**推迟（数据没丢，但远端删除永远不落地）。现在改为：
  * **轮转**扫描：每轮从上一轮停下的目录之后接着列、到尾回绕，远端根恒定参与；游标存
    `sync.db` 的 `meta`（`reconcile_scan_cursor:<mountpoint>`），`sync --once` 跨进程接得上；
  * 「视图完整」从整视图收窄到**按目录**：只有本轮列过（列举成功，或 4/5/6 经 `stat`
    确认 `exist=0`）的目录里的候选才判定，没列到的目录里的条目一律暂不判定
    （不按缺失删本地），其它目录不陪绑；
  * 改名配对的已删侧同样要求「父目录本轮列过」，不把「没看到」配成一次改名。
  * **同一前提上的第二个坑（红队复核）**：`status 4/5` 既是「路径不存在/无权限」又是
    会话失效码（真机 `/Download` 回 5、`/homes` 回 4，但路径存在）。原来 4/5 直接进
    「确定不存在」，逐目录删除放开后权限/ACL 抖动会真删本地。现在 4/5/6 必须先用
    `stat` 正向确认 `exist=0`；stat 说存在 → 目录条目记进远端视图（防「父目录列举漏了
    它」时目录自身连子树被删），内容本轮不判定；stat 也失败 → 目录自身进
    `unresolved_dirs`、内容也不判定。stat 成功不置 `auth_failed`（否则永久 ACL 目录
    每轮重登 + 刷 WARN），只有 stat 也 auth 失败或根 4/5 才置。远端根例外：挂载根不可能
    消失，根的 4/5/6 一律按权限/会话/卸载处理。
    同时 `get_list`/`stat` 检查 HTTP 状态与响应形状（反代 502 的 JSON 错误体、HTTP 200
    的非列表 JSON 都不再被读成空目录），`list_limit` 不再拿缺省 `total=0` 在第一页就
    停止翻页。
  * 测试：`scan_window_rotates_and_covers_every_directory`、
    `scan_window_survives_a_deleted_cursor_directory`（纯函数）；真实 `reconcile_view` +
    mock NAS 的 `reconcile_rotates_scan_window_instead_of_starving_deletions`、
    `listing_failure_only_defers_its_own_directory`、
    `listing_status_4_or_5_never_deletes_without_stat_confirmation`、
    `listing_root_status_4_or_5_defers_instead_of_deleting`、
    `directory_missing_from_parent_listing_but_stat_exists_is_not_deleted`、
    `stat_failure_keeps_directory_and_subtree`。旧的
    `delete_verdict_requires_a_fully_listed_remote_view` 由轮转测试替代。

### C3. 待裁决队列被巡检**静默删光**（用户裁决意图丢失）

- **场景一**：daemon 刚启动 / 用户卸载 / 恢复失败时 `views` 为空 → 旧巡检把每行都当成
  「任务已删 + 远端已不存在」→ 整队清空，理由还显示成「NAS 上的文件已不存在」。
  **修法**：`DecisionFacts::observed` 禁止用占位签名判定，并用磁盘 `tasks/*.json` 区分
  「任务被删」与「只是没挂载」；配置读不全时保守保留。
- **场景二（red-team 复核补上）**：`observed` 只保证**远端** stat 到了；daemon 重启后本地
  节点表是空的，`local_sig()` 返回占位 `MISSING` → rule 4 会把**已裁决待执行**的行判成
  「冲突已自行消解」清掉（真机 `/home/qxync-test/hello.txt` 升级重启即会中）。
  **修法**：新增 `DecisionFacts::local_observed`（本地节点真的存在才为真），rule 4 只在
  两个观察都成立时才敢判「消解」。
- **测试**：`sweep_keeps_queue_rows_when_task_exists_but_mount_is_absent`、
  `sweep_drops_queue_rows_only_when_no_task_covers_the_path`、
  `sweep_keeps_resolved_rows_when_local_side_not_observed` 等；变异测试确认撤回即红。

### C4. 冲突对比面板是「危险的假象」+ 方向反了（会让人选错裁决）

- **假象**：`DiffOutcome` 是 `#[serde(tag="status")]` newtype 变体，wire 上字段与 `status`
  **平级**；前端多读了一层 `o.diff`，兜底 `{}` 不报错 → 恒显「本地多 +0 / -0 / 两边内容
  逐行相同」。**没比过和比出零差异在界面上必须长得不一样**（这是本模块反复强调的原则，
  但旧前端恰好违反了它）。
- **方向**：真实 `text_diff` 里 `-` = 只有本地有（`removed`）、`+` = 只有 NAS 有（`added`）；
  GUI 图例与 CLI 输出都标反了。方向看反会直接导致选错「保留哪边」且**不可撤销**。
- **修法**：读平级 + 逐行形状校验（坏形状显示错误，绝不落成「逐行相同」）；core 注释、
  wire 契约夹具、GUI 图例、CLI 输出四处统一，并用生产函数写测试钉死方向。
- **测试**：`decisions_wire_contract.rs`（8 条）、`diff_direction_is_local_minus_remote_plus`、
  GUI 离线夹具 62 条断言（含「坏形状必须显示错误」）。

### C5. 文本对比的 LCS 可能 OOM / 卡死 daemon

- **根因**：DP 表按「行数平方」分配。512 KiB 上限内，1 字符一行的文本约 26 万行/侧 →
  `26万 × 26万 × 4B ≈ 275 GB`。
- **修法**：有界回退 —— 差异区两侧各截前 2000 行再做精确 LCS（最坏 ~16 MiB），
  `truncated=true`；公共前后缀已掐掉，所以截断后仍必然产生差异行，**绝不误报「逐行相同」**。
- **测试**：262144×262144 行输入 <5s 返回；1000×1000 行仍走完整 LCS。

## 3. 高价值问题（High/Major，已修）

### 3.1 同步引擎 / daemon

| 问题 | 根因 / 影响 |
|---|---|
| 同一批 526 项被挡：**每 30s 一条 WARN + 一条 journal，连续 13 小时** | 无签名去重；journal 1 万条上限几天被冲掉。改为「数量+原因」签名，变化才 WARN/journal，重复降 debug；解除补记一条 |
| 「最近错误 / 熔断告警 / note」只写不清，恢复后永远红着 | 统一到 `absorb_round(completed)`：完整跑完的轮次零错误才清；提前返回（会话失效/服务端未就绪）只更新当前错误、不清历史告警；脱水路径同款修复 |
| 会话过期要等 120s 保活才自愈 | `poll_once` 把错误塞进 `errors` 后 Ok 返回 → poller 的 `is_auth` 重登分支永远不触发。新增 `SyncReport.auth_failed`（`status=3` 只在 max_log 端点识别，附真机证据）→ 立即重登 |
| `ask` 策略每轮重复计数 + journal **谎报**「生成 N 个冲突副本」 | 实际一个副本都没生成、队列只有一条。改为首次入队才计数/记日志；journal 文案改准确 |
| 「引擎活着」的 scan journal 每 30s 一条 | 改为 600s 限频（一天 144 条） |
| 回收站子树进 baseline/对账 | 真机 baseline 71% 是 `/home/@Recycle`；QTS 清回收站会产生成批「幽灵删除」，FDO `.trashinfo` 还会被反向同步到 NAS。现在 `@Recycle`/`.Trash`/`.Trash-<uid>` 从对账/baseline/改名配对/事件/队列全部排除（`qxync-core::trash`，与 FUSE `deny_trash` 同一套段级语义），已有条目一次性清理（只清状态、不动文件） |
| diff 边界：空文件发 `bytes=0--1`、超限报「读了多少」而非真实大小 | 空文件不发 Range；超限优先取 FUSE 节点元数据的真实大小 |

### 3.3 协议层 / CLI / LAN

| 问题 | 根因 / 影响 |
|---|---|
| `download_range` 的「200 + JSON 错误体」防护是**死代码** | `body.windows(9)` 匹配 8 字节的 `"status"`，**条件恒为 false**，这道保险从上线起从未生效 → 服务端错误体被当文件内容静默返回。已改为精确识别服务端错误信封（不误伤用户同步的 JSON 文件） |
| `download_range` 区间边界 | `start > end` 会被服务端忽略 Range 回整个文件（FUSE 会把整文件写进区间缓存）；服务端忽略 Range 也未检测 → 两处显式报错 |
| 上传流把**本地读错误吞成 EOF** | 按声明长度发短 body：轻则错误根因丢失，重则服务端落盘截断文件 |
| 会话保活把 `status=8`（服务端初始化中）判成会话失效 | 每轮无意义重登 + 错误诊断；改为「探测失败，稍后再试」 |
| LAN 对端 `local_of` 用 `trim_start_matches` **反复剥前缀** | `/home/home/x` → `x`，对端读到的可能是**另一个文件**（数据完整性）；改为单次 `strip_prefix` |
| LAN 对端 `path_allowed` 在 roots 为空时 **fail-open** | 任意路径可被对端读取；改为 fail-closed |
| `read_cached` 拿「半水合文件的 0 字节」当本地内容做 diff | 假差异 → 可能选错裁决；改为校验所需区间都已就绪（内存位图 / 纯读 `.qxstate` + size/mtime/file_id 核对），未就绪给明确原因 |
| CLI `conflicts` 参数**静默优先** | `--clear/--diff/--forget/--resolve` 同时给时静默取一个；改为 clap 互斥（exit 2）、`--as` 必须配 `--resolve` |
| CLI diff 方向 / 图例 / 双重前缀；累计计数器误导 | 已统一/标注 |
| decisions diff 只算 30s 超时 | diff 最多从 NAS 拉 512KiB，慢链路会误判超时；归入长任务（600s，CLI/GUI 共用表） |

## 4. 已知问题 / 后续排期（本轮**未修**，如实列出）

1. **diff 依赖 FUSE 节点**：daemon 重启后用户还没在挂载点里访问过该路径时，「对比」会得到
   「本进程还没物化这个文件」的说明。根治需要 FUSE 侧新增「按远端路径物化节点 + 关联已有
   缓存」的 API（daemon 侧调一次即可）。这是本轮 diff 功能最明显的使用限制。
2. **FUSE 挂载点里仍能看到回收站目录**：引擎已不管理，但 `ls` 还能看到、可读可水合
   （写被 `deny_trash` 拒绝）。是否隐藏属产品决定（官方 Qsync 也不把 NAS 回收站当用户目录）。
3. **`.Trash-<uid>` 只认本机 uid**：若 NAS 侧 uid 与本机不同则不排除（真机当前一致）。
4. **持续重复的同步 errors 仍每轮 WARN 一次**：长时间断网时日志仍会增长（blocked 已去重）。
5. **GUI**：删除队列（`StatusData.deletes`）未展示；文件页三态 / LAN 面板查询失败静默降级；
   无单实例保护（两个 GUI 可同时跑）；`pick_with` 无超时；`link_read`/`credential_present`
   吞错；`ui_spec` 自检有三处「声称比实际多」。
6. **协议层**：`download_to_file` 尚未复用「200 + JSON 错误体」防护；HTTP 401/403 归为
   Transport 不触发重登（真机鉴权失败走 200+status 4/5，风险低）；上传无取消接口；
   LAN 配对限流是全局的、对端可登记任意 addr（低危）。
7. **`status=3` 只在 `qbox_get_max_log` 端点识别**为会话失效（其它端点语义未验证）。
8. **冲突计数语义**：首页/诊断展示的 `conflicts` 仍是「累计处理数」，不是「当前待裁决数」
   （队列卡本身有数量）。建议后续把 `decisions_pending` 引进 `SyncInfo`。
9. **diff 大差异**：差异区 >2000 行/侧时走有界回退，脚注会明确「结果已截断」，但
   `added/removed` 统计只覆盖已对比前缀（数字偏小）。
10. **`recorded_local` 字段未参与巡检判据**（只为对称保留），`decisions_swept` 之前只赋值
    不读（本轮已补进 journal）。

## 5. 你现在机器上该做什么（live remediation）

> ⚠️ 本批修复已随 **v0.6.0** 发布；如果你机器上还跑着 `/usr/bin/qxyncd v0.5.1`，
> 那仍是旧行为。**先升级再处理现场**，否则「放行删除」在旧版本上仍然看不出结果。

1. **构建并替换**（需要你自己有 sudo 的环境执行）：

   ```bash
   cd ~/项目/qxync
   cargo build --release --workspace --bins
   qxync daemon stop                      # 或 systemctl --user stop qxyncd
   sudo install -m755 target/release/qxync target/release/qxyncd target/release/qxync-gui /usr/bin/
   qxync daemon start                     # 或 systemctl --user start qxyncd
   ```

2. **处理卡住的 526 项真实远端删除**（`bigdir-probe` 等测试数据已被 NAS 移进回收站）：
   新版升级后第一轮会先自动清掉 baseline 里 1438 条回收站记录（只清状态、不动文件），
   然后删除候选会从 526 降到约 513；确认这些是测试数据后，在 GUI 首页/诊断页点
   「放行删除」，或 `qxync sync --once --force-deletes`。
   **不要再在新版还没生效时反复点**：旧版上放行后的结果看不到，只会重复弹告警。
3. **处理 `/home/.recent` 那条永恒的待裁决**：它其实是 NAS 自己维护的「最近访问」索引，
   不是用户数据。新版用「忽略这条」直接出队即可（只删队列行、不动文件）。
   `/home/qxync-test/hello.txt`（已裁决 keep_remote）在新版里会等到本地节点物化后再判定，
   不会在重启瞬间被误清。
4. **如果换过会话/长时间断网**：新版会在轮询阶段立即重登，不再等 120s，也不会把
   「服务端初始化中」误诊成「sid 失效」。
