## 一、重启 / 重新挂载后，缓存状态立刻恢复（M31）

### 之前的现象

daemon 重启或重新挂载后：

- `qxync status` 显示「已缓存 7.6 KiB / 水合文件 1」（实际盘上有 **495 MiB / 386 份**）；
- Dolphin 角标 / `user.qxync.state` / GUI 文件页三态**全部变回白云**（placeholder）；
- 更糟的是：读一个明明已缓存的 5.26 MiB 文件，**真的回源重新下载了 41 个区间**。

### 根因（两个独立缺陷）

1. **水合位图只在第一次 `read` 时才读回**。位图（`.qxstate`）落盘没问题，但读回它的
   唯一入口是 `cache_file_for`。重启后节点表从目录清单重建、区间表全空，而角标 /
   `status` 缓存统计 / GUI 三态全看内存节点 → 整列已缓存文件显示成占位符。
2. **`mtime` 被改后位图签名不更新**。`cp -a` / `rsync -a` 往挂载点拷文件的时序是
   「写完 → 落位图（记的是**写盘时刻**）→ 工具再把源文件的时间戳设回去」。
   `setattr` 更新了节点/清单/远端，却没回写 `.qxstate` 头 → 位图与清单的签名
   **永久分叉**（真机 392 份里 326 份命中）。重启后认领严格比对签名必然失配
   → 整份缓存被判不可信 → 回源重下。

### 现在的行为

| 环节 | 行为 |
|---|---|
| 挂载时 | 扫 `<cache>/*.qxstate` 重建水合索引（**只读头 + 位图，不读内容**，392 份毫秒级） |
| 节点物化 | 按签名预填区间表（零网络）——`ls` 完角标就是对的，不需要先 `cat` 一遍 |
| `status` / GUI | 缓存统计从索引算；「共 N」分母用 baseline（不再随「物化了几个节点」跳变） |
| 只改 mtime 的 `setattr` | 同步回写 `.qxstate` 头（签名不再分叉）；在线路径同步补上在途上传作业的 mtime |
| 认领容差（新增第二种） | 清单 mtime **更旧** + 全量就绪 + 逐区间 `xxhash64` 全过 → 认领并把签名对齐清单。**远端更新方向仍然拒绝、校验和不过仍然回源** —— 「绝不返回错误内容」的红线不动 |

### 升级后预期（你这台机器）

```text
qxync status → 已缓存 ≈ 490 MiB / 水合文件 392 / 共 baseline 数
Dolphin 角标 → 已缓存文件立刻显示 ✓（不用先读一遍）
```

## 二、写入的校验和与内容分叉 + 改名丢校验和（M32）

M31 排查时 `qxync verify` 报 403 个已水合文件里 **198 个「内容损坏」**——但抽查
（`B.pdf`、损坏的 docx）盘上内容与 NAS 重新下载的字节 **sha256 完全一致**。
内容没坏，坏的是 `.qxsum`（逐区间 xxhash64 表）。两个独立缺陷：

1. **未对齐写入被当成「整区间写完」**：`mark_written_chunks()` 旧判据用
   `min(区间尾, EOF)` 当区间尾 —— 新建/追加文件第一次写进区间的几 KB 就被当成
   整区间内容算了 hash，之后追加/补写不再重算 → `.qxsum` 永久停在第一版。
   真机证据：19 个单区间损坏样本全部满足「盘上 hash == `xxh64(内容前 N 字节)`」，
   N 正是那个程序第一次写的长度（WPS 锁文件 1 字节、KIO 4096、某程序 16000）。
2. **改名 / O_TMPFILE 物化只搬「内容 + 位图」，漏了 `.qxsum`**：新名字于是
   「有位图、没基准」（判损坏、白重下）或「新内容 + 旧文件的基准」（每次都判损坏）。
   真机 22 份孤儿 `.qxsum` 全挂在 `.part` / `.tmp` / `wpsdiag_*` 这类改名前的临时名上。

### 修复

- 部分覆盖的区间只**记脏**、不拿半截内容算 hash；新增 `finalize_written_chunks()`
  在 **`release` / `flush` / `fsync`** 时按最终内容一次补齐（只读脏区间 ——
  整块对齐的 `cp` 零额外开销）；
- `move_cache_triplet()` 三件套（内容 / 位图 / 校验和）一起搬，先清目标位置残留的
  旧基准（宁可没基准，也不能拿错基准）；硬链接复制分支同时复制 `.qxsum`。

### 存量的 198 份怎么办

| 方式 | 效果 |
|---|---|
| 什么都不做 | 首次读时安全闸拒绝认领、重新下载一次（内容本来就是对的，只浪费一次带宽）；下载会写回正确 `.qxsum`，不再复发 |
| `qxync verify --repair` | 提前把坏区间退回按需水合，下次读再下载 |
| 用 WPS / 编辑器再保存一次 | 经 FUSE 写入会在 `release` 时自动重算校验和，**不回源** |

刻意**没有**做「直接拿本地内容重算校验和」的自动修复 —— 那等于让可能已损坏的内容
自己给自己发合格证，破坏 T3「没有基准就不声称内容正确」的红线。

## 三、GUI 下载进度：右下角浮动卡片（M33）

M26 的进度链路（daemon 推进度行 → GUI emit → 前端监听）**本身一直是通的**，
坏在展示挂点：进度写在文件页工具栏那个小小的「进行中…」徽标上 —— 字号小、
位置不显眼、切到别的页就彻底看不见，真机上等于「没有进度提示」。

现在下载超过 **3 秒**（静默期，与 CLI 同一套规则）在**窗口右下角**浮一张卡片：

```text
┌──────────────────────────────────────┐
│ big.bin                              │
│ ▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░ │
│ ⬇ 61.2% · 2.4 MiB/4.0 MiB · 798 KiB/s · 剩余 2s │
└──────────────────────────────────────┘
```

- 多笔并发下载各自一张、纵向堆叠；`position: fixed` 任何页面都可见；
- 容器 `pointer-events: none`（只有卡片本身可点、点击即关），不挡下面的页面交互；
- 成功 → 绿色「✅ 下载完成 · N」停留 2.5s 自动消失；失败 → 红色 + 错误摘要停留 6s；
  快下载（<3 秒）从头到尾无痕；未知总量（服务端 chunked）进度条走滑动动画；
- Rust / daemon 侧**零改动**（纯 UI 层修复）。

## 五、升级须知

1. 下载本版 Release 资产（tar.gz / Arch 包 / `.deb`），或源码 `cargo build --release`；
   **`qxyncd` / `qxync-gui` 都换了，必须重启 daemon**（GUI 重新打开）：
   ```bash
   qxync daemon stop
   qxync daemon start
   ```
2. 升级重启后 `status` / 角标**立刻**显示真实水合状态；**不需要**重新读一遍文件。
3. 存量 198 份校验和分叉的文件，首次读时会重新下载一次（见 §二表格），属预期行为。
4. M31/M32 修复的是**新产生**的分叉；旧分叉的 `.qxstate` 签名在下次挂载认领时
   按新容差规则自愈（清单更旧 + 校验和全过 → 零网络认领）。
