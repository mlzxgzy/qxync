# M17：两步验证（2SV / TOTP）

> **状态**：已实现，随 **v0.6.2** 发布。本文是设计说明 + 协议实测记录：
> 为什么以前登不上、QTS 到底怎么要验证码、密钥存在哪、daemon 重登怎么现算、
> 哪些第二因素**没**做。
>
> 涉及三层：`qxync-core`（TOTP 与凭据模型）、`qxync-client`（`authLogin.cgi` 请求体）、
> `qxync` CLI / `qxyncd` / `qxync-gui`（入口与展示）。
> **没开 2SV 的账号，行为一字不改** —— 这是 M17 的硬约束。

---

## 1. 问题背景

### 1.1 症状

账号在 QTS 里打开「两步验证」（2SV）之后，qxync 的登录全线失败，且报错**指向错误的方向**：

- CLI `qxync login` 报 `登录失败: authPassed=0 … need_2sv=1`，后面还跟着一句
  「检查口令编码：必须是 base64」；
- daemon 的自动重登（保活 / 轮询遇鉴权失败 / 挂载点热重试）同样失败，
  挂载点从「能用」变成持续 EIO；
- GUI 的「保存并登录」停在失败，看板/文件页都拿不到会话。

旧实现只发 `user + pwd(base64)`：

```rust
// crates/qxync-client/src/lib.rs（v0.6.1 及以前，login() 的请求体）
let body = [
    ("user", user),
    ("serviceKey", "1"),
    ("client_app", "Qsync"),
    ("client_agent", concat!("qxync/", env!("CARGO_PKG_VERSION"))),
    ("gen_client_id", "1"),
    ("remme", "1"),
    ("dont_verify_2sv_again", "0"),
    ("pwd", pwd.as_str()),
];
```

注意最后那段错误消息：`errorValue` 缺失时被格式化成 `?`，整句还跟着一句
「检查口令编码：必须是 base64」—— 口令明明是对的，用户只会去反复检查密码。
**这是 v0.6.2 顺带修掉的一个真实误导**（见 §3.6）。

### 1.2 为什么「顺手支持一下」不行

2SV 不是登录后的一次性弹窗：`authLogin.cgi` 的**第一次请求**就决定了给不给 sid。
没有第二因素时，服务端返回的是 `authPassed=0` + `need_2sv=1`，客户端手里**没有任何
续接凭据**；`qsyncsrv.cgi` / `utilRequest.cgi` 的所有端点都拿不到 sid。

所以必须做到两件事：

1. **能带第二因素**：同一份表单里多一个字段；
2. **能长期自动登录**：daemon 会在会话过期后反复重登（可能几小时/几天一次），
   不能要求用户每次都在场输验证码 → 只能保存 **TOTP 密钥**，重登时现算。

## 2. 协议实测（2026-10-18，QTS 测试机）

> 测试环境（地址 / 账号 / TOTP 密钥）在 `docs/测试环境.local.md`，该文件已 gitignore。
> 下面只保留判据字段，sid 已打码。

### 2.1 结论：一个字段，两种发法

在 v0.6.1 那份表单基础上，多带一个 **`security_code=<6 位 TOTP>`**，其余字段一个不动：

| 字段 | 值 |
|---|---|
| `user` | 账号 |
| `serviceKey` | `1` |
| `client_app` | `Qsync` |
| `client_agent` | `qxync/<版本>` |
| `gen_client_id` | `1` |
| `remme` | `1` |
| `dont_verify_2sv_again` | `0` |
| `pwd` | `base64(口令)` |
| **`security_code`** | **6 位 TOTP（仅开了 2SV 的账号需要）** |

**实测（协议层）**：把 `security_code` 直接放进第一次请求，也能 `authPassed=1` +
拿到 `authSid` —— 一次往返就够，不需要「先拿 need_2sv 再发第二次」的握手。

**实现选择（qxync）**：照 QTS Web UI 的两步流程 —— 第一次请求**不带** `security_code`，
只有响应是 `need_2sv=1` 时才发带 `security_code` 的第二次请求。这么选的原因：

1. **未开 2SV 的账号请求体与 v0.6.1 逐字节相同** —— 不是「希望 NAS 忽略多出来的字段」，
   而是结构上就没有这个字段（M17 的硬约束）；
2. 30 秒的验证码只在**确实需要**时才生成/提交，不用为「账号可能没开 2SV」白算一次；
3. 这条路正是 NAS 自带前端 `qos-core-login.js` 走的路（§2.3），行为最容易对齐。

sid 签发之后与普通登录完全一样：`qsyncsrv.cgi` / `utilRequest.cgi` 路径、会话保活、
热更新语义都不变。

### 2.2 三种响应的判据（脱敏节选）

```
<!-- A. 不带 security_code：登录被拦在第二步 -->
<authPassed>0</authPassed>
<need_2sv>1</need_2sv>
<need_2_step_verification>1</need_2_step_verification>

<!-- B. 带正确的 security_code：拿到 sid -->
<authPassed>1</authPassed>
<authSid>********</authSid>

<!-- C. security_code 错误：仍是第二步，且没有 errorValue -->
<authPassed>0</authPassed>
<need_2sv>1</need_2sv>
```

要点（写代码时最容易搞错的两条）：

1. **A 和 C 都长成 `authPassed=0 / need_2sv=1`**，服务端**不会**告诉你「验证码错了」还是
   「你根本没给」。所以「没提供」与「提供了但被拒」的区分只能靠**客户端自己是否带了字段**。
2. **验证码错误时没有 `errorValue`**。旧代码把它格式化成 `?` 并附加「检查口令编码」，
   对 2SV 账号是完全错误的提示。

### 2.3 旁证：QTS 自己的登录前端也是这么干的

NAS 自带前端 `/cgi-bin/js/qos-core-login.js` 是**两步**：先 `pwd` 拿到 `need_2sv`，
第二段请求带 `pwd + security_code`。字段名就是 `security_code`，**6 位、30 秒、
SHA-1（RFC 6238）** —— 与 §2.1 的「第一次请求就带码」在服务端是同一个校验，
只是官方前端为了交互把它拆成了两步。

> 这跟 M0 得出的那条经验一致：**登录协议的权威参考是 NAS 自己带的前端**，
> 不是 Windows 二进制的逆向报告（报告里的 `code` / `verify_code` 字段名没有被真机接受）。

### 2.4 没被验证的协议细节（如实写）

- **没测** `dont_verify_2sv_again=1`（「记住这台设备」）会不会让后续请求免验证码。
  qxync 有意保持 `0`：不写设备信任状态、不需要 NAS 侧配合，语义最干净。
- **没测** 连续输错验证码会不会触发账号锁定 / 限流。所以客户端每轮只尝试一次，
  失败就把服务端的原话交给用户，不做自动重试。
- **没测** 非 TOTP 的第二因素（见 §9）。

## 3. 设计与数据模型

### 3.1 内置 TOTP：不新增依赖

`crates/qxync-core/src/totp.rs`（新）实现 RFC 6238 的**最小可用子集**：

| 组成 | 做法 |
|---|---|
| Base32 解码 | RFC 4648 §6：去空白 / 连字符 / `=` 补位，统一大写；密钥至少 8 个 Base32 字符，长度模 8 必须是 `0/2/4/5/7`；非法字符或**尾部非零填充位**直接报错（不猜） |
| `otpauth://` URI | 只取 `secret`；`algorithm` 必须是 `SHA1`（或缺省）、`digits` 必须是 `6`、`period` 必须是 `30` —— 显式写了别的值**直接报错**，不静默按默认值算 |
| SHA-1 + HMAC | 手写（RFC 3174 / RFC 2104），与 TOTP 一起放在 `totp.rs` 内，不引入 `sha1` / `hmac` crate |
| 动态截断 | RFC 4226 §5.3：`offset = 末字节 & 0x0f`，取 4 字节大端、清最高位 → `% 10^6` |
| 时间步 | `STEP_SECS = 30`、`DIGITS = 6`；只算**当前步**，不做 ±1 步容错（服务端接不接受由它决定，客户端不猜） |
| 对外入口 | `normalize_otp`（输入 → `Otp`）、`resolve_code`（`Otp` → 本次要提交的 6 位码，密钥形式现算）、`code_now` / `code_at`（现算 / 单测用）、`is_code`、`base32_decode` |

为什么手写而不是加依赖：仓库对新增 crate 很克制（`Cargo.toml` 的依赖都是带明确理由的），
而 TOTP 需要的只有 SHA-1/HMAC/Base32 三小块，各三四十行，**可读、可单测、不引入供应链**。
代价是「加密实现自己写」的风险 —— 用 RFC 3174 / RFC 2202 / RFC 4648 / RFC 6238 的
官方向量钉死（§8.1）。

### 3.2 一个输入，两种含义：`Otp`

```rust
// crates/qxync-core/src/totp.rs
pub enum Otp {
    /// 6 位一次性验证码（不落盘）
    Code(String),
    /// TOTP 密钥（Base32 或 otpauth:// URI，归一化成大写 Base32，会落盘供重登现算）
    Secret(String),
}

pub fn normalize_otp(input: &str) -> Result<Otp>;
```

判别规则是**确定性**的：去掉首尾空白后，**纯 6 位数字 → `Code`**（6 位数字永远不会被
当成密钥 —— 合法密钥不短于 8 个 Base32 字符，这个歧义必须消灭）；`otpauth:` 开头 → 解析
URI；其余按 Base32 密钥归一化并校验。解析失败就报错。
这样 CLI 的 `--otp-code` / `--otp-secret` 和 GUI 的**一个输入框**共用同一套解析，
不会出现「两个入口对同一个字符串理解不同」。

### 3.3 凭据：新增可选 `otp_secret`

```rust
// crates/qxync-core/src/config.rs
pub struct Credentials {
    pub host: String,
    pub user: String,
    pub password: String,
    /// 可选：TOTP 密钥。缺省 = 该连接未配置两步验证。
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub otp_secret: Option<String>,
}
```

落盘形状（`default` 连接；其它连接是 `links/<id>.credentials.json`）：

```json
{
  "host": "<NAS>",
  "user": "<用户>",
  "password": "<口令>",
  "otp_secret": "<TOTP密钥>"
}
```

- **旧凭据文件不需要迁移**：没有 `otp_secret` 就是 `None` = 未配置 2SV。
- **按连接隔离**：A 的密钥不会被拿去登 B（与口令同一套 `load_for` / `save_for`）。
- 配套方法（都在 `config.rs`）：
  - `has_otp()`：这个凭据里有没有**非空**密钥（空串/纯空白按「没配」处理，
    GUI 清空后不会留下一个空密钥）；
  - `with_otp_secret(Option<String>)`：改口令时用
    `Credentials::new(host, user, password).with_otp_secret(旧密钥)` 把密钥原样带上，
    **只换口令不会把 2SV 密钥抹掉**；
  - `present_otp_for(paths, link) -> bool`：只回答「这个连接配没配」，
    GUI 显示「已配置」用它，**不读、不回显、不返回密钥**。

### 3.4 IPC 契约：一次性验证码透传

```rust
// crates/qxync-core/src/ipc.rs
Request::Login {
    user: Option<String>,
    password: Option<String>,
    /// 一次性输入（6 位码 / Base32 密钥 / otpauth URI）；serde(default) = 旧客户端不带也能解析。
    #[serde(default)]
    otp: Option<String>,
}

pub struct LoginData {
    pub sid_masked: String,
    pub user: String,
    pub uid: Option<String>,
    /// 本次登录是否经过了第二步验证（旧字段缺省 false）。
    #[serde(default)]
    pub two_step: bool,
}
```

- `otp` 是**请求级**的：如果解析出 `Secret`，daemon 归一化后写进凭据文件供以后重登现算；
  如果解析出 `Code`，只用于这一次登录，**不落盘**。
- daemon 侧的优先级：本次请求给的 `otp` > 凭据里保存的 `otp_secret`
  （`login_internal` 里先 `otp.or_else(|| creds.otp_secret)`），所以定时重登在没有请求参数时
  也能自己算。
- **IPC_VERSION 不 bump**：只加 `serde(default)` 字段，新老两端互相可解析
  （与 M16 的结论同一个口径：bump 会让新旧进程无法混跑，代价大于收益）。

### 3.5 客户端：`login_with_otp`（两步流程）

```rust
// crates/qxync-client/src/lib.rs
pub async fn login(&mut self, user: &str, password: &str) -> Result<Session>;          // 保持旧签名
pub async fn login_with_otp(&mut self, user: &str, password: &str, otp: Option<&str>)
    -> Result<Session>;                                                                // 新入口
```

`login()` 只是 `login_with_otp(.., None)` 的薄封装。`login_with_otp` 的实际流程：

1. **先归一化输入**（`normalize_otp`）：格式不对就直接报错，不白跑一趟 NAS；
2. 发**第一次** `authLogin.cgi` —— **不带 `security_code`**，请求体与 v0.6.1 逐字节相同
   （`auth_login(user, password, None)`）；
3. `authPassed=1` → 账号没开 2SV，正常返回（`two_step=false`）；
4. `need_2_step_verification=1` / `need_2sv=1` → 生成验证码（`Code` 直接用；`Secret` 用
   `code_now` **现算**），发**第二次**请求，带 `security_code`；
5. 第二次仍 `need_2sv=1` → 明确报「验证码被 NAS 拒绝」（可能过期 / 密钥错 / 时钟偏移）；
6. 成功 → `Session { sid, …, two_step: true }`（把新 sid 热推给同账号挂载点是 **daemon** 的事，
   见 §6；客户端只负责把这次登录做成）。

> 「未开 2SV 的账号请求体一字不改」是**结构性**保证：第一次请求里根本没有这个字段，
> 而不是「带上空值赌 NAS 忽略」。

### 3.6 错误提示要能自救

旧提示「检查口令编码：必须是 base64」对 2SV 账号是误导。现在的分支：

| 场景 | 客户端能知道的事实 | 提示（实际文案要点） |
|---|---|---|
| `authPassed=0` / `need_2sv=1`，**没带** otp | 账号开了 2SV，我们没提供第二因素 | 「该账号已开启两步验证（2SV），但这次没有提供验证码或 TOTP 密钥：用 `--otp-secret <Base32密钥>` 保存密钥，或 `--otp-code <6位验证码>` 只用于本次登录」+ NAS 响应摘要 |
| `authPassed=0` / `need_2sv=1`，**带了** otp（第二次仍拒） | 提供了但被拒 | 「两步验证失败：验证码被 NAS 拒绝 —— 检查 TOTP 密钥是否正确、验证码是否已过期（30 秒一换）、本机与 NAS 的时钟是否一致」 |
| 其它 `authPassed=0` | 与 2SV 无关 | 保留原来的 `errorValue` 提示（含 base64 那条） |

提示里**绝不含密钥、也不含验证码**；日志同理（只记 `two_step=true/false` 与打码 sid）。

## 4. CLI 用法

两个**全局参数**（与 `--password` 同级，`login` 子命令和直连模式都吃）：

```bash
# 推荐：保存 TOTP 密钥 —— 之后 daemon 重登自己现算验证码
qxync --host <NAS> --port 9834 --insecure \
      --user <用户> --password '<口令>' \
      --otp-secret '<TOTP密钥>' login

# 一次性：只用于这次登录，不保存
qxync --host <NAS> --port 9834 --insecure \
      --user <用户> --password '<口令>' \
      --otp-code 123456 login
```

- `<TOTP密钥>` 是 Base32 密钥，也接受 `otpauth://totp/...?secret=...` 整条 URI；
  从 authenticator app 的「手动输入」或二维码解码结果里拿。
- 环境变量版：`QXNYC_OTP_SECRET` / `QXNYC_OTP_CODE`（**推荐**，不会进 shell 历史）。
- **优先级**：`--otp-code`（一次性）> `--otp-secret`（本次）> 凭据里已保存的 `otp_secret`。
  所以「只补一个密钥」不用重复给口令/地址：

  ```bash
  qxync login --otp-secret '<TOTP密钥>'
  ```

- `--otp-secret` 只接受**密钥**：传 6 位数字会直接报错并提示改用 `--otp-code`
  （一次性验证码不该落盘）。
- 账号**没开** 2SV：不带这两个参数，行为与 v0.6.1 完全一样（第一次请求之后就直接成功，
  根本不会发带 `security_code` 的第二次请求）。给了密钥也照常登录，只是这次用不上。
- `login` 成功后多打两行：`两步验证 : 已通过（TOTP）` 与
  `TOTP 密钥 : 已保存（daemon 重登时自动现算验证码）`（只在真的存了密钥时打印后者）。

> `--otp-code` 会出现在 `ps` 的 argv 里。一次性码 30 秒过期、且失败不自动重试，
> 风险有限；长期使用请用 `--otp-secret`（密钥走环境变量）。

## 5. GUI 用法

「设置 → 连接」表单里新增一项 **「两步验证（可选）」**（`#f-otp-secret`，口令那种
不回显的输入框）：

| 行为 | 说明 |
|---|---|
| 填 **6 位验证码** | 一次性：只随本次「保存并登录」发给 daemon，**不落盘**；界面会提示「一次性验证码不会保存」 |
| 填 **TOTP 密钥 / `otpauth://` URI** | 归一化后写入该连接的凭据文件（`0600`），之后 daemon 每次重登自动现算验证码 |
| **留空** | 保留已保存的密钥（编辑连接时不填 = 不改）；目前**没有**单独的「清除密钥」按钮 |
| 已配置提示 | 凭据提示行尾部追加「两步验证已配置 / 未配置」；连接列表里配过的连接多一个徽标 |
| 不回显 | 密钥只写不读：每次填表都清空输入框；`credential_present` / `links_status` 只回布尔 `otp` |
| 登录结果 | 「设置 → 连接」表单下方的结果框（`#login-result`）在 sid / user / uid 之后多一行「两步验证」：`LoginData.two_step=true` → `已通过（TOTP）`，否则 `未启用 / 本次未使用`；另按 `otp_saved` / `otp_note` 追加「密钥已保存（之后自动生成验证码）」/「一次性验证码不会保存」 |
| 失败提示 | 直接把 daemon 的错误原文显示出来（含 §3.6 的自救提示），不在前端拼「密码错误」这种猜测 |

> GUI 侧不自己算 TOTP —— 前端是零依赖静态三件套，没有 crypto；密钥只做「存/传」，
> 现算发生在 daemon / core（§6）。「填的是验证码还是密钥」由 core 的 `normalize_otp`
> 判别，GUI 不自己猜。

## 6. daemon 的重登行为（这一节是「长时间挂载不掉线」的关键）

daemon 会在这些时刻重登：会话保活、轮询遇鉴权失败、挂载点遇鉴权失败的热重试。

1. `login_internal` 读**该连接**的凭据（`Credentials::load_for`）；
2. 待用的第二因素按优先级取：本次 IPC 请求的 `otp` > 凭据里的 `otp_secret`；
3. 如果账号要 2SV：**每次重登都从密钥现算一个当前验证码**（`code_now`），
   在第二次请求里拼进 `security_code`；
4. **只保存密钥，绝不缓存验证码** —— 验证码 30 秒就废，缓存它等于把「下次重登」变成
   「下次一定失败」；
5. 如果 IPC 传进来的是**密钥**（不是 6 位码）：归一化后**写回凭据**（0600）；
   如果传进来的是验证码：只用于这一次，不落盘；只换口令时用
   `Credentials::new(..).with_otp_secret(旧密钥)` 保留原密钥；
6. 重登成功照旧把新 sid 热推给同账号挂载点（M10 语义不变），日志记
   `登录成功 user=… sid=… two_step=true/false`；
7. 账号要 2SV 但**没配密钥**：报一条明确的 Auth 错误（提示用 `--otp-secret` 补），
   不会静默降级成「未登录」让人摸不着头脑。

`Request::Login { otp }` 里的**一次性验证码**只对当次请求有效：
GUI 里填 6 位码 → 登录成功 → 凭据文件里仍然**没有** `otp_secret` →
daemon 下次重登会再次失败并提示。**要长期用，请存密钥**（GUI 填密钥，或 CLI `--otp-secret`）。

## 7. 安全与存储

| 项 | 做法 |
|---|---|
| 敏感级别 | TOTP 密钥 = **与口令同级**（拿到口令 + 密钥就能完全接管账号的自动登录） |
| 存储位置 | 与口令**同一个凭据文件**：`default` 是 `~/.config/qxync/credentials.json`，其它连接是 `~/.config/qxync/links/<id>.credentials.json` |
| 权限 | `0600`（复用既有 `Credentials::save_for` 的写盘逻辑，不新开一套） |
| 明文？ | 是，明文（**与现在的口令一致**）。keyring/系统密钥环是后续工作，不是这一版的范围 |
| 日志 | 不写密钥、不写验证码；只记 `two_step` 与打码 sid |
| 错误信息 | 不回显密钥；格式问题只说具体原因（「TOTP 密钥太短（N 个 Base32 字符，至少 8 个）」/「长度不合法」/「里有非法字符」/「otpauth URI 的算法是 X，只支持 SHA1」） |
| IPC | `LoginData` 只有 `two_step: bool`，**没有任何密钥字段**；GUI 的「已配置」来自 `present_otp_for` 的布尔值 |
| 设备信任 | 有意保持 `dont_verify_2sv_again=0`：不往 NAS 写「信任这台设备」，避免留下额外的持久状态 |

## 8. 测试

### 8.1 单元测试（`cargo test -p qxync-core` / `-p qxync-client`）

| 覆盖点 | 判据 |
|---|---|
| SHA-1（RFC 3174 §7.3） | 空串 / `abc` / 长串 / **100 万个 `a`**（多块 + 长度跨块）四组官方向量逐字节一致 |
| HMAC-SHA1（RFC 2202 §2） | 三组官方向量逐字节一致 |
| Base32（RFC 4648 §10） | `MZXW6===` → `foo`、`MZXW6YTBOI======` → `foobar`、小写也认、非法字符报错 |
| TOTP（RFC 6238 附录 B，SHA-1 seed） | 六组时间点。种子是 `"12345678901234567890"`；客户端只取 **6 位**，所以对应 `287082 / 081804 / 050471 / 005924 / 279037 / 353130`（`t=59 / 1111111109 / 1111111111 / 1234567890 / 2000000000 / 20000000000`） |
| `normalize_otp` 容忍的用户写法 | 小写 + 空格 + 连字符（`jbswy3dp ehpk-3pxp`）、`====` 补位、`otpauth://` URI 都归一化成同一个大写 Base32（单测用的是公开示例密钥，不是真实账号的密钥） |
| `normalize_otp` 的拒绝面 | 6 位数字 → `Code`（不会被当密钥）；`digits=8` / `period=60` / `algorithm=SHA256` 的 URI、非法 Base32、太短（<8 字符）、空串都报错 |
| `resolve_code` | 验证码原样返回；密钥形式**现算**且结果是 6 位数字 |
| 凭据兼容 | 旧 JSON（无 `otp_secret`）能读；带上密钥写回后 `0600` 且能读回；空串按「没配」处理 |
| IPC 兼容 | `serde(default)`：旧形状 `Login`（无 `otp`）仍能反序列化、`LoginData` 无 `two_step` 时默认 false（没有单独单测，靠 serde 语义与新旧混跑保证，与 M16 同口径） |
| 2SV 错误分支 | 由 §8.2 的真机用例断言「两步验证 / 2SV」出现在错误里；错误串只拼 `authPassed` / `errorValue` / `need_2sv` 三个判据字段，**不拼密钥** |
| 离线协议测试 | `two_step.rs::m17_bad_totp_secret_fails_before_network`：非法密钥必须在联网前就以 `Error::Auth` 失败（不 ignore、不需要 NAS） |

cargo test -p qxync-core m17_credentials
cargo test -p qxync-client          # 客户端既有套件：确认登录改动没碰坏其它解析
cargo test -p qxync-proto-test --test two_step   # 只跑那条离线用例（真机用例是 ignored）

## 9. 能力边界（如实写）

**做的是**：QNAP 账号的 **TOTP（authenticator app）** 第二因素。

**没做的**：

- ❌ **只支持 TOTP**。QNAP 还支持安全问题、邮件验证码、二维码批准、设备批准等第二因素，
  这些**一个都没实现**；遇到这类账号，登录仍会失败（错误提示只能说到「两步验证」这一层，
  不会假装能登）。
- ❌ **不是 OAuth / 云账号**：仍然只做「直连 NAS 的本地账号」，2SV 不改变这条边界。
- ❌ **没有「记住这台设备」**：不实现 `dont_verify_2sv_again=1` 的持久信任；
  每次新会话都用新验证码（有密钥就自动算，用户无感）。
- ❌ **没有恢复码 / 备用码**流程：密钥丢了只能去 NAS 端重置 2SV。
- ❌ **没有 keyring**：密钥与口令一样明文存 0600 文件。
- ⚠️ **依赖本机时钟**：验证码是「本机时间 + 密钥」算出来的；本机时间偏太多，
  服务端会拒。提示里会让人检查时钟（`timedatectl` / NTP）。
- ⚠️ **协议细节未测全**：见 §2.4（设备信任、失败限流）。

## 10. 兼容性

| 场景 | 结果 |
|---|---|
| 账号**没开** 2SV，升到 v0.6.2 | 行为一字不改：请求体不带 `security_code`，凭据文件不新增字段 |
| 旧凭据文件（无 `otp_secret`） | 直接可读 = 「未配置 2SV」；不需要迁移 |
| 新凭据文件给**旧版本**读 | 旧版本忽略未知字段（serde 默认），口令照常可用；只是不支持 2SV 账号 |
| 回退 v0.6.1 | 2SV 账号重新登不上（其余功能不受影响）；凭据文件不需要改回 |
| 多连接（M16） | 每条连接各自一份 `otp_secret`，互不串用 |
| IPC 新旧混跑 | **不 bump `IPC_VERSION`**，`otp` / `two_step` 都是 `serde(default)`，可混跑 |
