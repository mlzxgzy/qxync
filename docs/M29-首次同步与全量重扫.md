# M29：首次同步与「太久没同步」按首次处理

> 真机反馈（2026-10-21，账号主目录 4964 个目录）：
>
> ```text
> 说明（qnap.kdajv.com）：
> qbox_get_sync_log lower=337938 返回 -17（区间内没有事件，第 182 次）；
> 对账：对账时间预算 15s 耗尽：本轮列了 171/4964 个目录，下轮从游标续扫；
> 目录数 4964 超过单轮硬顶 2000（本轮按轮转列了 2000 个）；
> 未列到的目录下 29678 项本轮暂不判定（不按缺失删本地）
> ```
>
> 用户的判断（本设计的验收口径）：
> **第一次同步应该把整棵树同步一遍；同步完就有缓存了；有缓存就恢复原来的同步频率；
> 太久没同步也应该按「没同步过」算。**

---

## 1. 问题在哪

变更发现的主路径是「列目录 + baseline 差集」（真机事件快路径基本是死的，`-17` 恒返回）。
旧实现每轮只按「间隔 × 50%」的预算列一小段目录（默认 30s 间隔 → 15s 预算），
**首次同步**也要被这个预算和 2000 个目录的硬顶切成几十轮：

```text
4964 目录 × 每轮 ~171 个 = 29 轮（30s 间隔下约 24 分钟，且期间每条删除判定都推迟）
```

这有三个后果：

1. **首次同步看起来永远跑不完**：用户看不到「已同步完」，只看到每一轮都在「暂不判定」；
2. **目录数越多越慢**：轮转周期与目录数成正比，与「有没有缓存」无关；
3. **休眠/离线很久回来以后**，baseline 已经不可信，却仍旧按 30s/600s 的常规节奏
   慢慢轮转，而不是先对齐一次。

---

## 2. 语义（三层，和用户的说法一一对应）

| 状态 | 判据 | 行为 |
|---|---|---|
| **首次同步** | 这个挂载点还没有 `reconcile_full_done:<挂载点>` | 全量列举：BFS 列完整棵树（每目录一次），一轮做完 |
| **有缓存了** | 全量完成标记已落 | 回到**常规轮转 + 用户配置的间隔**（默认 30s） |
| **太久没同步** | 距上次**完整跑完**一轮同步 ≥ `FULL_SYNC_STALE_AFTER`（默认 1h） | 视为「没同步过」：再做一次全量列举 |
| **上次没列完** | `reconcile_full_pending:<挂载点>` = `1` | 继续全量（崩溃/断网/预算用完留下的标记） |

「全量同步」的产物是**目录树 + 元数据（baseline/清单缓存）**，不是把每个文件内容都下载 ——
本客户端的 `space_saving` / `pagecache` 是**按需同步**：文件内容在你读它的时候才水合。
这与「有缓存了」的含义一致：本地有了完整目录清单和 baseline，`ls` 不再等网、对账有据可依。

---

## 3. 一轮全量同步怎么做

`reconcile_view` 在全量模式下改走 **BFS**（广度优先，窗口可增长）：

```text
队列 = 当前已知目录（挂载视图节点 + baseline 里的父目录 + 候选的父目录）
while 队列非空:
    列一个目录
    把列举里新出现的子目录「接着入队」（同一个目录只入队一次）
    把条目收进 remote_map（之后登记 baseline）
```

* 每个目录**只列一次**（旧做法按层分多轮，每轮还要把已列过的目录重列一遍）；
* 不读轮转游标、不受常规单轮预算（间隔 × 50%）与 `max_dirs_per_poll` 硬顶截断；
* 单轮预算 `FULL_SCAN_BUDGET`（默认 1800s，`QXNYC_FULL_SCAN_BUDGET_SECS` 可覆盖，`0` = 不限）；
* 预算用完 → 收手、保留 `pending`，轮询循环 **2 秒后**继续（`FULL_SYNC_RETRY_SECS`），
  不等 30s/600s 的常规间隔；
* 收尾时机在**删除判定之前**：删除被熔断挡住，不该让「整棵树已经列完了」不算数
  （否则熔断期间每轮都重扫整棵树）。

完成时落两份 meta（按挂载点）：

```text
reconcile_full_done:<mountpoint>     完成时间（unix 秒）—— 首次同步只做一次的标记
reconcile_full_pending:<mountpoint>  进行中标记（完成时删除）
```

link 级再落一份「上次成功同步」：

```text
sync_last_ok_unix   只有「事件 + 对账 + 巡检」完整跑完的一轮才更新
```

失败/断网/服务端未就绪的轮次**不更新**它 —— 这样「离线 2 小时」回来时，“太久没同步”
会自然触发一次全量；离线期间的轮次不会把时间拨到现在，把问题掩盖掉。

---

## 4. 常规轮转没有被删掉

全量同步只在上述四种状态之一下发生。**完成之后**立刻回到原来的轮转窗口/时间预算：

```text
每轮预算 = 间隔 × 50%，游标落在 reconcile_scan_cursor:<mountpoint>
```

也就是说，改的是「首次/追赶」这一段，日常稳态的删除延迟、单轮耗时上限语义保持不变。

## 5. 可见性

* `SyncInfo` 新增 `full_sync_pending`（任一挂载点在等全量）与
  `last_sync_ok_age_secs`（距上次完整跑完一轮的秒数）；
* `qxync status` / `qxync sync` 打印「全量同步: 进行中」与「上次成功: N 前」；
* GUI「同步摘要」显示「全量同步：进行中（首次 / 太久没同步）」与「上次成功同步」；
* 每轮的「说明」文字带进度与原因，例如：

```text
全量同步完成：首次同步：这个挂载点还没有完整列举过；本轮列了 5362 个目录
（其中新发现 0 个），登记 baseline 30561 项；之后按常规间隔轮询
```

```text
全量同步未完成：距上次成功同步 2 小时 0 分钟……；本轮列了 982/1717 个目录
（本轮时间预算 90s 用完），下轮继续
```

## 6. 环境变量（排障 / 调参）

| 变量 | 默认 | 含义 |
|---|---|---|
| `QXNYC_FULL_SYNC` | `1` | `0` = 关掉整套首次/超时全量（退回 v0.7.8 之前的纯轮转，做对比排障用） |
| `QXNYC_FULL_SYNC_AFTER_SECS` | `3600` | 「太久没同步」阈值；`0` = 不因超时触发（首次/未完成仍然触发） |
| `QXNYC_FULL_SCAN_BUDGET_SECS` | `1800` | 全量列举单轮预算；`0` = 不限 |
| `QXNYC_SCAN_BUDGET_SECS` | 间隔 × 0.5 | 常规轮转的单轮预算（原逻辑，未变） |

## 7. 真机实测（2026-10-21，`qnap.kdajv.com:9834`，只读）

`full_scan_real_nas_bootstrap_progress`（`#[ignore]`，90s 预算）：

```text
列目录 982（新发现 1716）、baseline 6358 条、中止=false、错误 []
notes: 全量同步未完成：首次同步……本轮列了 982/1717 个目录（本轮时间预算 90s 用完），下轮继续
```

* 速率 ≈ **10.9 目录/秒（92ms/目录）**；
* 该账号实测 5362 个目录 → 一轮全量约 **8~9 分钟**（预算 1800s 内）；
* BFS 在真实目录树上确实「顺着新发现的子目录继续列」，不是每层等一轮。

## 9. 明确没做

* **不下载文件内容**：全量只同步「目录树 + 元数据」，内容仍按需水合（space_saving 语义）。
  想强制下载全部内容，应走缓存/脱水的独立策略，而不是把首次同步变成下载队列。
* **不检测服务端事件日志的保留窗口**：`qbox_get_sync_log` 在真机恒 `-17`，没有可靠的
  「日志被截断」信号；「太久没同步」用本地时间判断，属于保守近似（多扫一次不会丢数据）。
* **不改常规轮转的删除保护语义**：全量完成发生在删除判定之前，熔断仍按原阈值整批挡住。
