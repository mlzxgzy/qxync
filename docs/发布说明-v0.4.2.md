# qxync v0.4.2 —— 连着保存两次不再凭空冒出冲突副本，顺便把保存提速

**中文** · [English](#english)

[![License](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](https://github.com/mlzxgzy/qxync/blob/master/LICENSE-MIT)

**这一版没有破坏性变更**：配置、任务文件、缓存目录布局、命令行参数都不需要改。
升级方式就是换二进制 + 重启 daemon。唯一的**新增**是一个可选环境变量
`QXYNC_HYDRATE_FANOUT`，不设就用默认值（并发取块 8），行为与上一版一致、只是更快。

## 一句话

「一个文件删一行保存一次，再马上删一行保存一次，凭什么给我冲突副本」—— 这个 bug
有，而且比看上去更必修：它不是偶发，**只要两次保存间隔短于一轮同步轮询（默认 30s）就会中**。

原因也不是「两次保存该合并」，而是**同步基线漏推进一步**。同一处改动还顺带把
「一次保存」的开销从「随文件大小线性增长」压到约 1/8。

## 冲突副本的真正原因：baseline 漏了一步

qxync 靠**三向比较**判断谁改了什么：`本地 vs 同步基线（baseline）vs NAS 远端`。

`baseline` 记的是「上次同步成功时**远端**的签名」（大小 + 修改时间）。这里的 bug 是：
**只有同步引擎在一轮轮询里观察到远端之后才会推进它**。而我们自己把文件传上去之后，
成功回调**只清了「本地有改动」这个标记，没动 baseline**。

于是从「上传完成」到「下一轮轮询」之间，有一个**最长 30 秒**的窗口，窗口里三方长这样：

```
本地   == 远端 == 新版本     （传输成功，两边一致）
baseline == 老版本            （没人推进它）
```

下一轮轮询一看：「远端变了」+「本地没标脏」，按理说应该是「本地落后了，刷新一下就完事」。
但 `decide` 还要多问一句「本地是不是和 baseline 不一样」—— 而本地确实和 baseline 不一样
（它就是新版本），于是判定为 **双方都改 → 冲突副本**。

所以：第二次保存的**增量**被误认成了「对方也改过」。实测的决策表输出（`base=(100,1000)`，
第一次传上去的是 `(90,2000)`）：

```
本地标脏、基线未推      -> UploadLocal   （正常上传）
上传成功后、本地已清脏  -> Conflict      ← 就是这一格
第二次保存              -> Conflict
```

**修法**：上传成功的那一刻就把 baseline 推进到刚写上去的那个签名。这个窗口就不存在了，
两次保存各自就是各自的增量。

**真正的双方都改仍然照常判冲突** —— 三向比较的决策表一行都没动（`decision_table` 测试原样通过）。
这个版本只消掉「自己跟自己打架」这种假冲突。

## 顺带修掉一个反向的坑

上面那个修复自己也有个坑，一并修了。

一轮轮询的流程是「**克隆一份 baseline 快照** → 跑很久的网络 IO → 最后落盘」。
落盘时原本是**整份盖回**这份开轮询时的旧快照 —— 而在这期间，上传成功回调刚推进上去的
签名会被**抹掉**，等于把修复自己撤销了。

现在落盘改为**合并**：只接受比内存里更新的条目（修改时间更大者为新）；时间相同时保留
内存里那份（秒级粒度下「同一秒内连改两次」很常见，凭什么认定旧快照更权威？）。

## 保存慢：取块是一段一段串行取的

先说被**排除**的一个方向：不是数据库。每保存 4 KB 就要 fsync 一次的
`SQLite synchronous=FULL`？实测**每次提交 0.008 ms**，压根不是瓶颈。

真正的原因是 FUSE 写路径：写之前必须把整个文件缺的块都取到本地（read-modify-write
的硬要求 —— 否则未取回的区间是 0，整文件上传会把 NAS 上的内容清零）。而这些块
**是一块接一块串行取的**（128 KiB 一块）：

| 文件大小 | 块数 | 串行开销（按 15ms 往返算） |
|---|---|---|
| 1 MiB | 8 | ~120 ms |
| 4 MiB | 32 | ~480 ms |

也就是说**一次保存的等待时间随文件大小线性增长**。这些块彼此没有任何依赖，
现在改为**按扇出并发取**（默认 8 路），墙钟时间从 `O(块数 × RTT)` 降到
`O(⌈块数/8⌉ × RTT)`，1 MB 约 **8 倍**提速。

正确性不受影响：每一块各自有去重锁（同一个块不会被并发下载两次），而且
**内容先于位图落盘**，所以不会出现「位图说这块有了、实际内容却是半截」。

并发度用 `QXYNC_HYDRATE_FANOUT` 调（1–64，默认 8，**设成 1 就退回串行**，作为
「并发取块出问题」时的逃生阀）。默认取 8 是按家用 NAS 保守定的：再高容易触发
服务端限流 / 排队，反而更慢。

顺带一提，这一项还**缩小了上面那个冲突窗口** —— 取块越慢，窗口越宽。

## 还有一个小竞态

上传完成后统计字节数时，读的是**那一刻磁盘上**的文件大小。两次保存挨得近时，
上传作业可能早就被取走了，这时读到的是**下一个版本**的大小 —— 而这个数字正是用来
推进 baseline 的，等于把 baseline 停在一个**远端并不拥有**的签名上。

现在回调拿到的是**这一次真正发出去的字节数**；另外，如果上传期间本地又变了，
就**不**推进 baseline，等下一版落地时再推一次。

## 验证情况

- 全量 `cargo test --workspace`：**199 passed / 0 failed**（新增 10 条，含一条**对照组**
  —— 证明那条假冲突路径确实存在、且被本版本消掉了）。
- **未在真机验证**：并发取块涉及真实网络行为，仓库里的真机测试
  （`m2c_engine_refresh_conflict_delete_protection`）默认 `#[ignore]`。
  建议接 NAS 实测一次保存延迟，并留意有没有触发服务端限流。

## English

# qxync v0.4.2 — Two saves in a row no longer spawn a bogus conflict copy, and saving is faster

**中文** · [English](#english)

No breaking changes: configuration, task files, cache layout and CLI arguments are all
unchanged. Upgrading means replacing the binaries and restarting the daemon. The only
**addition** is an optional `QXYNC_HYDRATE_FANOUT` environment variable; unset it and
behaviour matches the previous release — just faster.

## TL;DR

"I delete a line, save, then delete another line and save again — why am I getting a
conflict file?" That was a real bug, and more than a cosmetic one: it was not
intermittent, it triggered **whenever two saves were closer together than one sync poll
(30s by default)**.

The cause was not "two saves should have been merged". It was that the **sync baseline
was never advanced**. The same change also cuts the cost of a save from growing linearly
with file size to roughly 1/8 of it.

## The real cause: the baseline missed a step

qxync decides who changed what by comparing **local vs. the sync baseline vs. the NAS
remote**. The baseline records the **remote** signature (size + mtime) as of the last
successful sync. The bug: **only the sync engine advanced it, and only when a poll round
observed the remote**. After we uploaded a file ourselves, the success callback **cleared
the "local has changes" flag but did not touch the baseline**.

So between "upload finished" and "next poll" there was a window of up to **30 seconds**:

```
local  == remote == the new version   (upload succeeded, both sides agree)
baseline == the old version           (nobody advanced it)
```

The next poll sees "remote changed" + "local not dirty", which should mean "local is just
behind, refresh it". But `decide` also asks "is local different from the baseline?" — and
it is (it *is* the new version), so it concluded **both sides changed → conflict copy**.

In other words, the second save's **increment** was mistaken for "the other side also
changed". Observed decision-table output (`base=(100,1000)`, the first upload lands as
`(90,2000)`):

```
local dirty, baseline stale   -> UploadLocal   (normal upload)
after upload, local cleared   -> Conflict      ← this cell
second save                   -> Conflict
```

**Fix**: the moment an upload succeeds, advance the baseline to the signature just
written. The window no longer exists, and each save is its own increment.

**Genuine simultaneous edits are still detected as conflicts** — the decision table itself
is untouched (`decision_table` passes unchanged). This release only removes the
false "fighting with myself" conflict.

## A reverse trap, fixed together

The fix above had a trap of its own, also fixed here.

A poll round works like: **clone a baseline snapshot → run long network IO → persist it
back**. Persisting used to write that **stale snapshot back wholesale**, which **wiped**
signatures the upload callback had advanced in the meantime — undoing the very fix above.

Persistence now **merges**: only entries strictly newer than the in-memory ones are
accepted (larger mtime wins); on an mtime tie the in-memory entry is kept (two edits
within the same epoch second are common, so the old snapshot is not automatically
authoritative).

## Slow saves: chunks were fetched one at a time

First, the hypothesis we **ruled out**: it is not the database. `SQLite synchronous=FULL`,
which fsyncs on every 4 KB write? Measured at **0.008 ms per commit** — not the
bottleneck at all.

The real cause is in the FUSE write path: before writing, every missing chunk of the file
must be fetched locally (a hard requirement of read-modify-write — otherwise unfetched
ranges read as 0 and the full-file upload zeroes the NAS content). And those chunks were
fetched **strictly serially**, 128 KiB at a time:

| File size | Chunks | Serial cost (@15 ms RTT) |
|---|---|---|
| 1 MiB | 8 | ~120 ms |
| 4 MiB | 32 | ~480 ms |

In other words, **the wait for one save grew linearly with file size**. The chunks are
completely independent, so they are now fetched with a **fan-out** (8 by default),
turning `O(chunks × RTT)` into `O(⌈chunks/8⌉ × RTT)` — roughly **8×** for 1 MB.

Correctness is unchanged: each chunk has its own dedup lock (the same chunk is never
downloaded twice concurrently) and **content is persisted before the bitmap**, so a chunk
can never be marked ready while its content is only half written.

Tune with `QXYNC_HYDRATE_FANOUT` (1–64, default 8; **set 1 to go back to serial** as an
escape hatch if concurrent fetching ever misbehaves). 8 is a conservative default for a
home NAS — higher tends to trigger server-side throttling/queueing and end up slower.

This also **narrows the conflict window** above — the slower the fetch, the wider the window.

## One more small race

When computing the byte count after an upload, the code read the file size **on disk at
that moment**. With two rapid saves the job may already have been dequeued, so it read
the **next** version's size — and that number is what advances the baseline, parking it
on a signature the **remote does not have**.

The callback now receives the byte count **actually sent**, and if the local file changed
again while the upload was in flight, the baseline is deliberately **not** advanced; the
next version advances it when it lands.

## Verification

- Full `cargo test --workspace`: **199 passed / 0 failed** (10 new, including a
  **control group** that proves the false-conflict path existed and is gone).
- **Not verified on real hardware**: concurrent chunk fetching involves real network
  behaviour, and the repository's hardware test
  (`m2c_engine_refresh_conflict_delete_protection`) is `#[ignore]`d by default. Worth
  measuring one save against a real NAS, and watching for server-side throttling.
