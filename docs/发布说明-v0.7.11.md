# v0.7.11 —— 休眠唤醒后守护进程不再自杀

> 发布日期：2026-10-26
> 上一版：[v0.7.10](发布说明-v0.7.10.md)（回放顺序与远端副本证据 + 目录列表叠加 + 回放等待语义）
>
> 这一版只修一件事，但它是**两层错误互相掩盖**：
>
> 1. **「笔记本盒盖休眠一段时间再开盖，服务就自己停了，还得手动启动」**（M37）；
> 2. 更要命的是：进程死得无声无息，而 systemd 把这种死法当成「干净退出」——
>    连「崩溃自动重启」这条兜底都失效了。

## 一句话

```text
升级 + 重启 daemon 后：
  → 盒盖休眠再开盖，qxyncd 不再消失：FUSE 挂载点不断、上传队列不丢
  → 就算它真的因为别的原因死了，systemd 也会在 5 秒内拉起来（不再「手动启动」）
  → 「已有 daemon 占着 socket」不会变成每 5 秒一轮的重启风暴（退出码 3 拦住）
```

## 一、现象（真机 2026-10-26）

同一台笔记本的一次开机里：

| 时刻（CST） | 事件 |
|---|---|
| 12:06:32 | user 单元拉起 `qxyncd`（PID 1025） |
| 15:54:41 → 15:57:08 | 盒盖休眠（s2idle）**2 分 20 秒** |
| **15:57:28** | 进程死亡 —— 恰好是**唤醒后第 20 秒**（唤醒后第一轮轮询/保活第一次用网络） |
| 16:38 → 19:59 | 又两次休眠/唤醒；守护早已不在，什么都不会发生 |
| 20:02:41 | 用户手动 `qxyncd` 拉起一个（PID 368191）—— 这就是「还得手动启动」 |

`systemctl --user status` 当时的样子：

```text
Active: inactive (dead) since Mon 2026-10-26 15:57:28 CST
Process: 1025 ExecStart=/usr/bin/qxyncd --foreground (code=killed, signal=PIPE)
```

不是 panic（那是 `code=exited`），不是 OOM（那是 `signal=KILL`），也不是正常退出。
守护自己的文件日志**断在死前约 3 分钟**（停在 `tracing_appender::non_blocking` 的缓冲区里，
没来得及落盘）—— 这正是「被信号瞬杀、没机会跑任何清理」的指纹：正常退出与 panic 展开
都会让 `WorkerGuard` drop 并 flush。

## 二、第一层：SIGPIPE 把整个进程杀掉

### 根因

`crates/qxync-daemon/src/main.rs` 的 `main` 从 M1.5 起照搬了 CLI 的一行：

```rust
unsafe { libc::signal(libc::SIGPIPE, libc::SIG_DFL) };
```

这行**对 CLI 是对的**（`qxync ls | head` 的 stdout 被提前关掉，进程该按 shell 惯例安静地死），
但 daemon 是**长驻多连接**进程：

| daemon 里的写端 | 休眠唤醒后发生了什么 |
|---|---|
| NAS HTTPS 长连接 / 会话保活（每 120s） | 连接在对端早已失效（TCP RST / NAT 超时），第一次 `write()` 就 EPIPE |
| 变更轮询（每 30s） | 唤醒后立刻到期的定时器正好触发 |
| 本地 IPC socket（CLI / GUI 客户端） | 客户端断开后写它就 EPIPE |
| journald stderr 管道 / FUSE 会话 | 极端情况下也会 |

Rust 运行时默认把 SIGPIPE 设成 `SIG_IGN`，所以这些写入本来只会**返回 `EPIPE` 错误**，
由各调用点的错误处理消化（重连 / 记一笔离线）。被改成 `SIG_DFL` 之后，
**内核在第一次这样的写入时直接 SIGPIPE 杀掉整个进程**。

### 现在的行为

daemon 改为**忽略 SIGPIPE**（`SIG_IGN`，即 Rust 运行时默认处置）：写坏连接退化成普通的
`EPIPE`/`ECONNRESET`，由调用点按「这条连接坏了 → 重连」消化，进程继续活着。
CLI 侧保持 `SIG_DFL` 不变。新增回归测试
[`crates/qxync-daemon/tests/sigpipe_survival.rs`](../crates/qxync-daemon/tests/sigpipe_survival.rs)：
隔离 XDG 目录起一个空转待命的 `qxyncd` → `kill(SIGPIPE)` → 断言**进程仍活着、IPC 仍应答**。

★ 顺手修掉的第二条通道：`qxync get <大文件>` 跑到一半 Ctrl-C，旧版本会因为 IPC 写端
断开把 daemon 一起杀掉；现在只会在日志里留一条写失败，`qxync status` 照常。

## 三、第二层：systemd 认为「被 SIGPIPE 杀掉」= 成功退出

```text
$ systemctl --user show qxyncd.service -p Restart -p Result -p NRestarts
Restart=on-failure
Result=success          ← 信号死亡，却记成 success
NRestarts=0             ← 一次都没重启过
```

这是 systemd 的既定语义，不是日志异常：`systemd.service(5)` 规定**除 `Type=oneshot` 外，
`SIGHUP` / `SIGINT` / `SIGTERM` / `SIGPIPE` 这 4 个信号被杀都算「干净退出」**。于是：

* `Result=success` ⇒ `Restart=on-failure` 只对「失败」生效，**永远轮不到重启**；
* 用户看到的就是 `inactive (dead)` +「得手动启动」。

修复（`packaging/systemd/qxyncd.service`、`qxyncd@.service`）：

```ini
[Unit]
StartLimitIntervalSec=0        # 重启永不放弃（默认 5 次/10s 后 systemd 就躺平）

[Service]
Restart=always                 # ★ 唯一能覆盖 SIGPIPE/SIGTERM 这类「clean exit」的策略
RestartSec=5
RestartMode=direct             # 自动重启不再白等 SIGTERM「挂载守护模式」那 30s
RestartPreventExitStatus=3     # 「已有 daemon 占着 socket」不是失败，别重试
```

> ⚠ **行为变化**：`qxync daemon stop`（IPC，干净退出 0）与 GUI 的「停止」也会被拉回来
> —— 看起来像「没停掉」。装了单元之后**只用** `systemctl --user stop|start|restart`,
> `systemctl --user reload`（= SIGHUP，重载同步引擎、不碰挂载点，推荐）来管它。
>
> ⚠ `RestartMode=direct` 只作用于**自动重启**：显式 `systemctl restart|stop` 仍走
> 「SIGTERM → 保留挂载不退 → 等满 30s → SIGKILL」这条 M15/T6 的老路径（挂载点靠
> `auto_unmount` + 启动僵尸清理兜底）。
>
> ⚠ `StartLimitIntervalSec=0` 的代价：除退出码 3 外，任何**启动期**失败（配置坏、
> socket 无权限…）都会每 5 秒重试一次并一直刷日志。对「同步客户端」来说「可能吵」
> 远好过「静默躺平」，这是刻意取舍；想收窄得先做 §已知限制里的 P1 项。

## 四、退出码 3：「已有 daemon 占着 socket」不再重启风暴

`Restart=always` + 不限次数会带来一个新问题：如果你手动起过一个**不受 systemd 管**的
daemon（本次事故里正是这样），单元启动时会因为「socket 已被占用」失败 → systemd 每 5 秒
重试一次，永远刷屏（现场在 20:08 抓到过每 3 秒一轮的循环）。

所以 `bind_socket` 发现「另一个 daemon 已占着 socket」时改为返回专用错误
`daemon::AlreadyRunning`，`main` 把它映射成**退出码 3**，单元用
`RestartPreventExitStatus=3` 拦住。日志文案不变（`daemon 已在运行（socket …）`）。

## 六、升级

```bash
# 1) 装新二进制（SIGPIPE 修复在这一步生效）
sudo install -m755 target/release/qxync target/release/qxyncd /usr/bin/

# 2) 装单元（Restart=always / StartLimitIntervalSec=0 / RestartPreventExitStatus=3）
sudo install -m644 packaging/systemd/qxyncd.service  /usr/lib/systemd/user/qxyncd.service
sudo install -m644 packaging/systemd/qxyncd@.service /usr/lib/systemd/user/qxyncd@.service
systemctl --user daemon-reload

# 3) 收掉「不受 systemd 管」的那个 daemon，再交给 systemd
qxync daemon stop            # 如果当前 daemon 是 CLI/GUI 起的
systemctl --user restart qxyncd
systemctl --user status qxyncd
```

不想覆盖 `/usr/lib` 里的单元时，可以用 **user drop-in**（无需 root）：

```bash
mkdir -p ~/.config/systemd/user/qxyncd.service.d
cat > ~/.config/systemd/user/qxyncd.service.d/50-m37-always-restart.conf <<'EOF'
[Unit]
StartLimitIntervalSec=0

[Service]
Restart=always
RestartSec=5
RestartMode=direct
RestartPreventExitStatus=3
EOF
systemctl --user daemon-reload && systemctl --user restart qxyncd
```

★ 三者只能选一个：`qxync daemon start/stop`、GUI 的「启动/停止」、systemd。
装完单元就统一交给 `systemctl --user`。

装完可以这样验收（需要真的盒盖）：

1. `systemctl --user status qxyncd` 记下 `Main PID`；
2. 盒盖休眠 ≥ 3 分钟再开盖；
3. 期望 `Main PID` **不变**；`journalctl --user -u qxyncd -b | tail` 在唤醒后出现新一轮
   同步轮询；`ls ~/qxync/default/qsync` 正常（挂载没断）。
4. 若还是死了：状态里应能看到最近一次自动重启时间与 `NRestarts`，而不是
   `inactive (dead)` —— 至少不会再退回「必须手动 start」。

## 已知限制（如实记）

* 真机「盒盖 → 唤醒」验收需要人和真 NAS，**本版发布前没做**；自动化只钉住「直接发
  SIGPIPE 不死」与「退出码 3」，没有覆盖「唤醒后写坏连接 → EPIPE → 重连」的完整链路
  （需要真会话 + 真休眠）。
* `cargo clippy` 在发版环境未安装，未运行。
* 显式 `systemctl restart/stop` 仍要等 30s + SIGKILL（M15/T6 的「SIGTERM 保留挂载」
  副作用，`RestartMode=direct` 救不了）——「想重启同步」请用 `systemctl --user reload`。
* 同一轮只读审计列出、但**本版没做**的加固（都不是本次事故根因）：
  systemd 下 SIGTERM 快退；`State.client` 持锁跨网络 await 可能导致「活着但卡住」；
  上传 / 删除 worker 无 `catch_unwind` 与监督；5 个后台任务 handle 忽略 Err；
  运行期不检测 FUSE 会话死亡；无 `logind PrepareForSleep` 监听与 `sd_notify` watchdog。
  清单与建议见 M37 §6。
