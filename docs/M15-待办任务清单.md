### 0.3 明确不做（已评估，不要重新捡回来）

| 曾经的提议 | 为什么不做 |
| --- | --- |
| **拆分 FUSE 进程与同步进程（双进程 + RPC）** | 需 16 个 `LocalView` 方法跨进程 RPC（`lib.rs:645-694`），且 `reconcile_view` 每 30s 全量拉`nodes()`（`daemon/sync.rs:637`），10 万节点时性能不可接受。**本文 §2 用 200 行拿到 90% 收益**，暂不需要 |
| `CF_PLACEHOLDER_STATE_*` 标志位编码 | Windows 需要把状态编码进 NTFS 属性供 Explorer 独立读取；FUSE 下 `getattr` 由本进程应答，**位图推导（`lib.rs:292-300`）是对的**，改成标志位是倒退 |
| reparse point 兼容层 / 桌面桥 / UWP | Windows 特有 |
| oplock / 租约 / 硬链接策略 | FUSE 已有 per-node `op_lock`（`lib.rs:229`），冲突率低；硬链接 + 占位符 identity 语义复杂 |
| 内核态方案 | Linux FUSE **必须**用户态持 fd，无捷径 |
| `delta.rs` 增量上传接线 | 完整 librsync 实现已在 `delta.rs`，但真机实测 `versioning_support=0`（`client/lib.rs:833`），服务端不支持 |
| 备份任务 / 版本还原 | 官方客户端也没有的价值，优先级低 |
| 上传断点续传 | ✅ **已证伪**（2026-10-04）：服务端**实现了**分片（5 个 func，参数表完整），但只服务 Qbox 空间（`/remote:` 前缀），普通家目录路径过不去（status 12/46）→ 详见 §2 T4。T2 已把整文件读内存改成流式，重试退避是现有兜底 |

**★ 真机实测发现的硬约束：服务端不接受 chunked 编码**

第一版实现用 `Part::stream`（纯流式、无`Content-Length`），真机直接被拒：

```
HTTP 411 Length Required   （QNAP 回的是 HTML 错误页，不是 JSON）
```

排查这条时 `parse_upload_result` 的报错只有「非 JSON」毫无线索，已改成带上
HTTP 响应原文前200B（`client/src/lib.rs`）—— 以后遇到类似被拒能直接看到原因。

### T3：内容校验和（xxhash + `--verify`） ✅ 已完成

**优先级**：最高（数据正确性）

**现状问题**

全 workspace **无 `etag` / `checksum` / `sha256` / `md5`**。下载只校验长度：

```rust
// crates/qxync-fuse/src/lib.rs:2751
if data.len() != want { return Err(...) }   // 只查长度
```

网络截断/改写、稀疏空洞被当真数据、位图与内容写序颠倒（`lib.rs:114-115` 已规避一半）——
这些**长度都对、内容错了**，用户几个月后才发现。

`delta.rs:381` 有 `md4` 实现，但只服务于未接线的 delta 路径。

**★ 与原文不一致的地方（实测发现，已按实测改）**

原文第 1 条说「`per_chunk_xxhash(8 × nchunks)` 追加进 `.qxstate` 文件头」。**照做会写爆盘**：

- 10 GB 文件 / 128 KiB = **81920 个区间**，`8 × nchunks` = **640 KB**；
- 而 `persist_chunk_state` 是**每个区间就绪就全量重写一次**（M9 的既有行为）；
- 于是水合一遍 10 GB 要写 640 KB × 81920 ≈ **52 GB** —— 比数据本身大 5 倍。

所以**拆成两个文件**（语义等价，写放大从 O(n²) 降到 O(n)）：

| 文件 | 内容 | 写入方式 |
|---|---|---|
| `<cache>.qxstate` | v2 头 + 位图 | 全量重写（10 GB 文件也只 10 KB，随便重写） |
| `<cache>.qxsum` | 定长 `8 × nchunks` 的 per-chunk xxhash64 | **定点 `pwrite` 8 字节**，写一个区间改一格 |

`.qxsum` 与 `.qxstate` 同生共死（`remove_cache_files` 一起删）。

**改动点（实际）**

1. **`.qxstate` 升 v2**（`lib.rs`，`QXSTATE2`）—— 头追加 `file_id(16)`（T9 用，当前恒为全零）
   与 `whole_xxhash(8)`。`file_id` 先占位是为了 T9 落地时**不用再升一次版**。
2. **per-chunk 校验和**落在新增的 `.qxsum`，写入点三处：
   - `ensure_chunk`：数据已在内存里，直接 `xxh64(&data)`，零额外 IO；
   - `mark_written_chunks`：本地写也要算（否则 verify 会把「用户自己写的文件」全判成损坏），
     一次 write 覆盖多个区间时合成**一次 `pwrite` 批次**（`sum_store_many`）；
   - `install_refreshed`：整份刷新出来的内容一次算齐。
3. **认领时全量校验**：`cache_file_for` 保留原有「签名不符即整份作废」，**之后**逐区间核
   `xxhash64`；核不过的区间清成未就绪，让 `read` 退回按需水合 —— **绝不返回错误内容**。
   `.qxsum` 缺失的区间一律当「不可信」（没有基准可比就不许声称内容正确）。
4. **`qxync verify [--path <dir>] [--repair] [--json]`** + **GUI 一键校验**
   （诊断 → 同步/缓存卡片，两个按钮：`校验` / `校验并修复`）。

**为什么用 xxhash 而非 sha256**：快一个数量级，而这里要挡的是**意外损坏**
（掉电、位翻转、写序颠倒、网络截断改写），不是恶意篡改 —— 攻击者能同时改内容和
校验和的话，本来就能改 `sync.db`。真要防篡改得靠服务端签名，那是另一件事。

### T4：上传分片续传 ❌ 已验证不可行，任务取消（2026-10-04）

**优先级**：低 → **结论：不做**

**原文前提是错的**。原文写「前置：`upload.php` 是否支持分片索引。若不支持，

**「服务端不支持分片」这件事从来没被验证过**，只是一直被当成事实。2026-10-04 验了。

**★ 验证方法：静态分析服务端二进制 + 真机实测（两条独立证据）**

静态分析对象是 `QsyncServer_5.0.0.8_20260916_x86_hal.qpkg` 里的
`cgi/qsyncsrv.cgi`（**是 ELF x86-64 二进制，不是 PHP** ——
这点曾长期被误判，README 里「`qsyncsrv.cgi?func=download` 恒 status:20」
的结论其实是对着二进制猜的）。`qpkg` 剥法：shell 头 + `tar.gz`（偏移 1827）
→ `QsyncServer.tgz` → `cgi/`。

`strings` + `objdump -d` 读出的分片上传实现：

| func | 处理函数 | 必需参数 | 说明 |
| --- | --- | --- | --- |
| `start_chunked_upload` | `0x6973c` | `ssid`、`upload_root_dir` | 申请 `upload_id` |
| `get_chunked_upload_status` | `0x6cae8` | `upload_id`、`upload_root_dir` | 查已收分片 |

另有 5 个 `upload.c` 内部符号：`op_chunked_upload`（读 `offset` / `filesize` /

`upload_id` 约束是**长度 `[2,32]` + `Is_Alphabet_Num`**（`sub rax,0x2; cmp rax,0x1e; jbe`），

—— 即 **`upload_id` 是客户端自选、服务端只校验形态的令牌**。

**所以「服务端完全不支持分片」是错的 —— 它实现得很完整。** 真正的障碍在下一条。

**★ 真正的障碍：分片通道只服务 Qbox 空间，与 `upload.php` 的路径空间不通**

真机实测（QTS 5.2.9 / Qsync QPKG build 20260723 / 账号 test1），
探针 `xtask/probe/upload_chunk_probe.py`：

| `upload_root_dir` | handler status |
| --- | --- |
| `/home/qxync-t4probe`（**存在**的普通目录） | **12** |
| `/home/qxync-t4probe/`、`/home`、`/` | **12** |
| `/remote:/home/qxync-t4probe` | **46** |
| `/remote:home`、`/remote:home@1000` | **46** |

`start_chunked_upload` 走 `0x6927c` → `0x9d02a`（realpath + UID 校验，
内部认 `/remote:` 前缀与 `@` 分隔的 `name@uid`），
**普通家目录路径过不去，拿不到 `upload_id`**。
而 `func=upload.php` 的 `dest_path` 用的恰恰是普通绝对路径 ——
**两套路径空间不通**。

`handler_status()`（取最后一个非 0 值）。这个坑在别的 func 上一样会踩。

### T6：SIGTERM 保留挂载（同步可停、挂载留活） ✅ 已完成（2026-10-04）

**优先级**：高 → **已实现**

**现状问题**

```rust
// crates/qxync-daemon/src/daemon.rs:571-604（改前）
tokio::select! {
    _ = shutdown_rx.recv() => break,   // 收到 shutdown 请求
    _ = tokio::signal::ctrl_c()  => break,
    _ = wait_sigterm(&mut sigterm) => break,
}
...
let n = shutdown_all_mounts(&state).await;   // ← 无条件卸载全部
```

`systemctl restart` 和 `systemctl stop` 走同一条路径。但用户重启的意图是
「继续用」，不是「关掉」。

#### ★★ 原文改动点 1 的方案在 systemd 下不成立 —— 换成「按信号来源分派」

原文要加 `Options.keep_mount_on_exit`，并让 `systemctl restart` 传 `true`、
`qxync daemon stop` 传 `false`。**这条路走不通**，原因是纯机制性的：

| 原文设想的传参通道 | 实际情况 |
| --- | --- |
| `qxync daemon stop` 传 `false` | 它走 **IPC**（`Request::Shutdown`）让已在跑的进程自己退出，**不 spawn 新进程**，新进程根本没机会传 `Options` |
| `systemctl restart` 传 `true` | restart 的 stop 阶段与 stop 发的是**同一个 SIGTERM**，单元文件里没有任何「我现在是 restart」的上下文可读 |

也就是说**唯一可靠的判据是「信号 / IPC 的来源」**，不是参数。于是改成：

```rust
// crates/qxync-daemon/src/daemon.rs:114
enum ExitReason { IpcShutdown, CtrlC, Sigterm }
impl ExitReason {
    fn should_unmount(self) -> bool { !matches!(self, ExitReason::Sigterm) }
}
```

主循环 `tokio::select!` 每个分支 `break` 时带上原因，循环**之后**才决定行为：

| 退出原因 | 来源 | 行为 |
| --- | --- | --- |
| `IpcShutdown` | `qxync daemon stop`（IPC） | **真正卸载**全部挂载 + 删 socket/pid |
| `CtrlC` | SIGINT（前台 Ctrl-C） | **真正卸载**全部挂载 |
| `Sigterm` | SIGTERM（`systemctl stop/restart`） | **保留挂载** → 停同步 → 转挂载守护 |

这一版比原文更保守也更正确：IPC stop 的语义（用户明确要「关掉」）没有被
任何新参数稀释掉。

#### ★★ 原文改动点 2 的「保留挂载」在 systemd 下救不了 restart —— 如实说明

`hold_mounts()`（`daemon.rs:918`）按原文做了：停同步任务 → `mounts_persist` 写盘
→ **不调 fusermount** → 进程继续存活应答内核里那个还活着的 FUSE 连接。
守护期间的能力按任务书附录 A.3：

| 能力 | 守护期间 |
| --- | --- |
| `ls` / `readdir` / `ls -l` / `getfattr` | 正常（吃内存快照，零网络） |
| 打开**已下载**的文件读内容 | 正常（FUSE 回调在本进程里） |
| 打开**未下载**的文件 | 失败（引擎停了，不再去 NAS 水合） |
| 写文件 | 进上传队列，但 worker 已停 → 队列留着，下次启动再推 |

**但它救不了 `systemctl restart`，这是 systemd 的语义限制，不是 qxync 的缺陷：**
restart 的流程是「stop 旧进程 → **等它退出** → start 新进程」，而守护进程
按设计不会在 SIGTERM 后立刻退出，于是 stop 阶段会一直等到 `TimeoutStopSec`，
然后被 SIGKILL —— 挂载一样断（而且是强杀，比正常卸载更难看）。
所以本模式**不打算、也不试图**活过 systemd 的 stop 阶段。

**systemd 下真正能用的主路径是 SIGHUP**（`systemctl reload qxyncd`）：它不终止
进程，也就没有「等旧进程退出」这一步 → 挂载点一秒都不中断。已加
`ExecReload=/bin/kill -HUP $MAINPID`，并新增 `qxync daemon reload` 走同一条路径
（`crates/qxync-cli/src/main.rs:2442`），两种部署下用户行为一致。
`systemctl restart` 的体验由 T5 兜底：短暂断开后启动自动重挂。

#### 停同步不用 `abort()` —— 用「代次令牌」让任务在循环点自己退

同步引擎 5 个后台任务（poller / 脱水 / 自动释放空间 / journal 落库 / 会话保活）
原先返回 `()`，拿不到 `JoinHandle`。**刻意不用 `JoinHandle::abort()`**：poller 那一轮
`run_sync_once` 正在改 baseline、推冲突决策，从中间劈开等于让同一处改动被判成两次
冲突 —— 那是在制造数据正确性问题，比「重载慢几秒」严重得多。

改成代次令牌（`daemon.rs:150` / `:186`）：

```rust
struct SyncEpoch { tx: tokio::sync::watch::Sender<u64> }
struct EngineGen { rx: tokio::sync::watch::Receiver<u64> }   // Clone
impl EngineGen {
    /// true = 睡满了；false = 被换代唤醒，该退出了
    async fn sleep(&mut self, d: Duration) -> bool { … }
    async fn changed(&mut self) { … }
}
```

`stop_sync_engine`（`daemon.rs:872`）`bump()` 换代 → 各任务的 `select!` 分支立刻
返回 → 在**循环点**干净退出 → `timeout(5s)` 等句柄，等不到就只 WARN 继续
（一个卡在网络 IO 上的任务不该把退出拖住）。`start_sync_engine`（`daemon.rs:821`）
是 5 个任务的唯一汇集处 —— 收在一处是为了 SIGHUP 能**整套**重启，少起一个就是
「重载之后那个功能悄悄不工作了」，而这种故障极难排查。

> ★ 这里踩过一个 `watch` 语义的坑，值得记下来：`EngineGen` 构造时必须
> `borrow_and_update()` 把当前值标记成「已看到」。`reload_sync_engine` 的顺序是
> 「先 bump、再起新」，不标记的话**每个新任务一启动就在第一次 `select!` 立刻退出**，
> 同步静默失效 —— 这是最难查的一类故障。已有单测
> `t6_epoch_bump_retires_old_generation_only` 复现真实顺序盯着这条。

#### 改动点 3：新进程遇到「挂载已被旧进程托管」

`restore_mounts_on_start`（`daemon.rs:3575`）在挂载表检查之后、`create_dir_all`
之前新增：若 `is_mounted(mp)` 为真 ——

* subtype 是 `fuse.qxync` → 打 INFO「已由其他 qxyncd 进程托管，本进程只做同步」，
  跳过挂载；
* subtype 不是 → 打 WARN 跳过（T7 同一条边界：可能是别人的文件系统，**绝不能动**）。

两种情况都**不覆盖 `mounts.json` 的记录**：那个挂载点现在**确实挂着**（只是不是本
进程挂的），抹掉记录等于告诉下一个进程「这里没挂过」，等旧进程一挂它就永远消失了。

同步引擎全是纯 async 任务、一样都不依赖 FUSE 会话（§0.2 已核实），所以「只做
同步」完全能工作。不做 fd 传递（复杂且易错）。

> ★ 顺带发现并修掉一个会静默吃掉挂载点的坑：T5 的 `mounts_persist` 是「从挂载表
> **全量重建**」，而别人托管的挂载点不在本进程挂载表里 —— 一次写盘就把那些记录
> 抹了。新增 `externally_held_records()`（`daemon.rs:2286`）把它们从盘上找回来带上。

#### 挂载守护必须有退出条件

守护进程绝不能变成「收不干净的东西」。`hold_mounts` 的 5 个退出条件：

| 条件 | 语义 |
| --- | --- |
| IPC `Shutdown`（`qxync daemon stop`） | 用户明确要关掉 → 真卸载 |
| 第二次 SIGTERM / SIGINT | 「我说了停」→ 真卸载 |
| 挂载表变空（2s tick 检查） | 没什么可守护的 → 直接退 |
| `--mount-hold-secs` 超时（**默认 0 = 无限**） | 兜底，防「忘了它还活着」 |
| SIGHUP | 不退出 —— **恢复同步引擎**（挂载点本来就在） |

守护期间 IPC 仍然服务（`listener.accept()` 还在循环里）—— `qxync daemon stop`
正是靠它结束守护的，`status` 也要能问，否则用户看到「进程活着但 status 连不上」。

### T7：僵尸挂载清理 ✅ 已完成（2026-10-04）

**优先级**：中 → **已实现**

**现状问题**

真崩溃 / OOM 后，`/mnt/qxync` 留在 `/proc/mounts` 里但 `ENOTCONN`，
用户 `cd` 进去看到 `Transport endpoint is not connected`。

它不只是难看：不清掉它，`restore_mounts_on_start` 会一直撞「路径已挂载」而
恢复失败，于是 T5 的「重启能自愈」这条路整个断掉。

#### 安全边界（四条，少一条就可能误卸别人的挂载）

`cleanup_zombie_mounts()`（`daemon.rs:2539`）只对「自己记过的那几个挂载点」负责：

1. **只遍历 `mounts.json` 记过的挂载点**，绝不扫全盘 —— 我们没有权力决定系统上
   哪些挂载点该存在；
2. **必须已挂载**（`is_mounted`）才有得清；没挂载的直接跳过（那是「记录有过、
   现在没挂」的正常状态）；
3. **必须 subtype 是 `fuse.qxync`**（`is_qxync_mount`）—— 是别的文件系统就只 WARN；
4. **必须写探针失败**（= 内核已经不应答了）才动手 —— 活的挂载点绝不碰。

判定抽成纯函数 `zombie_action(mounted, ours)`（`daemon.rs:2657`），
因为真机上要 `kill -9` 才造得出这些组合，判定逻辑必须能脱离 FUSE 单测。

#### ★ 判定顺序有讲究：subtype 检查排在探针之前

`zombie_action` 先判 `!ours` 再走探针。理由是**探针有副作用** —— 它要往挂载点里
**写一个文件**，对别人的文件系统写一次就是一次不该有的副作用。顺序反过来就等于
「为了确认这是不是我们的，先往人家的目录里写一下」。

#### ★ 探针只认 `ENOTCONN`，且刻意不用 `fs::metadata`

```rust
// crates/qxync-daemon/src/daemon.rs:2651
fn probe_mount_alive(mp: &Path) -> bool {
    match std::fs::File::create(&mp.join(ZOMBIE_PROBE)) {
        Ok(_)  => { let _ = std::fs::remove_file(mp.join(ZOMBIE_PROBE)); true }
        Err(e) if e.raw_os_error() == Some(libc::ENOTCONN) => false,   // 确认僵尸
        Err(_) => true,   // EROFS / EACCES / EIO… 一律当「活的」
    }
}
```

* **不用 `fs::metadata`**：那会命中内核的 dentry/inode 缓存，僵尸挂载点也可能返回
  缓存里的属性，看起来「活着」—— 于是清理永远不触发。写文件必须真走一遍 FUSE 的
  `create` 才拿得到真话。
* **只认 `ENOTCONN`**：`qxync mount` 默认只读，只读挂载写探针必然 `EROFS`。
  拿 `EACCES` 判僵尸会去清一堆健康的只读挂载点。宁可漏清（用户手工
  `fusermount3 -uz` 一下就行），也不能对着健康挂载点动手。
* **探针要删掉**：它会被 `readdir` 看到、会被同步上去。

#### ★ 原文改动点 2 有两处偏差，实现时已修正

| 原文 | 实际 | 原因 |
| --- | --- | --- |
| `.qxync-probe` 用 `metadata().is_err()` 判 ENOTCONN | 改成 `File::create` + **只认 `ENOTCONN`** | `metadata` 命中内核缓存，僵尸也会返回「活着」→ 清理永不触发；`is_err()` 更把 `EROFS`/`EACCES` 一起当成僵尸 |
| 「确认是僵尸 → `fusermount3 -uz`」 | `-uz` 之后**刻意不删 `mounts.json` 记录** | 记录留着，恢复逻辑才能把它重新挂回来。删了记录就变成「清理 = 卸载用户的挂载点」，与意图正好相反 |

另加两条实现细节：

* **`-uz`（lazy）而不是 `-u`**（`lazy_umount`，`daemon.rs:2677`，`fusermount3` 失败
  回退 `fusermount`）：`-u` 遇到「挂载点里还有进程持有 fd」会失败，而那恰恰是
  崩溃现场最常见的形态。
* **失败只 WARN，绝不阻塞 daemon 启动**；`fusermount3` / `fusermount` 都不存在
  也只是 WARN。

执行时机在 `run()`（`daemon.rs:720`）：`restore_tasks` 分支内、
**`restore_mounts_on_start` 之前** —— 顺序反了就白清。

### T8：per-file 同步状态机 + 进度上报 ✅ 已完成（2026-10-04）

**优先级**：中（体验改善）

**现状问题（做之前）**

用户能看到的状态**全是聚合数字**（`daemon.rs` 的 `status`）：

- `SyncInfo`（`ipc.rs:562-584`）：polls / refreshed / conflicts / uploaded / last_error
- `CacheInfo`（`ipc.rs:589`）：used_bytes / total_files / hydrated_files
- `HydroStats`（`ipc.rs:505`）：累计 count / bytes

文件级只有 `SpaceState` 三态（`ipc.rs:948-995`：仅在线 / 本地可用 / 始终可用），
且**只覆盖空间维度，不覆盖同步维度**。用户无法回答「我上周改的文件上传成功了吗」。

唯一错误明细在 `journal` 表（`store.rs:87-101`），而 journal 环形裁剪
（1 万条 / 30 天，`daemon.rs:37-58`）。

> 注：`tasks.rs` 是**任务配置模型**（JSON 持久化），**不是**执行器，别误读。

**★ 实现依据（做完之后的实际落法）**

**1. `in_sync` 是派生值，不是新状态机**

`Node`（`lib.rs:542`）加了两个字段，但**没有引入任何新的持久化表或状态枚举** ——
三个信息源本来就在（`Node.dirty`、`UploadQueue::has_pending`、`decisions` 里
`resolution IS NULL` 的条数），汇总成一个布尔值就够了：

```rust
pub fn combine_in_sync(dirty: bool, pending_upload: bool, conflicts: usize) -> bool {
    !dirty && !pending_upload && conflicts == 0
}
```

**是「与」不是「或」**：`dirty=false` 只说明「没有本地改动」，**不代表 NAS 上就有这份
内容** —— 作业还排在队列里没发出去时（`pending_upload=true`）用户看到的就是「我明明
改完了，为什么 NAS 上还是没有」。冲突同理：内容两边都在，但**谁都没生效**。

**双写策略**（`FsHandle::file_states`）：写入点用 `Node::set_dirty` 保证
`dirty`/`in_sync` 同时变；读取点用 `combine_in_sync` 重算一遍并**顺手写回节点**。
这样即使某个写入点漏了也不会一直错下去。「清脏」**不**直接置 `in_sync=true` ——
队列里可能还排着别的作业，也可能有待裁决冲突，真正的判定在读时。

**2. `conflicts` 必须能区分「没有」与「没查到」**

FUSE 侧不知道 `decisions` 表，所以 `file_states` 把冲突数做成**入参**；
daemon 查表失败时传 `None`，`conflicts_known=false` 如实标注 ——
**不拿「查不到」冒充「没有」**（`daemon.rs` 的 `pending_conflicts_by_path`）。

**3. 进度走回调，不走轮询**

轮询要么得在 daemon 里另开定时器去问 NAS（一次 `list` 换不到字节级进度），
要么得在 FUSE 侧留共享计数器定时读 —— 而 FUSE 会话在挂载线程里，daemon 拿不到它。
回调是唯一能把「刚收好一个分片」在**发生的当场**送到状态表去的办法。

- **下载侧**：`FetchCtx` 加 `progress: Option<ProgressHook>`（`lib.rs:909`），
  `fetch_chunk_bytes` 每收完一个分片（128 KiB）调一次。
  参数是「**本次收到的字节数**」而不是累计值 —— 8 路并发扇出谁先谁后不确定，
  只有把累加收在一个 `AtomicU64` 里（`transfer_meter`）才能保证单调。
- **上传侧**：进度直接从 T2 `client.upload_file` 返回的**真正发出字节数**推进
  （`UploadQueue::note_progress`），`bytes_sent` 用 `min(total)` 夹住 ——
  上传期间用户把文件改大了也只会显示 100%。
- **panic 隔离**：`invoke_progress_hook` 用 `catch_unwind` 包住（复用
  `invoke_success_hook` 的写法，M7 实测踩过「回调 panic 打死 worker」的坑）。
  进度是纯展示，它只能坏它自己。
- **完成即清空**：传输结束（无论成败）就没有在传的作业了，`None` 是唯一诚实的
  表达 —— 停在 96% 会被读成「还有一个作业在跑」。

**4. 两个维度正交，不能压成一个枚举**

`SpaceState`（空间：内容在不在本地）**保持不变**。「仅在线 + 已同步」是完全
正常的状态（没缓存但跟 NAS 一致）。CLI/GUI 组合展示成一句话：

```
同步中 42% · 仅在线
已同步 · 始终可用
未同步（1 个冲突待处理）
```

**5. 唯一偏离原文的地方：`file-states` 子命令是扩展而非新建**

任务书写「clap 定义 + 路由 + `run_file_states` + `print_file_states`」，
但 `qxync file-states` **M8.4 就已经存在**（`main.rs:290`），只是当时只输出
空间三态。T8 是**扩展**它（加同步维度文案与汇总行），没有另建一个重复子命令。
`--json` 的字段名由 `t8_file_states_json_field_names_are_stable` 钉住。

**6. 附录 B.2 的「重试中」没有单独做（刻意）**

附录 B.2 提到「`HYDRATE_TIMEOUT`（60s）可复用来做『重试中』状态上报」。
T8 **没有**加这个状态：进度槽位是 `Option<(u64, u64)>`，要塞「重试中」就得
引入第三种状态 —— 那正是任务书明确禁止的「新状态枚举」。当前做法是：

### T9：稳定文件身份 `file_id` ✅ 已完成（2026-10-04）

**优先级**：中（地基，影响面大）

**现状问题（做之前）**

`Inner.by_remote: HashMap<String, INodeNo>` 是唯一索引，
`baseline` / `uploads` / `deletes` / `pins` / `decisions` **五张表全以 `path` 为主键**。
全 workspace 无 `file_id` / `etag` / 远端 inode。

后果链条：
1. 远端改名 → 路径变 → `baseline` 查不到 → 三向合并（`qxync-core/src/sync.rs` `decide`）
   判成「本地新增 + 远端删除」→ 走 `rename_local` → **平白生成冲突副本**。
2. 远端移动（`dir1/a.txt` → `dir2/a.txt`）同理。
3. 上传队列按 `remote_path` 排队，排队期间远端改名 → 上传写到旧名字，生成幽灵文件。

**约束**：服务端 `DirEntry` **没有** id 字段，只能本地自建。

**★ 实现依据**

1. **身份算法** —— 新增 `qxync-core/src/file_id.rs`：
   - `pub type FileId = [u8; 16]` + `pub const ZERO_FILE_ID`（`:61` / `:64`）。
   - 两个**固定不同** seed（`SEED_A = 0x9E3779B97F4A7C15`、`SEED_B = 0xC2B2AE3D27D4EB4F`）
     各跑一次 `xxhash64`，拼成 16 字节（`:97` `compute_file_id`）。
   - `xxhash64`（seed 0）从 `qxync-fuse` **下沉**到 `qxync-core::file_id::xxh64`（`:76`）——
     seed 必须保持 0，T3 已写进 `.qxsum` 的校验和一个字都不能变。
   - 规范化只去**首尾 ASCII 空白 + 尾部 `/`**（`:86`），**刻意不做大小写折叠、
     不做 Unicode 归一化**（那会把两个不同的文件合并成同一身份）。
   - 算完若 `id == ZERO_FILE_ID` 强制把 `id[15] = 1`，**绝不返回全零**。
2. **`nodes` 表 + schema v3 → v4**（`qxync-core/src/store.rs`）：
   - `SCHEMA_VERSION` 3→4（`:35`），只新增一张表，五张老表**一个字没动**。
   - 接口：`node_upsert`（`:870`）/ `node_by_path`（`:944`）/ `nodes_by_file_id`（`:926`）/
     `node_rename`（`:976`）/ `node_forget`（`:1019`）/ `node_forget_subtree`（`:1031`）。
   - 升级安全性靠「`SCHEMA_SQL` 全是 `CREATE TABLE/INDEX IF NOT EXISTS` 幂等补齐 +
     `init` 里 `pragma_update(user_version)`」，**无需写数据迁移**。
3. **打通 T3 留好的位置**（`.qxstate` **没有再升版**，仍是 v2）：
   - `Node.file_id` 由 `Node::refresh_file_id`（`lib.rs:644`）现算；
     `persist_chunk_state` 落盘时带上真值。
   - `cache_file_for`（`lib.rs:3155`）在 T3 的顺序上**加一档**：签名 → **身份** →
     逐区间核 xxhash。身份对不上就整份不认领（退回按需水合，**绝不返回错误内容**）。
4. **rename 回调迁移**（`lib.rs` `fn rename`）：节点更新处**刻意不重算 `file_id`**，
   块外加一句 `migrate_nodes_row`（`lib.rs:3230` → `store.node_rename`）把 `nodes` 行的
   path 搬过去。失败只 warn，不影响用户操作。
5. **对账按 file_id 判 rename**（`qxync-core/src/sync.rs`）—— T9 的真正价值：
   - `pair_renames(removed, added)`（`:464`）把「远端删除 + 远端新增」按身份配成改名；
   - `apply_renames_to_baseline`（`:532`）把配对落到 baseline，**不产生冲突副本**；
   - **不改编 `decide` 签名** —— 配对是 `decide` 之前的独立纯函数，daemon 侧接线点在
     `crates/qxync-daemon/src/sync.rs` 的 `reconcile_view`（**本任务未改，见「留给后续的」**）。
6. **上传队列落地到新名字**（`qxync-fuse/src/upload.rs`）：
   `UploadJob.file_id`（`:56`）+ `set_name_resolver`（`:291`）+ `retarget_by_identity`（`:297`），
   worker 在**真正发之前**复查落地位置，改了主键就 `persist_delete(旧) + persist_put(新)`。

**★ 三条确定性保证（配对为什么不会错）**

| 保证 | 做法 |
|---|---|
| **同轮** | 只输入本轮对账的候选，不跨轮累积 |
| **互斥** | 一个 `file_id` 最多配一次；同一侧出现重复身份即**整组作废** |
| **确定** | 按「同父目录优先 + `old_path` 字典序」排序，无随机、无并发 |

**保守退化（宁可多报冲突，绝不错配或丢数据）**：`ZERO_FILE_ID`、类型不符、
配不上、**歧义**（同 id 多行）→ 一律不配，退回原有的增删判定。
`nodes_by_file_id` 返回 `Vec` 就是为了让调用方能看见「多行 = 歧义」。

**★ `nodes` 表清理策略**（不留就会出事）

本地删除的文件**必须**从表里去掉，否则下次对账会把老 `file_id` 配到**新文件**身上
（→ 把「新建」误判成「改名」→ 丢掉新文件）。三条清理入口，都挂在已有的删除路径上：

| 入口 | 动作 | 位置 |
|---|---|---|
| 远端删除（`remove_remote`） | `node_forget_subtree`（连子树） | `lib.rs` `LocalView for FsHandle` |
| 本地删除（`remove_entry`，unlink/rmdir） | `node_forget` / `node_forget_subtree` | `lib.rs` |
| 改名（`rename`） | `node_rename`（改 path，**身份不动**） | `lib.rs:3230` |

索引写失败**一律只 warn，不影响数据操作**（索引只决定配对收益，最坏退化成多报冲突）。
另有 `nodes_clear` 供整机级重置。

**★ 与原文不一致的地方**

1. **`nodes` 主键从「`file_id` 单列」改成「`(file_id, path)` 复合键」。**
   原文第 2 条写「`file_id` 主键，`path` 唯一索引」。**照做会静默丢身份**：
   `file_id` 只由 `(mtime, size)` 算出，批量 rsync 出来的一堆小文件 mtime 与 size
   全都相同 → 算出**同一个 id** → 后写行把前行「顶掉」→ 另一个文件身份凭空消失
   → 索引丢数据。改成复合键后「同 id 多行」是**合法状态**，调用方看到多行即当歧义
   （保守不配对）。「一个路径只挂一个身份」仍由 `CREATE UNIQUE INDEX nodes_path` 保证。
   `node_by_file_id` 相应改成 `nodes_by_file_id -> Vec<NodeRow>`。
2. **主算法不含文件名。** 原文第 1 条写「取 `<mtime>-<size>-<规范化名字>` 的哈希」。
   **名字混进 id 会让 `a.txt → b.txt` 改名后 id 变化，配对永远配不上** ——
   正好把 T9 要解决的问题重新造回来。所以：
   - 文件且 `mtime > 0`：`f\0<mtime>\0<size>`（**不含 name/parent**）；
   - 文件且 `mtime <= 0`（退化）：`f\0<name>\0<parent>\0d<size>`；
   - 目录：`d\0<name>\0<parent>`（size 无意义、mtime 会被增删子项改动）。

   名字/目录只在**退化路径**参与 —— 那里本来也拿不到稳定特征，只能靠位置。
3. **`.qxstate` 的 `file_id` 参与的是「身份核对」而不是「签名比对」的一部分。**
   T3 说「把 `file_id` 也纳入签名比对」，实现上放在签名**之后**单独一档，
   以免破坏 T3 已验证的「先比签名、再逐区间核 xxhash」顺序。

## 附录A：为什么「离线可用」在 Linux 上能做到 90%

> 论证基础，来自 `M14` 的调研。**T5/T6/T7 的可行性都建立在这上面**，
> 改动前请先理解这一节，否则容易把方案误判为「不可能」而放弃。

### A.1 先厘清：Windows 那种体验到底是什么

Windows 上的体验不是错觉：`Qsync` 客户端进程退出/崩溃后，
文件资源管理器里那个云盘节点还在，文件列表能点开、能看大小、能右键、能复制。
只有打开未下载的文件才失败或提示"需要连接到云"。

**机制原因**：`cldflt.sys` 是**内核态文件系统 minifilter 驱动，常驻内核**，
与用户态同步引擎解耦；且占位符状态存在 **NTFS 目录项**（reparse point）里。

| Windows | Linux / qxync |
| --- | --- |
| 占位符状态存在 **NTFS 目录项**里 | 占位符状态存在 **qxyncd 进程内存**里 |
| `cldflt.sys` 在内核，**用户进程死了它还在** | 内核里没有任何 qxync 的东西 |
| Explorer 直接问内核，内核答得出来 | 内核只能问 FUSE 守护进程，**进程死了就没人答** |
| 所以「引擎退出但文件夹还能浏览」 | 进程一死 → FUSE 连接断开 → `ENOTCONN` |

**结论**：Linux 上没法照抄（内核没有 cldflt 等价物），**但能做到八九成**——
关键差异只在于「谁来回答元数据请求」。

### A.2 qxync 的元数据路径本来就不需要网络

这是方案成立的前提，逐行核实过：

**① `getattr` 只读内存**（`lib.rs:2903-2916`）

```rust
fn getattr(&self, _req: &Request, ino: INodeNo, _fh, reply: ReplyAttr) {
    // 目录/文件都直接答元数据 —— 不触发任何下载（ls -l 必须是真实大小）
    let attr = {
        let g = self.inner.lock().unwrap();
        g.nodes.get(&ino).map(|n| n.attr)      // ← 纯内存 HashMap 查表
    };
    match attr {
        Some(a) => reply.attr(&ENTRY_TTL, &a),  // ENTRY_TTL = 500ms
        None => reply.error(fuser::Errno::ENOENT),
    }
}
```

**零网络调用、零 `Client`、零 async。** 这延续了文件头铁则
（`lib.rs:8-10`：「元数据（`getattr`/`readdir`/`lookup`）**不触发下载**」）。

**② `readdir` 吃本地快照**——`Inner.dirs` 的 `DirListing`（`lib.rs:320-323`）
由 daemon 轮询经 `apply_listing`（`daemon/sync.rs:653`）推下来。快照在内存则零网络请求。

**③ 已下载内容本来就在磁盘上**——水合后是真实稀疏文件（`lib.rs:2646-2649` 的 `set_len`），
进程退出后那些字节还在，只是没进程再去应答内核的 `read` 请求。

### A.3 离线能力矩阵

| 能力 | 需不需要 qxyncd 活着 | 现状 |
| --- | --- | --- |
| `ls` / `readdir` 看目录列表 | **不需要**（吃 `DirListing` 快照） | 依赖进程活 |
| `ls -l` 看文件大小/mtime | **不需要**（读 `Node.attr`） | 依赖进程活 |
| `getfattr` 读 pin / state | **不需要**（读 `Inner` + `PinMap`） | 依赖进程活 |
| 打开**已下载**的文件读内容 | **需要**（FUSE 回调应答 read） | 依赖进程活 |
| 打开**未下载**的文件 | 需要，且还要网络 | 依赖进程活 + NAS |

**所以「离线可用」的本质**：让 FUSE 进程在同步停掉后继续活着，
但切到「不联网、只答元数据 + 已有内容」的模式。这就是 T6 的做法。

### A.4 一个认知修正

M13 曾断言「FUSE 会话随进程死，所以无解」。**那个结论有个前提——进程是主动退出的。**

而用户「想重启」≠「想关掉」。`systemctl restart` 与 `qxync daemon stop`
现在走的是同一条路径（`daemon.rs:571-604` 都发 SIGTERM、都卸载），
但语义完全不同。所以 T6 的做法不是「让进程死后挂载还在」（做不到），
而是**「让不该卸载时不卸载」+「真断了快速自愈」（T5/T7）**。
