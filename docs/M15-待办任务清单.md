## 0. 背景与范围

### 0.1 目标

两件事，都不涉及架构重构：

1. **重启不丢挂载** —— `systemctl --user restart qxyncd` 后挂载点仍可用。
2. **数据正确性** —— 修掉当前会导致静默损坏 / 功能性错误的问题。

### 0.2 现状结论（已逐行核实，可直接采信）

### 0.3 明确不做（已评估，不要重新捡回来）

| 曾经的提议 | 为什么不做 |
| --- | --- |
| **拆分 FUSE 进程与同步进程（双进程 + RPC）** | 需 16 个 `LocalView` 方法跨进程 RPC（`lib.rs:645-694`），且 `reconcile_view` 每 30s 全量拉`nodes()`（`daemon/sync.rs:637`），10 万节点时性能不可接受。**本文 §2 用 200 行拿到 90% 收益**，暂不需要 |
| `CF_PLACEHOLDER_STATE_*` 标志位编码 | Windows 需要把状态编码进 NTFS 属性供 Explorer 独立读取；FUSE 下 `getattr` 由本进程应答，**位图推导（`lib.rs:292-300`）是对的**，改成标志位是倒退 |
| reparse point 兼容层 / 桌面桥 / UWP | Windows 特有 |
| oplock / 租约 / 硬链接策略 | FUSE 已有 per-node `op_lock`（`lib.rs:229`），冲突率低；硬链接 + 占位符 identity 语义复杂 |
| 内核态方案 | Linux FUSE **必须**用户态持 fd，无捷径 |
| `delta.rs` 增量上传接线 | 完整 librsync 实现已在 `delta.rs`，但真机实测 `versioning_support=0`（`client/lib.rs:833`），服务端不支持 |
| 备份任务 / 版本还原 | 官方客户端也没有的价值，优先级低 |
| 上传断点续传 | 视服务端 `upload.php` 是否接受分片，不确认前不做（见 **T4** 备注；T2 已把整文件读内存改成流式，断点续传的前置已铺好） |

**★ 真机实测发现的硬约束：服务端不接受 chunked 编码**

第一版实现用 `Part::stream`（纯流式、无`Content-Length`），真机直接被拒：

```
HTTP 411 Length Required   （QNAP 回的是 HTML 错误页，不是 JSON）
```

所以**必须**用 `Part::stream_with_length` 把长度告诉服务端 —— 这也正是 reqwest
`Part::file` 内部做的事（`file.metadata()` 取 len）。**「流式」在这里的正确含义
是「内存里只留一块 + 长度已知」，不是「不告诉服务端长度」。**

排查这条时 `parse_upload_result` 的报错只有「非 JSON」毫无线索，已改成带上
HTTP 响应原文前200B（`client/src/lib.rs`）—— 以后遇到类似被拒能直接看到原因。

**实际改动**

1. `Client::upload_file(dest, local, name)`（`qxync-client/src/lib.rs`）：
   先 `metadata` 取长度 → `tokio::fs::File` → `stream_with_length` 发流。
   返回**真正发出的字节数**（`AtomicU64` 在 stream 里累加，不是 metadata 的长度 ——
   上传期间用户可能还在改同一个文件）。
2. `Client::upload_stream_sized(reader, expected_len)`：任意 `AsyncRead` 的通用版。
3. `UploadQueue::upload_one`（`upload.rs`）改调`upload_file`，删掉 `fs::read`。
   **「用刚发出的字节数推进 baseline」这条正确性关键保持不变**（`upload.rs:470`）。
4. `upload_bytes` **保留不动**（daemon/CLI/测试还有 8 处调用，且它们传的都是
   小payload）。

### T3：内容校验和（xxhash + `--verify`） ✅ 已完成

**优先级**：最高（数据正确性）

**现状问题**

全 workspace **无 `etag` / `checksum` / `sha256` / `md5`**。下载只校验长度：

```rust
// crates/qxync-fuse/src/lib.rs:2751
if data.len() != want { return Err(...) }   // 只查长度
```

网络截断/改写、稀疏空洞被当真数据、位图与内容写序颠倒（`lib.rs:114-115` 已规避一半）——
这些**长度都对、内容错了**，用户几个月后才发现。

`delta.rs:381` 有 `md4` 实现，但只服务于未接线的 delta 路径。

**★ 与原文不一致的地方（实测发现，已按实测改）**

原文第 1 条说「`per_chunk_xxhash(8 × nchunks)` 追加进 `.qxstate` 文件头」。**照做会写爆盘**：

- 10 GB 文件 / 128 KiB = **81920 个区间**，`8 × nchunks` = **640 KB**；
- 而 `persist_chunk_state` 是**每个区间就绪就全量重写一次**（M9 的既有行为）；
- 于是水合一遍 10 GB 要写 640 KB × 81920 ≈ **52 GB** —— 比数据本身大 5 倍。

所以**拆成两个文件**（语义等价，写放大从 O(n²) 降到 O(n)）：

| 文件 | 内容 | 写入方式 |
|---|---|---|
| `<cache>.qxstate` | v2 头 + 位图 | 全量重写（10 GB 文件也只 10 KB，随便重写） |
| `<cache>.qxsum` | 定长 `8 × nchunks` 的 per-chunk xxhash64 | **定点 `pwrite` 8 字节**，写一个区间改一格 |

`.qxsum` 与 `.qxstate` 同生共死（`remove_cache_files` 一起删）。

**改动点（实际）**

1. **`.qxstate` 升 v2**（`lib.rs`，`QXSTATE2`）—— 头追加 `file_id(16)`（T9 用，当前恒为全零）
   与 `whole_xxhash(8)`。`file_id` 先占位是为了 T9 落地时**不用再升一次版**。
2. **per-chunk 校验和**落在新增的 `.qxsum`，写入点三处：
   - `ensure_chunk`：数据已在内存里，直接 `xxh64(&data)`，零额外 IO；
   - `mark_written_chunks`：本地写也要算（否则 verify 会把「用户自己写的文件」全判成损坏），
     一次 write 覆盖多个区间时合成**一次 `pwrite` 批次**（`sum_store_many`）；
   - `install_refreshed`：整份刷新出来的内容一次算齐。
3. **认领时全量校验**：`cache_file_for` 保留原有「签名不符即整份作废」，**之后**逐区间核
   `xxhash64`；核不过的区间清成未就绪，让 `read` 退回按需水合 —— **绝不返回错误内容**。
   `.qxsum` 缺失的区间一律当「不可信」（没有基准可比就不许声称内容正确）。
4. **`qxync verify [--path <dir>] [--repair] [--json]`** + **GUI 一键校验**
   （诊断 → 同步/缓存卡片，两个按钮：`校验` / `校验并修复`）。

**为什么用 xxhash 而非 sha256**：快一个数量级，而这里要挡的是**意外损坏**
（掉电、位翻转、写序颠倒、网络截断改写），不是恶意篡改 —— 攻击者能同时改内容和
校验和的话，本来就能改 `sync.db`。真要防篡改得靠服务端签名，那是另一件事。

**★ 过程中被测试抓到的真问题**

1. **`.qxsum` 缺失会让刚刷新的文件被误判**。`install_refreshed` rename 新内容后
   直接把区间表置全 true，但没写 `.qxsum` → 下次认领时「有位图、无校验和」，
   整份判成不可信。已有的 `install_refreshed_swaps_content_metadata_and_bitmap_atomically`
   测试直接报红 —— 这是校验和方案自己踩的坑，不是原有问题。
2. **每区间一次 `open` 撑不住大文件**。`sum_store_one` 原本每次都
   `open + stat + pwrite`，8192 个区间的文件就是 8192 次 open。改成
   `sum_store_many`（一次 open 写多格）。
3. **fixture 用 Rust 侧代码生成会掩盖 bug**。`qxstate_fixture.py` 的 Python xxh64
   第一版给 `mergeRound` 加了 avalanche，导致**短输入官方测试向量能过、长输入全错**
   （区间是 128 KiB，正好踩中）。两套独立实现互相校对才有意义。

### T5：挂载状态落盘 + 启动自动重挂

**优先级**：高（用户体感最强）

**目标**：daemon 重启后自动恢复挂载，用户无感。

**改动点**

1. 新增落盘文件 `$XDG_STATE/qxync/mounts.json`：
   ```json
   {
     "version": 1,
     "mounts": [{
       "mountpoint": "/home/kami/qxync",
       "remote": "/home/kami",
       "read_write": true,
       "cache_mode": "pagecache",
       "conflict": "rename_local",
       "threads": 4,
       "hydrate_timeout_secs": 60,
       "delete_limit": null
     }]
   }
   ```
   **故意不存**：sid、`Client`、节点表。sid 每次挂载重新登录
   （`daemon.rs:1632-1633` 本就挂载时 `set_sid`）；节点表靠懒加载重建
   （`lookup` 三级回退，`lib.rs:2086-2133`）。

2. 挂载成功后写盘；卸载成功后清对应条目。
   写入要**先写 tmp 再 rename**（参照 `lib.rs:114-115` 的原子写惯例）。

3. 启动时读 `mounts.json` 恢复。三个约束：
   - **必须已登录** —— 照抄 `daemon.rs:553-560` 那个等 `sid` 就绪的轮询模式；
   - **必须 `is_mounted()` 幂等检查**（`daemon.rs:1927`）—— 已挂载且 `remote` 一致就跳过；
   - **失败不阻塞启动** —— 单个挂载失败只 `warn!`，继续恢复其他的。

4. **与现有 `restore_tasks` 合并**：`restore_tasks_on_start`（`daemon.rs:2784`）
   目前只恢复**任务表里的挂载**，手动 `qxync mount` 挂的不在内。
   统一成：`mounts.json` 是唯一真相源，`tasks` 只表示「哪些共享文件夹该自动挂」。

5. `mount_task(state, &Task)`（`daemon.rs:2641`）已存在且参数从 `Task` 取，
   恢复时可复用；`mount()`（11 参数，`daemon.rs:1565`）是唯一挂载入口。

6. **改默认值要同步改注释**：`main.rs:52-58` 现在写着
   「默认关闭是刻意的：恢复会凭空挂载」。加了 `is_mounted` 幂等检查后这个顾虑
   基本消解，可以默认开——但**注释必须一起改**，否则代码和文档打架。

**验收**

- [ ] `systemctl --user restart qxyncd` 后，3~5 秒内挂载点自动恢复
- [ ] 恢复后 `ls -l` 的大小/mtime 与重启前一致
- [ ] 已挂载的重复恢复会被幂等跳过（日志可见）
- [ ] 单个挂载恢复失败不影响其他挂载，也不阻止 daemon 启动
- [ ] `mounts.json` 损坏时 daemon 仍能正常启动（降级为不恢复）

### T6：SIGTERM 保留挂载（同步可停、挂载留活）

**优先级**：高

**现状问题**

```rust
// crates/qxync-daemon/src/daemon.rs:571-604
tokio::select! {
    _ = shutdown_rx.recv() => break,   // 收到 shutdown 请求
    _ = tokio::signal::ctrl_c()  => break,
    _ = wait_sigterm(&mut sigterm) => break,
}
...
let n = shutdown_all_mounts(&state).await;   // ← 无条件卸载全部
```

`systemctl restart` 和 `systemctl stop` 走同一条路径。但用户重启的意图是
「继续用」，不是「关掉」。

**改动点**

1. `Options`（`daemon.rs:67`）加 `keep_mount_on_exit: bool`。
   - systemd `restart` → `true`
   - `qxync daemon stop`（`cli/main.rs:2277`）→ 显式传 `false`

2. 替换 `daemon.rs:604` 那行，改成条件分支：
   - `keep_mount_on_exit == false` →照旧 `shutdown_all_mounts`
   - `keep_mount_on_exit == true` →
     - 停同步相关任务（poller / dehydrator / journal flusher / peer host）
     - `persist_mounts` 写盘
     - **FUSE 会话继续跑，进程转入挂载守护模式**（`hold_mount_forever`）

3. **必须处理的副作用**：进程不退出 ⇒ 新 qxyncd 启动会撞车。
   处理方式：新进程启动时发现 `mounts.json` 里的挂载点**已被占用** →
   **新进程只做同步，挂载归旧进程**（同步引擎不依赖 FUSE，已核实）。
   不做 fd 传递（复杂且易错）。

   > 这一步顺带让代码形态朝「挂载与同步分离」靠拢，将来若真需要双进程，
   > 是顺水推舟而非从零做。

4. **必须同步改 systemd 注释**：`packaging/systemd/qxyncd.service` 现在写着
   「qxyncd 收到 SIGTERM 会卸载全部 FUSE 挂载点并删 socket/pid」。
   改完这句就是错的，会误导排障。

**验收**

- [ ] `systemctl --user restart qxyncd` 后挂载点**不中断**（FUSE 会话未断）
- [ ] 重启期间挂载点内 `ls` 正常
- [ ] `qxync daemon stop` 仍然真正卸载挂载（别把 stop 也改成保留）
- [ ] 重启后同步功能正常恢复（轮询、对账、队列继续工作）
- [ ] 旧进程与新进程同时在跑时，**没有 panic 循环**（日志确认）

### T7：僵尸挂载清理

**优先级**：中

**现状问题**

真崩溃 / OOM 后，`/mnt/qxync` 留在 `/proc/mounts` 里但 `ENOTCONN`，
用户 `cd` 进去看到 `Transport endpoint is not connected`。

**改动点**

qxyncd 启动早期清理：

1. 遍历 `mounts.json` 记的挂载点，`is_mounted()`（`daemon.rs:1927`）为真时，
   写个探测文件试试还活着不（`path.join(".qxync-probe").metadata().is_err()` → 已 ENOTCONN）。
2. 确认是僵尸 → `fusermount3 -uz <mp>`（lazy卸载）。
3. **安全边界**（避免误删别人的挂载）：
   - 只清 `mounts.json` 里记录过的路径，**不扫全盘**；
   - 校验 `/proc/self/mounts` 里的 subtype 是 `qxync`（挂载时设于 `lib.rs:3653`），
     确认是自己挂的才动；
   - 用 `-uz` 而非 `-u`，失败就跳过，**不阻塞启动**。

**验收**

- [ ] `kill -9` qxyncd 后重启，挂载点被自动清理并重建
- [ ]挂载点上有其他文件系统时不会被误清
- [ ] 清理失败不阻止 daemon 启动

### T8：per-file 同步状态机 + 进度上报

**优先级**：中（体验改善）

**现状问题**

用户能看到的状态**全是聚合数字**（`daemon.rs` 的 `status`）：

- `SyncInfo`（`ipc.rs:562-584`）：polls / refreshed / conflicts / uploaded / last_error
- `CacheInfo`（`ipc.rs:589`）：used_bytes / total_files / hydrated_files
- `HydroStats`（`ipc.rs:505`）：累计 count / bytes

文件级只有 `SpaceState` 三态（`ipc.rs:948-995`：仅在线 / 本地可用 / 始终可用），
且**只覆盖空间维度，不覆盖同步维度**。用户无法回答「我上周改的文件上传成功了吗」。

唯一错误明细在 `journal` 表（`store.rs:87-101`），而 journal 环形裁剪
（1 万条 / 30 天，`daemon.rs:37-58`）。

> 注：`tasks.rs` 是**任务配置模型**（JSON 持久化），**不是**执行器，别误读。

**改动点**

1. `Node`（`lib.rs:210-241`）加两个字段：
   ```rust
   /// 同步维度：本地与远端是否一致
   in_sync: bool,
   /// 上传/下载进度 (done_bytes, total_bytes)
   progress: Option<(u64, u64)>,
   ```
2. `SpaceState` **保持不变**（那是空间维度）。CLI / GUI 组合展示：
   - `同步中 42% · 仅在线`
   - `已同步 · 始终可用`
   - `未同步（1 个冲突待处理）`
3. 三个信息源已现成：`dirty`（`lib.rs:222`）、`uploads.pending`、
   `decisions` 待裁决数（`store.rs:102`）。扩 `file_states` 返回字段即可。
4. 进度上报：`FetchCtx`（`lib.rs:413`）加 `on_progress` 回调，每收一个分片调一次；
   `UploadJob` 同理（配合 T2 的字段）。经 IPC 汇总到 daemon，由 `status` 增量暴露。

**验收**

- [ ] `qxync file-states <dir>` 能看到每个文件的同步状态与进度
- [ ] 进度数字与实际传输一致（对照 T2/T8 的实测）
- [ ] 大文件下载时 GUI 进度条平滑推进，不是跳变

### T9：稳定文件身份 `file_id`

**优先级**：中（地基，影响面大）

**现状问题**

`Inner.by_remote: HashMap<String, INodeNo>`（`lib.rs:305`）是唯一索引，
`baseline` / `uploads` / `deletes` / `pins` / `decisions` **五张表全以 `path` 为主键**
（`store.rs:54,61,65,77,102`）。全 workspace 无 `file_id` / `etag` /远端 inode。

后果链条：
1. 远端改名 → 路径变 → `baseline` 查不到 → 三向合并
   （`qxync-core/src/sync.rs:349`）判成「本地新增 + 远端删除」→ 走 `rename_local`
   → **平白生成冲突副本**。
2. 远端移动（`dir1/a.txt` → `dir2/a.txt`）同理。
3. 上传队列按 `remote_path` 排队（`upload.rs:256`），排队期间远端改名 →
   上传写到旧名字，生成幽灵文件。

**约束**：服务端 `DirEntry`（`model.rs:68`）**没有** id 字段，只能本地自建。

**改动点**

1. `DirEntry`（`model.rs:60-100`）加 `file_id: FileId`。
   本地持久化身份，取 `<mtime>-<size>` 的哈希（与服务端无关，稳定可复算），
   退化时用纯文件名哈希。长度 16 字节。
2. 新增 `nodes` 表：`file_id` 主键，`path` 唯一索引，
   外加 `remote_path` / `size` / `mtime`。
3. `rename` 回调（`lib.rs:3317`，迁移逻辑在 `:3413-3414`）里同步迁移 `nodes` 行。
   现在那里已手工迁移 `by_remote` 和缓存文件，加一行 SQL 即可。
4. 与 T3 的 `.qxstate` v2 打通（`file_id` 存在位图头部）。
   **T3 已把位置留好了**：`ChunkState.file_id` / `Node.file_id`（`lib.rs:106-118`、`:473-`），
   当前恒为 `ZERO_FILE_ID`（16 字节全零）。T9 只需在这两处填真值 + 让 `cache_file_for`
   认领时把 `file_id` 也纳入签名比对，**不需要再升 `.qxstate` 版本**。
5. **所有 `DirEntry` 构造点都要补字段**——包括 `DirEntry::local`
   （`model.rs:92`）和测试里的构造。

**验收**

- [ ] 远端改名后不产生冲突副本（对账判为 rename 而非增删）
- [ ] 上传队列排队期间远端改名，上传落到新名字
- [ ] 旧 `sync.db`（schema v3）能安全迁移到新schema
- [ ] 现有全部测试通过（`qxync-proto-test/tests/`）

## 附录A：为什么「离线可用」在 Linux 上能做到 90%

> 论证基础，来自 `M14` 的调研。**T5/T6/T7 的可行性都建立在这上面**，
> 改动前请先理解这一节，否则容易把方案误判为「不可能」而放弃。

### A.1 先厘清：Windows 那种体验到底是什么

Windows 上的体验不是错觉：`Qsync` 客户端进程退出/崩溃后，
文件资源管理器里那个云盘节点还在，文件列表能点开、能看大小、能右键、能复制。
只有打开未下载的文件才失败或提示"需要连接到云"。

**机制原因**：`cldflt.sys` 是**内核态文件系统 minifilter 驱动，常驻内核**，
与用户态同步引擎解耦；且占位符状态存在 **NTFS 目录项**（reparse point）里。

| Windows | Linux / qxync |
| --- | --- |
| 占位符状态存在 **NTFS 目录项**里 | 占位符状态存在 **qxyncd 进程内存**里 |
| `cldflt.sys` 在内核，**用户进程死了它还在** | 内核里没有任何 qxync 的东西 |
| Explorer 直接问内核，内核答得出来 | 内核只能问 FUSE 守护进程，**进程死了就没人答** |
| 所以「引擎退出但文件夹还能浏览」 | 进程一死 → FUSE 连接断开 → `ENOTCONN` |

**结论**：Linux 上没法照抄（内核没有 cldflt 等价物），**但能做到八九成**——
关键差异只在于「谁来回答元数据请求」。

### A.2 qxync 的元数据路径本来就不需要网络

这是方案成立的前提，逐行核实过：

**① `getattr` 只读内存**（`lib.rs:2903-2916`）

```rust
fn getattr(&self, _req: &Request, ino: INodeNo, _fh, reply: ReplyAttr) {
    // 目录/文件都直接答元数据 —— 不触发任何下载（ls -l 必须是真实大小）
    let attr = {
        let g = self.inner.lock().unwrap();
        g.nodes.get(&ino).map(|n| n.attr)      // ← 纯内存 HashMap 查表
    };
    match attr {
        Some(a) => reply.attr(&ENTRY_TTL, &a),  // ENTRY_TTL = 500ms
        None => reply.error(fuser::Errno::ENOENT),
    }
}
```

**零网络调用、零 `Client`、零 async。** 这延续了文件头铁则
（`lib.rs:8-10`：「元数据（`getattr`/`readdir`/`lookup`）**不触发下载**」）。

**② `readdir` 吃本地快照**——`Inner.dirs` 的 `DirListing`（`lib.rs:320-323`）
由 daemon 轮询经 `apply_listing`（`daemon/sync.rs:653`）推下来。快照在内存则零网络请求。

**③ 已下载内容本来就在磁盘上**——水合后是真实稀疏文件（`lib.rs:2646-2649` 的 `set_len`），
进程退出后那些字节还在，只是没进程再去应答内核的 `read` 请求。

### A.3 离线能力矩阵

| 能力 | 需不需要 qxyncd 活着 | 现状 |
| --- | --- | --- |
| `ls` / `readdir` 看目录列表 | **不需要**（吃 `DirListing` 快照） | 依赖进程活 |
| `ls -l` 看文件大小/mtime | **不需要**（读 `Node.attr`） | 依赖进程活 |
| `getfattr` 读 pin / state | **不需要**（读 `Inner` + `PinMap`） | 依赖进程活 |
| 打开**已下载**的文件读内容 | **需要**（FUSE 回调应答 read） | 依赖进程活 |
| 打开**未下载**的文件 | 需要，且还要网络 | 依赖进程活 + NAS |

**所以「离线可用」的本质**：让 FUSE 进程在同步停掉后继续活着，
但切到「不联网、只答元数据 + 已有内容」的模式。这就是 T6 的做法。

### A.4 一个认知修正

M13 曾断言「FUSE 会话随进程死，所以无解」。**那个结论有个前提——进程是主动退出的。**

而用户「想重启」≠「想关掉」。`systemctl restart` 与 `qxync daemon stop`
现在走的是同一条路径（`daemon.rs:571-604` 都发 SIGTERM、都卸载），
但语义完全不同。所以 T6 的做法不是「让进程死后挂载还在」（做不到），
而是**「让不该卸载时不卸载」+「真断了快速自愈」（T5/T7）**。

## 附录 B：UX 要求（配合 T5/T6/T7/T8）

即使技术上能读，UI 上也必须说清楚，否则用户会以为坏了。

### B.1 `status` 要能看出「挂载活着但同步停了」

```rust
pub struct MountHealth {
    /// 挂载点是否仍在内核挂载表里
    pub mounted: bool,
    /// 是否处于「同步已停、仅本地可读」状态（T6 之后会出现）
    pub offline_readonly: bool,
    /// 上次同步成功的时间（None = 从未）
    pub last_sync_unix: Option<u64>,
}
```

### B.2 读未下载文件时的错误要说人话

现在离线读未下载文件会走到 `ensure_chunk` 然后网络失败，
用户看到一串网络错误。应区分：

| 情况 | 现在 | 应该 |
| --- | --- | --- |
| NAS 不可达 | 网络错误 | "云端暂时连不上，正在重试（剩余 45s）" |
| 同步引擎停了 | 网络错误 / 卡住 | "同步已暂停，文件尚未下载到本地" |
| 文件确实不存在 | ENOENT | 保持 |

| `lib.rs:46` 的 `HYDRATE_TIMEOUT = 60s`（对齐 Qsync 的 `CANCEL_FETCH_DATA`）
可以复用来做「重试中」状态上报。

### B.3 xattr 加离线标志

现有 5 个键（`lib.rs:3493`/`:3544`）：
`user.qxync.state` / `.pin` / `.remote` / `.vsize` / `.chunks`。
加 `user.qxync.offline`，让脚本能判断「现在能不能指望这个挂载点」。
