# M20：离线可用与累计缓冲区

> **一句话**：断网不再等于「本地改动等 10 秒后丢失」。
> 离线时挂载点继续提供服务（已缓存内容读写照常），本地改动进持久化缓冲区；
> 联网后按用户操作顺序统一回放，回放完再解冻上传/删除，最后补一轮对账。
>
> 用户原话（2026-10-19）：「现在程序对离线场景的处理有点问题，最好能做到离线了之后
> 还能提供服务，就是累计缓冲区，然后等上线之后统一进行同步」。

---

## 0. 结论先行

能做到，而且**不需要改协议**（Qsync 服务端不感知离线，参考 M14 的结论）。
本版按「累计缓冲区 + 重连统一同步」实现，代价是新增一张 `outbox` 表和一套
连通性状态机；离线期间的所有改动都没丢，但有两个诚实的限制：

1. **未水合的区间离线读不了**（数据不在本地，这不是客户端能变出来的）；
2. 离线新建/改名的文件在同步落地前，重新打开挂载点不会出现在目录列表里
   （本地节点表是进程内状态）——**但内容与操作都在持久化队列/outbox 里，不会丢**。

## 1. 旧行为到底哪里「有问题」（逐条核实）

| 场景 | 旧行为 | 后果 |
| --- | --- | --- |
| 离线改文件 | 上传队列照常指数退避，`max_attempts = 5`（约 10 秒）后**把作业删库** | 本地缓存文件还在，但 NAS 永远停在旧版；用户以为「等联网就会同步」 |
| 离线删文件 | 删除队列同样 5 次后放弃并删行 | 联网后下一轮对账把远端那份当新增刷回来 —— 文件「复活」，且没有任何解释 |
| 离线建目录 | `mkdir` 直接打 NAS，失败回 EIO | 文件管理器里建文件夹失败，用户无法离线整理文件 |
| 离线改名/移动 | `rename` 打 NAS（远端有副本时），失败回 EIO | 同上 |
| 离线读未水合文件 | `ensure_chunk` 走网络，等 connect timeout（20s）才 EIO | `cat` 一个没下载过的文件要卡 20 秒 |
| 离线 `qxync status` | 依次请求 `nas_uid` / `max_log` / `check_alive`，各 20s connect timeout | 排查「怎么不同步了」时最该跑的命令，最长卡一分钟 |
| 离线 `touch` | `set_mtime` 失败只记 warn（本地 mtime 已改） | 联网后排队中的上传把 mtime 覆盖回旧值，时间戳永远对不上 |

**根因只有一条**：代码里没有「现在是离线」这个状态。每个组件各自「试一下网络，失败就
按普通错误重试/放弃」，没人负责「攒着，等网好了统一推」。

## 2. 设计

### 2.1 连通性状态机（`qxync-core::connectivity`）

全进程唯一判定，三种状态：

```text
Unknown（刚启动，一次网络都没试过）  → 行为上等同在线（先试一次），展示为「未检测」
Online
Offline  → 上传/删除队列停在闸门上；FUSE 写路径直接进 outbox；轮询器切短探活
```

判据只有一条：**`Error::Transport`**。业务错误（4/5/8、Auth、Parse）都不是离线 ——
它们重试一万次也不会因为「网又通了」而成功，必须继续走原来的重试/放弃逻辑。

`Arc<Connectivity>` 由 daemon 显式注入 FUSE 挂载点、上传队列、删除队列；没注入时
（只读 FUSE、老测试）行为与 M20 之前完全一致（永远在线）。

### 2.2 离线缓冲区（outbox）

`sync.db` schema v4 → v5，新增表：

```sql
CREATE TABLE IF NOT EXISTS outbox (
  seq          INTEGER PRIMARY KEY AUTOINCREMENT,  -- 回放顺序 = 入队顺序
  kind         TEXT    NOT NULL,                   -- mkdir / rename / setmtime
  path         TEXT    NOT NULL,                   -- mkdir: 新目录；rename: 源
  target       TEXT    NOT NULL DEFAULT '',        -- rename: 目标；setmtime: epoch
  is_dir       INTEGER NOT NULL DEFAULT 0,
  attempts     INTEGER NOT NULL DEFAULT 0,         -- 只有非网络错误才增加
  created_unix INTEGER NOT NULL DEFAULT 0
);
```

**为什么不在 `uploads` / `deletes` 表上加列**：那两个队列的语义是「内容搬运」，
作业自足、重试幂等；结构操作有**顺序依赖**（先父目录后子目录、先改名再往新名字里
传文件），而且回放前要和 NAS 现状对账（源还在不在、目标是不是被别的设备占了）。
混在一起会让「表 = 未完成作业」这个干净的语义变浑。

**顺序就是 `seq`**：本地先 `mkdir a` 再 `mkdir a/b`，回放必须同序；改名链
`a→b`、`b→c` 也必须同序（合并成 `a→c` 会改变语义）。

### 2.3 写路径：本地视图先行

| 操作 | 离线时的处理 |
| --- | --- |
| `write` / 截断（已水合） | 写缓存文件 → `mark_dirty` → 上传队列（作业进库，worker 等联网） |
| `create`（新文件） | 与在线一致：本地建节点 + 0 字节缓存 → 上传队列 |
| `mkdir` | 不发 NAS；`outbox_add(mkdir)` + 本地节点/映射；`remote_known=false` |
| `rename` / 跨目录移动 | 不发 NAS；`outbox_add(rename)`；本地节点/缓存/映射照常搬，排队上传/删除作业改写到新名字；**本地新建（远端没有老副本）的对象改名时会把 outbox 里 `/旧` 前缀的结构操作回写成 `/新`** |
| `touch`（只改 mtime） | `outbox_add(setmtime)`；同时更新队列里同路径作业的 mtime |
| `unlink` / `rmdir` | 本来就异步入队（M11）→ 队列等联网 |

**持久化是硬要求**：`enqueue_outbox` 落库失败时 `mkdir` / `rename` 回 EIO ——
宁可让用户看到失败，也不能假装成功却丢操作（没有状态库的只读/测试实例就是这样）。

落 outbox 的同时把上传/删除队列置「离线结构缓冲未清」闸门。闸门与 M17 的
`paused`（改名临界区，短暂且成对 resume）**分开**：混用会让改名提前放行上传。

### 2.4 重连：先回放，再解冻，最后对账

```text
轮询器在离线分支短探活（Client::probe_reachable，5s 超时）
每次间隔按已离线时长退避：前 30s → 3s，前 5min → 10s，之后 → 30s
  ↓ 成功
flush_offline_backlog()
  1. 冻结所有挂载点的上传/删除队列
  2. 按 seq 回放 outbox
     · mkdir  → 先 stat：不存在就建；已是目录 = 幂等命中；同名是文件 = 放弃（不删文件腾位）
     · rename → stat 源/目标：
                 源在目标不在 → 改名/移动
                 源不在目标在 → 视为已落地（崩溃在删行前 / 别的设备做过）
                 两边都在     → 先把 **NAS 上那份** 改成冲突副本，再落地（不覆盖、不丢数据）
                 两边都不在   → 再查「跨目录两段式」的中间路径 `目标目录/源文件名`：
                                在 → 补第二段 rename（move 成功、rename 中断的残留）
                                不在 → 放弃并留痕（可能被其它设备删了）
     · setmtime → 直接推
  3. 清空后解冻 + 唤醒队列，连通性置在线
  ↓
run_sync_once() 补一轮对账
```

**一轮跑到一半断网怎么办**：任何一步遇到网络层错误都先用 5 秒探一次
`base_url`（`Client::probe_network`，不需要会话）。

* 探活**也失败** = 整台 NAS 不可达 → **立刻中止本轮**，只记一条错误（NAS 地址 +
  已做到哪一步 + 恢复后自动继续），不再逐接口/逐目录各报一条、也不再把剩下的目录
  挨个等 connect timeout；本轮不判定任何远端缺失，已处理的事件游标照常落盘。
* 探活**通过** = 只是这一条请求被丢（闪断）→ 继续本轮；网络类列举错误每轮最多记
  3 条，其余降 debug。

中止的轮次按「未完成」并入长期状态（`absorb_round(..., completed=false)`）：不清
上一轮的真实告警 —— 没检查过不等于检查通过。这是把「一次断网 = 一屏错误」收敛成
「一次断网 = 一条错误 + 转离线探活」的关键。

**回放失败语义**：

* 网络错误 → 立刻停，**不计数**，剩余行原样留着，队列继续冻结（下一轮再来）；
* 回放没清空 → 轮询器 3 秒后重试（不等完整间隔）；
* 会话失效（4/5）→ 立刻触发重登，**不计数**（最多容忍 20 次，防坏账号死循环）；
* 服务端未就绪（status=8，NAS 迁移/启动中）→ 等下一轮，**不计数**；
* 真正的业务错误 → 计数，到 5 次才放弃并删行，原因写进 journal / `status.offline.last_note`。

回放没清空时轮询器会在 3 秒后重试（不等一个完整轮询间隔）—— 重登成功 / NAS 就绪后
通常下一轮就能推进，用户不会看到缓冲区「卡着不动 10 分钟」。

**对账为什么必须排在回放之后**：离线改名后，本地视图已经是新名字；如果先对账，
对账看到远端还是旧状态，会把「新路径」当远端新增、「旧路径」当本地删除，
平白生成一堆刷新/冲突判定。

**幂等**：daemon 可能崩在「回放成功、删行之前」，或者别的设备做了同样的操作。
所以每条操作回放前都先 `stat`，用「NAS 现在是什么」决定动作，而不是闭着眼重放。

### 2.5 状态可见

`StatusData` 新增（老 daemon 不给时前端必须按「正常」处理）：

```jsonc
{
  "connectivity": { "online": false, "known": true, "since_unix": 1790000000,
                    "last_error": "…", "offline_events": 1, "online_events": 0 },
  "offline": { "pending_upload": 3, "pending_delete": 1,
               "pending_mkdir": 2, "pending_rename": 1, "pending_set_mtime": 1,
               "replaying": false, "last_note": "…" }
}
```

* CLI `qxync status`：多两行「连通性」「离线缓冲」；**离线时不再发网络请求**；
* GUI 首页：每个连接一条离线横幅（已离线多久 / 攒了几项 / 联网后自动同步）；
  状态页会话区多「连通性 / 离线缓冲区 / 回放中 / 离线原因」；
* FUSE xattr：`user.qxync.offline` = `"1"` / `"0"`，脚本可直接判断。

`m20-offline.sh` 的关键断言（NAS 指向 `127.0.0.1:9`，必定不可达）：

```text
status 离线时 6ms 返回（< 5000ms 断言：跳过 nas_uid/max_log/check_alive）
status 如实显示「离线（已 N 秒）｜最近错误: …」
status 显示离线缓冲区：待建目录 1 / 待改名 1（sqlite3 预置的行）
无挂载点时从 queue.db 只读统计：待上传 1 / 待删除 1（离线重启不丢视野）
daemon 重启后 outbox 仍 2 行，attempts 仍 0（网络错误不消耗重试次数）
```

单测关键不变量：

* `offline_failures_never_count_toward_give_up`：网络错误不管试几次都是 `Offline`；
* `flush_outbox_keeps_rows_and_attempts_on_network_error`：`127.0.0.1:1` 回放 →
  行不丢、attempts 仍 0；
* `plan_rename_never_overwrites_the_target`：源/目标都在 → `ConflictDest`，
  两边都不在 → `GiveUp`（不瞎猜）；
* `plan_mkdir_is_idempotent_and_never_overwrites_a_file`；
* `m20_offline_outbox_persists_and_freezes_queues`：写 outbox 必须冻结上传队列；
  没有状态库时 `enqueue_outbox` 必须报错；
* `outbox_orders_dedups_and_roundtrips`：前缀回写（改名）按**段级前缀**、rename 的
  path 与 target 一起改、幂等；
* `m20_local_rename_rewrites_pending_outbox_prefix`：本地改名 → outbox 的 mkdir 路径跟着改；
* `retarget_pending_under_rewrites_delete_jobs_and_store`：删除作业随改名 rekey；
* `replay_errors_split_offline_auth_busy_from_fatal`：网络 / 会话失效 / 服务端忙 / 业务错
  四类分开（前三类不消耗重试次数）；
* `offline_touch_updates_pending_job_mtime_and_persists`；
* `delete_queue_follows_connectivity_and_backlog_gate`。

### 4.2 真机 FUSE 验收（2026-10-19，已通过）

本机 `/dev/fuse` 可用后补做的真机验收：**真 NAS（test1 账号）+ 真 FUSE 挂载 +
TCP 中继断网**（杀中继等价于拔网线，服务端协议不变）。可复现脚本：
[`xtask/tests/m20-real-nas.sh`](../xtask/tests/m20-real-nas.sh)（不含口令，参数从环境变量来）。

```text
xtask/tests/m20-real-nas.sh                  ✅ 57 passed / 0 failed
```

覆盖的链路（全部在真挂载点上）：

```text
在线   写文件 / 建目录 / 上传                 → 远端出现
断网   离线判定 27s（默认轮询间隔 30s 内）     status 单次 0s 返回
离线   mkdir / 建二级目录                     本地立即可见
离线   往新目录 / 改名后的目录里写文件         ✅（见 4.3 修复）
离线   rename 文件 / rename 目录              本地立即生效；目录清单跟着搬
离线   ls 新建目录 / 改名后的目录              ✅
离线   rm 文件                                进删除队列（待删除 1），不阻塞
离线   touch 改 mtime                         进 outbox（待改 mtime 1）
离线   读已水合文件                           内容正确
离线   读未水合文件                           2ms 内 EIO（旧版卡 20s）
离线   status                                 离线缓冲计数齐全；outbox attempts 全 0
重启   daemon 重启（仍离线）                  outbox 4 行不丢、attempts 仍 0
恢复   3s 内探活成功 → 回放                    远端出现改名后的目录/文件、内容哈希一致、
                                              旧名消失、删除生效、mtime 生效、缓冲区清零
```

**已知限制（真机确认）**：

* 离线重启 daemon 时，**挂载点要等网络恢复后才恢复**（恢复挂载要先登录；登录需要网络）。
  缓冲区本身不丢，联网后先回放再补挂载；这一点在 4.3 之后的版本仍是待改进项。
* 「从没列过」的目录（不是挂载根）离线时 `lookup`/`readdir` 仍诚实地回 EIO ——
  挂载根现在会在挂载成功后预热一次清单（见 4.3），所以根目录下的离线创建不再要求
  用户先手动 `ls` 一遍；但深层的未访问目录仍看不了。

### 4.3 真机验收抓到的两个 bug（已修）

1. **离线建出来的目录「能建不能用」**：`mkdir` 成功（本地节点 + outbox 都对），
   但紧接着 `ls` 新目录、往里写文件都 EIO。
   根因：内核在 `open(O_CREAT)` / `mkdir` 之前会先对目标名字发一次 FUSE `LOOKUP`；
   新目录在远端还不存在、本地也没有它的清单快照 → 「没有快照 + 已知离线」直接 EIO，
   `create`/`mkdir` 回调根本没被调用（daemon 日志里只有一次 lookup，没有 mkdir）。
   修复：离线 `mkdir` 在本地视图里给新目录放一份**空清单快照**（诚实：它确实空），
   联网回放后由清单刷新换成远端真实列表。目录改名时清单快照跟着搬到新路径
   （`listing_move`），否则改名后的目录同样「进不去」。
2. **断网后根目录建不了东西（哪怕在线时用过）**：FUSE 挂载根目录的清单快照是懒加载的，
   如果用户从没在挂载点里 `ls` 过根，断网后根下的 `mkdir`/`open(O_CREAT)` 都会卡在
   lookup 的 EIO 上。修复：挂载成功后主动**预热挂载根清单**；预热用
   `seed_listing`（只在还没有快照时灌入），避免「挂载时抓的旧清单」迟到落地，
   把用户刚新建、已 upsert 进快照的文件抹掉（这个竞态也在真机验收里复现过）。

## 5. 已知限制与后续

1. **离线新建/改名的目录在同步落地前不显示**（daemon 重启后本地节点表重建）。
   内容与操作不丢；联网回放后下一轮对账就会出现在列表里。
   （同一进程内是即时可见、可继续写入的 —— 见 4.3 的空清单快照修复；
   且 outbox/删除队列都会跟着改写路径。）
   ★ M21 起这条**大幅收窄**：清单持久化（`listings` 表）+ 挂载时装回，离线重启后
   已列过的目录、本地建的目录都照常可见 —— 只有「从没列过也没本地建过」的目录
   仍要联网后由轮询补上。
2. **离线重启 daemon 后，挂载点要等网络恢复才恢复**（恢复挂载需要先登录）。
   缓冲区、队列都还在，联网后先回放、再补挂载。
   ★ **M21 已修**：无会话挂载 + 持久化目录清单，离线重启 1 秒恢复挂载点且离线
   可用（见 [`M21-离线可重启.md`](M21-离线可重启.md)）。
3. **回放改名的冲突固定走 `rename_remote` 语义**：离线时读不到任务的 `conflict`
   策略在恢复后是否还有效，所以选「两边都保留」的保守解。将来可把任务策略快照进
   outbox 行。
4. **任务级 purge 不清理 outbox**（与上传/删除队列一致：按连接共享）。
   连接级 purge 直接删 `sync.db`，行随之消失。
5. **回放放弃没有补偿**：`mkdir` 撞同名文件、`rename` 源和目标都不在 NAS 上时，
   5 次重试后删 outbox 行并在 journal 留痕；后续对账会按常规增删/冲突规则处理，
   可能表现为「远端新增/本地刷新」，但不会静默删 NAS 数据。
6. **删除/上传两个队列之间没有全局顺序**（沿用在线语义）。离线时「先删后建同名文件」
   这种组合依赖队列各自顺序；真机上概率很低，若将来要严格化，需要把三类操作并入
   同一条 seq 日志。
7. **离线时 `status` 的 `session.alive` 显示「失活」**：离线时无法探测，界面用离线
   横幅区分；这是「不撒谎」（不知道就不说活着），但文案上还可以再细化。
   ★ **M22 已修**：`SessionInfo` 新增 `alive_known`（离线跳过探测时为
   `false`），CLI / GUI 对「没探测过」显示**「未知（离线未探测）」**而不是
   「失活」—— 后者会误导用户以为会话真失效了去重登，其实只是网断了。
8. **排队中途断网时 `daemon stop` / `umount` 的排空**：已知离线时 M20 就直接
   跳过排空；但「刚断网、连通性还没判定离线」的窗口里，drain 会等 worker
   第一次上传失败（置离线）才可能推进 —— 旧实现此后仍陪等满 120s 超时。
   ★ **M22 已修**：`drain` 在闸门（离线 / 回放未完）落下时**提前返回**，作业
   都在持久化库里，联网后继续。最坏耗时 = 一次在途请求的 connect timeout，
   不再是 120s。

## 6. 与既有设计的关系

* M14/M15 解决的是「同步引擎停了，挂载点还在不在」；M20 解决的是「网络断了，
  改动还在不在」—— 两件事互补，M20 的离线状态也给 M14 的「离线模式」提供了
  统一的判定入口。
* M11 删除队列 / M17 改名不排空队列 / T9 身份迁移：本版全部复用，没有另起炉灶。
* M15 附录 B.3 提过的 `user.qxync.offline` xattr 在本版落地。
