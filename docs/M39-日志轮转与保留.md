# M39 · 日志轮转与保留（同一天不再能写出一个 5 GB 的文件）

> 状态：**已实现 / 已验收（2026-10-27）**；§6 的数字均为验收当天实测（命令与输出摘要见该节）
> 前置：[M37 休眠唤醒后守护被 SIGPIPE 杀死](M37-休眠唤醒后守护被SIGPIPE杀死.md)
> （同一条 `tracing_appender` 落盘链路、同一个日志目录）

## 0. 结论先行

旧实现只有一句 `tracing_appender::rolling::daily`：

1. **只在跨天切段，同一天内没有上限** —— 一天里刷多少就写多大；
2. **从不删除旧文件** —— 只增不减。

真机因此攒出 **单个 5.17 GB** 的 `qxyncd.log.2026-10-23`（`du` 看是 4.9G，因为 du 用 GiB；
两种写法是同一个文件，见 §1.1）。M39 补两件事：

* **写路径**：`qxync_core::logcfg::RotatingWriter` —— 按天 **且按大小** 切段，
  写满 `log_max_file_mb`（默认 32 MiB）当场改名成 `<前缀>.log.<日期>.<n>` 再开新段；
* **清理**：`logcfg::prune` —— 按 `log_keep_days`（默认 14 天）与
  `log_max_total_mb`（默认 256 MiB）删旧文件，**按 mtime 从最旧删起**。

「正在写的文件不删」不靠猜：`RotatingWriter` 打开文件时持有 `flock(LOCK_EX|LOCK_NB)`，
`prune` 删之前先试加同一把锁 —— **加得上 = 没人在写，加不上 = 跳过并记进 `PruneReport.in_use`**。
daemon 与 GUI 是两个进程、各写各的文件、还可能有多个连接各自的 `qxyncd-<id>.log`，
这个判据对它们都成立（§2.3）。

策略归 `settings.json` 管（三个字段），**改完不用重启**：写路径每次现读进程内策略。
除「写日志时顺带清」之外，daemon 还有一条**独立的定时清理**（默认每小时，
`QXNYC_LOG_PRUNE_SECS` 可调），所以「不写日志也会按时删旧文件」。

同版本还加了一条**防御**：`accept` 失败后 `sleep(100ms)` 再重试（§3.7）——
这样即使哪天又出 fd 问题，也不会再变成一秒钟几千行的日志洪水。**但 fd 泄漏本身是另一件事**
（§5.6），M39 只保证「它再刷也刷不爆盘、旧文件会自动清」。

## 1. 现场：5.17 GB 是怎么来的

### 1.1 真机数字（2026-10-23，只读取证）

```text
$ ls -l ~/.local/state/qxync/log/
-rw-r--r-- 1 kami kami 5174393555 10月24日 02:00 qxyncd.log.2026-10-23
-rw-r--r-- 1 kami kami   28077319 10月19日 01:59 qxyncd.log.2026-10-18
-rw-r--r-- 1 kami kami   11189910 10月26日 06:44 qxyncd.log.2026-10-25
...
$ du -sh ~/.local/state/qxync/log/
4.9G
```

| 指标 | 数值 | 说明 |
|---|---|---|
| 单文件字节 | **5 174 393 555** | = 5.17 GB（十进制）/ 4.82 GiB；`du -sh` 报 4.9G 是 GiB 口径 |
| 单文件行数 | **52 266 068** | 平均 99 字节/行 |
| 整目录 | 4.9 GiB（当时）/ **5.93 GB（20 个文件，写本文时）** | 99% 都在这一个文件里 |
| 正常日体量（对照） | 10-18：27 MB / 8.0 万行；10-25：11 MB / 5.7 万行；10-20 ~ 10-24：136 KB ~ 392 KB | 平时一天几百 KB ~ 几十 MB |
| 刷屏窗口 | 2026-10-23T15:45:11Z 起（本地 23:45）到文件最后一行 18:00:18Z（本地 10-24 02:00） | ≈ 10 小时写掉 5.17 GB |

> 行首时间是 **UTC**（tracing 默认的 `SystemTime` 格式），本地是 +08:00。
> 文件名用的也是 UTC 日期（旧 `daily` 的上游实现就是 UTC；M39 沿用，见 §5.2）。

### 1.2 刷屏的真身：一条 WARN 的紧循环（99.998%）

按行归并统计（取前 200 万行，`sed` 把数字抹成 `N` 后 `sort | uniq -c`）：

```text
1999624  WARN qxyncd::daemon: accept 失败: Too many open files (os error N)
    239  INFO qxyncd::sync: 同步轮询: ...
     12  INFO qxync_fuse::upload: 已上传 ...
```

对**整个** 5.17 GB 文件精确计数：

```text
$ grep -c "accept 失败" qxyncd.log.2026-10-23
52265459          # 52 266 459 / 52 266 068 行
$ grep -m1 -n "accept 失败" qxyncd.log.2026-10-23
374:2026-10-23T15:45:11.602243Z  WARN qxyncd::daemon: accept 失败: Too many open files (os error 24)
```

**结论：这不是「每轮轮询打一行日志」，是 `accept` 失败后不退避的紧循环**（一天 5000 万次
`accept` 失败）。M39 的按大小切段保证「单文件不超过 32 MiB」，按总占用/天数保证「目录回到
上限内」；但**它不消除刷屏本身**：只要紧循环还在，切段后的编号段会一个个被写满、旧的再被
删掉 —— 磁盘不再被吃光，CPU 与 fd 仍在空转。本版只加了 100ms 退避（§3.7），
**fd 泄漏的根因不在 M39 范围**（§5.6）。

### 1.3 写本文时它又复发了一次（2026-10-27 08:34–08:37）

不是设计推演，是现场第二次抓到的同形状：

| 时刻（本地） | `qxyncd.log.2026-10-27` 大小 |
|---|---|
| 08:34 | 44 862 字节 |
| 08:36:33 | **707 336 193 字节（674 MB）** |
| 08:37 之后 | EMFILE 紧循环停住；文件仍被缓慢追加（内容是普通的「对账列举失败 / 同步轮询」轮次，08:41 到 707 375 327 字节，08:46 到 707 376 678 字节 ≈ 每秒几字节），说明旧的 daemon 进程还活着 |

内容同样是 `WARN qxyncd::daemon: accept 失败: Too many open files (os error 24)` 连续刷屏。
**旧二进制下一次紧循环，2 分半就是 674 MB** —— 这是 M39 存在意义的第二次现场证明。

> 取证环境说明：本文的 shell 在**独立 PID 命名空间**的沙箱里，`pgrep qxyncd` 看不到宿主的
> daemon（这也解释了为什么「没进程」但日志在涨）。判断「宿主上跑的是旧二进制」的依据是：
> ① 文件在被持续追加；② 里面**没有**新版的 `accept 失败（100ms 后重试）` 文案。
> 因此下文只说「旧二进制还活着」，不说「它正在刷 EMFILE」（那一阵 08:37 就停了）。

### 1.4 旧实现的两个缺陷（对应 M39 的两件事）

| # | 缺陷 | 后果 | M39 的处置 |
|---|---|---|---|
| 1 | `rolling::daily` 只会按时间轮转，**同一天内无上限** | 一次刷屏 = 一天一个大文件（5.17 GB） | `RotatingWriter`：写满 `log_max_file_mb` 就切段 |
| 2 | 旧文件**从来没人删** | 目录只增不减，攒到磁盘满 | `prune`：按天数 + 按总占用删；定时任务独立跑 |

## 2. 目标与取舍

### 2.1 为什么自己写 writer，不换 `tracing_appender` 的别的 `Rotation`

`tracing_appender 0.2.5` 只提供 `Rotation::{Minutely, Hourly, Daily, Never}` —— **全是时间
轮转，没有大小上限**。真要「写满 32 MiB 就切」，只能自己包一层 `io::Write`：
`RotatingWriter` 实现 `io::Write`，直接交给 `tracing_appender::non_blocking` 做后台落盘
（用法见 `logcfg.rs:398-409` 的文档注释），`tracing_subscriber` 那一侧完全不用改。

命名规则与旧实现**逐字一致**：`<前缀>.log.<YYYY-MM-DD>`，编号段是同一格式往后加 `.<n>`
（`logcfg.rs:408-409`）。`<前缀>` 来自 `log_prefix_for`（`crates/qxync-core/src/ipc.rs:98-104`）：
`qxyncd.log` / `qxyncd-<id>.log`；GUI 是 `qxync-gui.log`。所以历史文件仍然排得进同一序列。

### 2.2 为什么按 mtime 判新旧，不解析文件名里的日期

文件名里的日期只说明「这段是哪天的」，不说明「最后一次写是什么时候」；而清理要回答的是
后者（谁最旧）。而且目录里可能有：

* 旧 `daily` 留下的 `qxyncd.log.2026-10-18`；
* M39 切出来的 `qxyncd.log.2026-10-27.3`；
* 用户手工拷进来的日志、被 `cp -p` 保过时间的文件。

按 **mtime** 排序对上述全都成立，不需要维护任何额外索引
（`logcfg.rs:240-262` 的 `scan` 排序、`logcfg.rs:367` 的总量清理排序都用 mtime）。

### 2.3 为什么用 `flock` 判「谁在写」，而不是按 mtime/文件名猜

「正在写的文件不能删」：删掉之后进程还在往已 unlink 的 inode 写，日志就再也找不到了。
第一版设计是「每个前缀族里 mtime 最新的一个永不删」，但它是个**启发式**，有真实反例：

* daemon 与 GUI 是两个进程、各写各的前缀族。GUI 可能**几天不写一行日志** ——
  它的活动文件 mtime 很旧，按「族内最新」看着像死文件（如果只剩它一个），按 mtime 更会
  直接判死；
* 反过来，一个 40 天前就已经退出的 GUI 留下的孤儿日志，按「每族最新一个」会被**永远保护**，
  永远清不掉 —— 这正好和「保留 14 天」的承诺相反。

`flock` 把「谁在写」变成一个**内核事实**而不是推断：

```rust
// logcfg.rs:189-195 —— 写入器打开文件时拿一把排它锁（拿不到不影响写日志）
fn lock_exclusive(file: &File) { libc::flock(fd, LOCK_EX | LOCK_NB); }

// logcfg.rs:205-222 —— 清理前试加同一把锁：加得上 = 没人写（立刻解锁）
fn is_in_use(path: &Path) -> bool {
    let f = File::open(path)?;                 // 打不开（权限/已删）→ 当「在用」，保守跳过
    let rc = libc::flock(fd, LOCK_EX | LOCK_NB);
    if rc == 0 { libc::flock(fd, LOCK_UN); false } else { true }   // EWOULDBLOCK = 有人写
}
```

选它的理由：

* **跨进程、零配置**：daemon / GUI / 多连接各自的活动文件都被同一套判据保护，不依赖
  「哪个族最新」这种脆弱假设；
* **同一进程也挡得住**：`flock` 是 per-open-file-description 语义，同一进程用另一个 fd 再开
  一次也会冲突 —— 所以 daemon 的定时清理不会误删自己正在写的文件（`logcfg.rs:202-204` 注释）；
* **失败不影响写日志**：锁拿不到（比如日志目录在不支持 `flock` 的文件系统上）只是保护退化，
  写路径照旧（`logcfg.rs:187-188`）；
* **失败方向是「不删」**：`File::open` 失败、平台非 unix 时按保守处理（§5.3）。

### 2.4 为什么策略放 `settings.json`、且写路径「每次现读」

日志是**进程级**资源，但用户改策略的地方在设置页/CLI，中间隔着 daemon 进程。三个选择：

1. 改完要求重启 daemon —— 用户不会为「把日志保留从 14 天改成 3 天」重启服务；
2. 改完给写线程发消息 —— 要穿过 `non_blocking` 的后台线程，得自己加通道；
3. **写路径每次现读一份原子量** —— `logcfg::policy()`（`logcfg.rs:112-119`）读三个
   `AtomicU64`，`apply_settings`（`logcfg.rs:131-135`）在 `settings_save` 里更新它。

选 3：一次 `Relaxed` 原子读的代价可以忽略，热生效是结构性的，且**不要求 GUI 与 daemon
同时在线**（CLI `qxync settings --set` 也走同一条 `settings_save`）。

## 3. 设计

### 3.1 策略三字段

`Settings`（`crates/qxync-core/src/settings.rs:278-289`）新增三个 `u32`，serde `default`：

| 字段 | 默认 | 上限（normalize 夹） | `0` 的语义 | 单位 |
|---|---|---|---|---|
| `log_max_file_mb` | **32** | 4096（`MAX_FILE_MB_CAP`） | 不按大小切段（不推荐） | MiB |
| `log_keep_days` | **14** | 3650（`KEEP_DAYS_CAP`） | 不按天数删 | 天 |
| `log_max_total_mb` | **256** | 102400（`MAX_TOTAL_MB_CAP`） | 不限总占用 | MiB |

* 上限只在 `Settings::normalize` 里夹（`settings.rs:363-365`），**不做「必须非零」校验** ——
  三个字段的 `0` 各有语义，手改 JSON 写 `0` 是合法配置；
* `normalize` 夹上限的理由是「手改 JSON 写了 `4294967295` 时别真拿它去建盘」
  （`settings.rs:360-362` 的注释）；
* `LogPolicy` 是它们的字节版（`logcfg.rs:61-66`），`LogPolicy::from_settings` 只做
  MB→字节换算（`logcfg.rs:82-88`），范围校验不在这里重复做。

默认值为什么是这三个数：32 MiB ≈ 正常一天的量（真机平时几百 KB ~ 27 MB，见 §1.1），
真出刷屏时一天也只切出有限几段；14 天够复盘「上周开始不对」；256 MiB 是「一周正常日志」
的十倍余量，又是一块 SSD 上可以无感回收的量级。

### 3.2 切段：文件名规则与三个触发点

命名（`logcfg.rs:408-409` 的注释、`rotate_size` / `rotate_day`）：

```text
<前缀>.log.<YYYY-MM-DD>          ← 当前段（今天）
<前缀>.log.<YYYY-MM-DD>.<n>      ← 当天已切出的旧段，n 从 1 递增（找第一个不存在的 n）
```

日期标签是 **UTC**（`today_tag` / `date_tag`，`logcfg.rs:141-167`），与旧 `daily` 一致 ——
理由与证据见 §5.2。

三个触发点：

| 触发 | 时机 | 代码 |
|---|---|---|
| **大小** | 每次 `write` 前检查：`bytes + buf.len() > 上限` 且当前段非空 → 先切段再写 | `logcfg.rs:538-547` |
| **跨天** | 每次 `write` 前检查，**每秒最多查一次系统时间**（日志量大时不是每行都算日期） | `logcfg.rs:523-535` |
| **开局** | `RotatingWriter::new` 发现今天的段已经超限（典型：昨天写爆、今天重启）→ 直接切段 | `logcfg.rs:446-455` |

「当前段为空不切」是为了避免 `max_file_bytes < 单行长度` 时无限切空段
（`logcfg.rs:539` 的 `st.bytes > 0` 条件）。

切段实现上有个坑写在注释里（`logcfg.rs:491-498`）：**rename 之后旧文件句柄仍指向被改名的
inode**，必须先 `flush` 旧句柄、`rename`、再 `open_append` 新句柄、替换 `st.file`，否则会
继续写进已经改名的旧段。新句柄在 `open_append` 里重新拿 `flock`（`logcfg.rs:470-475`），
所以切段后「正在写的是新文件」这个事实对清理任务立即可见。

### 3.3 清理：`prune(dir, policy, keep)` 的判定顺序

`crates/qxync-core/src/logcfg.rs:305-394`，规则按顺序：

1. **筛选**：只看本目录里 `is_qxync_log_name` 命中（以 `qxync` 开头且名字含 `.log`）的
   **普通文件**；别的文件一概不碰（`logcfg.rs:174-176`、`310-325`）；
2. **保护集** = 调用方显式 `keep` ∪ **`flock` 探测到的「正在被写」的文件**
   （`logcfg.rs:332-343`）。跳过的文件记进 `PruneReport.in_use`（`logcfg.rs:340`、`380`）——
   不删不是失败，但要能被观察；
3. **按天数**：`keep_days > 0` 时，mtime 早于 `now - keep_days*86400` 且不在保护集的 → 删
   （`logcfg.rs:346-355`）；
4. **按总量**：`max_total_bytes > 0` 且剩余超过上限 → 从**最旧**开始删，直到不超限或删无可删
   （`logcfg.rs:357-375`）；
5. **执行**：逐个 `remove_file`；成功记进 `deleted`/`freed_bytes`，失败（权限/占用）记进
   `failed`，**不中断**（`logcfg.rs:383-392`）。

「按天数」先算、再算总量，是有意的：先把明显过期的删掉，总量判定面对的是更小的集合，
报告里的 `freed_bytes` 也是两者的和，不会重复计数（进入 `doomed` 的路径在两条规则里互斥，
`logcfg.rs:361-366` 的 `filter` 把已判死的排除了）。

写路径里两处「切段后顺手清一次」都传了当前段当 `keep`
（`logcfg.rs:532`、`545`）—— 即使 `flock` 因为文件系统不支持而失效，也有这层显式保护兜底。

### 3.4 谁在什么时候清理

| 触发点 | 频率 / 时机 | 位置 | 说明 |
|---|---|---|---|
| 写日志时顺带 | 每次切段（大小/跨天）后 | `logcfg.rs:529-532`、`543-546` | 用**当前段**当 `keep`，最精确 |
| daemon 定时任务 | 默认 **3600s**，启动后立刻跑第一次 | `crates/qxync-daemon/src/daemon.rs:5645-5686`（`log_prune_secs` / `spawn_log_maintenance`），调用点 `:871` | **独立于写日志**：不写日志也按时删；`QXNYC_LOG_PRUNE_SECS` 可调（最小 5s） |
| 保存设置 | 每次 `settings_save` | `daemon.rs:5841-5853`（同步态）、`:5602-5603`（空转待命） | 热应用策略 + **立即清一次**：把保留 14 天改成 3 天，用户期望马上看到空间回来 |
| `qxync log --prune` | 用户手动 | CLI → `Request::Logs{prune:true}` → `daemon.rs:5692-5751` | 进程外清理；靠 `flock` 不误删活动日志 |
| GUI「立即清理」 | 用户手动 | 同一个 IPC 请求 | 与 CLI 同一条路 |

定时任务放在 `run()` 的最前面（`daemon.rs:871`）是有意的：**空转待命**（还没配 NAS 连接）
的 daemon 也在写日志，同样要有人清。

### 3.5 热生效链路

```text
qxync settings --set log_keep_days=3     （或 GUI 保存）
  → daemon settings_save
  → save_settings_to_disk + *state.settings = s      （落盘 + 内存态）
  → logcfg::apply_settings(&s)                       （写进程内原子量，daemon.rs:5841）
  → logcfg::prune(log_dir, &new_policy, &[])         （立即清一次，daemon.rs:5842）
  → 之后每次 write：let pol = policy();  （logcfg.rs:518）→ 新策略立刻生效
```

daemon 启动时也应用一次（`crates/qxync-daemon/src/main.rs:243-266`），这样「今天的段一打开
就受约束」；读 `settings.json` 失败只 warn、退回默认策略 —— **日志初始化绝不能因为配置坏了
就失败**（同一节注释还有 M37 的教训：日志初始化 panic 会让用户只看到「socket 未就绪」）。
GUI 启动时同理（`crates/qxync-gui/src/lib.rs:1285`）。**GUI 是另一个进程**：它每次调 `logs`
都会把 daemon 回报的「生效策略」同步进本进程（`crates/qxync-gui/src/commands.rs:491-498` 的
`apply_policy_from_logs`），否则会出现两套真值 —— 界面写着「单文件 8 MiB」、GUI 自己的
`qxync-gui.log.*` 却还按启动时的 32 MiB 切段。取 daemon 的生效值（而不是设置文件）还顺带
覆盖「策略是 CLI 改的」这种情况。

### 3.6 IPC / CLI / GUI

IPC（`crates/qxync-core/src/ipc.rs`）：


### 3.7 同版本的防御：`accept` 失败后 100ms 退避

`crates/qxync-daemon/src/daemon.rs:1372-1378`（`accept_backoff`），三个 `accept` 失败分支都改走它
（`:698`、`:1134`、`:1348`）：

```rust
async fn accept_backoff(e: &std::io::Error) {
    tracing::warn!("accept 失败（100ms 后重试）: {e}");
    tokio::time::sleep(Duration::from_millis(100)).await;
}
```

原来的错误分支直接落回 `select!`，下一次 `accept` 立刻又失败 —— 纯烧 CPU + 刷日志。
退避后理论上限约 86 万行/天（10 行/秒），再被 `log_max_file_mb` 切段与 `log_max_total_mb`
兜住。**注意这是止血不是根治**：fd 为什么会被耗光（泄漏点）仍待查（§5.6）。

## 4. 配置与用法

### 4.1 改策略（CLI，立即生效）

```bash
# 单文件 16 MiB、保留 7 天、总量 128 MiB
qxync settings --set log_max_file_mb=16 --set log_keep_days=7 --set log_max_total_mb=128
# 只看当前值（settings 的输出里含 log_* 三项）
qxync settings --json | jq '.settings | {log_max_file_mb, log_keep_days, log_max_total_mb}'
```

* `--set` 走 `Settings::set_kv`（`settings.rs:520-546`），未知键会报错并**列出可用键**；
  非整数报「需要整数（MB/天）」；
* 保存路径优先走 daemon（`settings_save`，热生效 + 立即清理）；daemon 没在跑时退回
  `qxync settings` 的本地落盘（`cli/main.rs:990-1020`）—— 那次**不会**立即清理，
  下次 daemon 启动应用策略时会清。

### 4.2 看 / 手动清

```bash
qxync log              # 看占用与文件表
qxync log --prune      # 手动清一次（跨进程只删「没人持锁」的旧文件）
qxync log --json       # 脚本用
```

### 4.3 环境变量

| 变量 | 默认 | 作用 |
|---|---|---|
| `QXNYC_LOG_PRUNE_SECS` | `3600` | daemon 定时清理间隔（秒），最小 5；验收时调小以便观察（`daemon.rs:5645-5651`） |
| `RUST_LOG` | `--log-level` | 与 M39 无关：日志**级别**仍归它管（M39 只管文件**大小/数量**） |

### 4.4 典型场景

| 场景 | 怎么做 |
|---|---|
| 磁盘被日志吃光，先救急 | `qxync log --prune`（或 GUI「立即清理」）→ 观察 `qxync log` 的占用回落 |
| 只要最近一周的日志 | `qxync settings --set log_keep_days=7` → daemon 立即清一次 |
| 排查「上周三开始不对」 | 先把 `log_keep_days` 调大（如 30）**再**复现，别让清理把证据删了 |
| 临时关掉所有限制（排障） | 三项全 `0`：`--set log_max_file_mb=0 --set log_keep_days=0 --set log_max_total_mb=0`，**记得改回来** |
| 想确认策略真的生效 | `qxync log` 的「轮转策略」行读的就是进程内当前策略（清理用的也是它，不是 settings.json 缓存） |

## 5. 边界与已知限制（如实写）

### 5.1 删除是「尽力而为」

`prune` 对 `remove_file` 失败只记录、不中断（`logcfg.rs:383-392`）。失败会出现在
`PruneReport.failed` → `LogsData.failed` → CLI 的「⚠️ 没删掉的」/ GUI 的失败项。
不重试、不报错退出 —— 清理任务失败不该让 daemon 出问题。

### 5.2 日期按 UTC：与旧 `daily` 一致（本地 08:00 换文件）

旧 `tracing_appender 0.2.5` 的 `daily` 用 `OffsetDateTime::now_utc()`（上游
`rolling.rs:198,212,222`），即**按 UTC 日期**命名与切段。真机可证：

```text
qxyncd.log.2026-10-26  最后一行 2026-10-26T23:59:57.700755Z
qxyncd.log.2026-10-27  第一行   2026-10-27T00:00:00.755002Z
# 即「本地 08:00 换文件」（CST = UTC+8）
```

M39 沿用 UTC：`date_tag` 用 `secs.div_euclid(86_400)` → `civil_from_days`（`logcfg.rs:146-167`），
**不碰本地时区**。所以：

* 换段边界与旧实现**完全一致**（UTC 零点 = 本地 08:00），升级当天不会出现「文件名跳一天」
  或「同一天两套命名」；
* 时区跳变（出差改时区、DST）**完全不影响**：命名、切换点、清理全是 UTC 与 mtime，跟本地
  时区无关（代价只是用户按本地钟点找日志时要换算一下）；
* 代价：用户看文件名找「昨晚的日志」时，`.2026-10-27` 里其实从本地 08:00 才开始 ——
  这是从旧实现继承的行为，不是 M39 引入的。

### 5.3 `flock` 是启发式，不是绝对保护

**正常情况**（同一套二进制、daemon / GUI / 多连接各写各的文件）判据成立。但有明确边界：

| 情况 | 会发生什么 |
|---|---|
| **旧版本二进制还在跑**（升级后、重启前） | 旧 `daily` **不持锁**，`prune` 会认为它没人写。若它正好满足「超过保留天数」或「总量超限」，那一轮清理**可能删掉旧 daemon 正在写的文件**。已实测：真机 10-27 的日志此刻没有锁（新 CLI 能加上锁），因为跑的是旧二进制。后果是旧 daemon 之后的日志写进已 unlink 的 inode —— **只丢诊断信息，不丢数据**，重启即恢复成新文件。**升级后尽快重启 daemon**。 |
| 文件系统不支持 `flock`（NFS 等） | `lock_exclusive` 失败不影响写日志；`prune` 侧表现为「都能加锁」→ 保护退化成「只靠调用方传的 `keep`」。日志目录在本地状态目录，正常不会遇到。 |
| 清理时 `File::open` 失败 | `is_in_use` 直接返回 `true`（保守：不删），并记进 `in_use`（`logcfg.rs:208-211`）。这类文件可能永远删不掉（例如权限被改坏），需要用户手工处理。 |
| 非 Unix 平台 | `is_in_use` 恒 `false`、`lock_exclusive` 空实现（`logcfg.rs:197-198`、`224-227`）。本项目只支持 Linux，这层只是编译兼容。 |
| 两个进程写**同一个**文件 | `flock` 保护的是「正在写的那一个」，另一进程的活动文件可能被删 —— 正常部署不会出现（daemon 与 GUI 前缀不同，多连接用 `qxyncd-<id>`）。 |
| 用户 `tail -f` 正在看的旧文件 | 不持写锁 → 可能被删；Linux 上 `tail` 会继续读那个已 unlink 的 inode，用户看到的是「文件突然从目录里消失」。 |

### 5.4 总量上限不是硬上限

`flock` 保护「正在写」的文件优先于总量上限：如果**活动文件自己**就比 `max_total_mb` 大
（只在把单文件上限调成 `0`、或某次写入的 buf 巨大导致切段后仍超限时可能发生），删无可删后
目录仍可能超限。默认配置（32 MiB 单文件 / 256 MiB 总量）下不会发生：单文件上限远小于总量。

> 另一种「看起来超限」的现场：写本文时真机目录 5.93 GB。跑默认策略会删掉所有旧文件；
> 但那个 674 MB 的 `.2026-10-27` **正被旧 daemon 写着且不持锁**（§5.3 第一行）——
> 所以它会不会被删，取决于跑清理的是新二进制还是旧 daemon 自己。

### 5.5 `0` 的三个语义（别记混）

| 字段 | `0` = |
|---|---|
| `log_max_file_mb` | 不按大小切段（只剩跨天切段） |
| `log_keep_days` | 不按天数删 |
| `log_max_total_mb` | 不限总占用 |

三个都 `0` = 回到旧行为（只能靠跨天切段），**不推荐**，但排障时可用。

### 5.6 本里程碑**没有**做的

* **刷屏根因**：`accept 失败: Too many open files` 的 fd 泄漏/耗尽点**未定位**，
  单独记一笔待查。本版只加了 100ms 退避（§3.7），保证「失败不会变成日志洪水」；
* **日志压缩**（`.gz`）与**按文件个数**的上限；
* **日志级别的运行时调整**（仍归 `RUST_LOG` / `--log-level`；GUI 的「调试日志」开关仍是记录位）；
* **non_blocking 缓冲丢尾部**：进程被 SIGKILL/SIGPIPE 瞬杀时，最后一段缓冲不会落盘
  （M37 §1.2 的现场证据）。M39 不解决这个，它属于日志落盘链路本身。

### 5.7 清理范围只认「qxync 开头且含 `.log`」

`is_qxync_log_name`（`logcfg.rs:174-176`）刻意宽松到能覆盖未来的前缀
（`qxyncd.log.*` / `qxyncd-<id>.log.*` / `qxync-gui.log.*`），又窄到不碰同目录里的其它文件
（`notes.txt` / `qxync.db` / `readme.log` / `.hidden` 都不命中，测试
`only_qxync_log_names_are_touched` 钉住）。若将来加了第三种日志前缀，只要以 `qxync` 开头、
含 `.log` 就自动纳管。

### 6.1 真机旧文件回收演练（隔离 XDG 目录）

预置两个文件：**5 174 393 555 字节**的 `qxyncd.log.2026-10-23`（稀疏文件，mtime = 4 天前，
就是真机那个 5.17 GB 现场的等价物）+ 300 KiB 的 `qxyncd.log.2026-10-25`（2 天前）。
启动 daemon（`QXNYC_LOG_PRUNE_SECS=5`，策略默认 32 MiB / 14 天 / 256 MiB）：

```text
INFO qxyncd: ★ M39：日志轮转策略已应用（单文件 32 MB / 保留 14 天 / 总量 256 MB）
INFO qxyncd::daemon: 日志清理已启动：每 5s 按策略清理一次（.../log)
INFO qxyncd::daemon: 日志清理：删除 1 个文件，释放 4934.69 MiB（保留 14 天 / 总量上限 256 MB）
```

三个要点，都能从这三行里读出来：

1. **那个 5.17 GB 文件不是等 14 天才被删** —— 它只「4 天前」，按天数根本不该删；
   真正删它的是**总量上限**（5.17 GB ≫ 256 MiB），而且是从最旧删起；
2. 300 KiB 的近期文件**保留**（总量已经回到上限内，不需要再删）；
3. 「当前段 920 B 活着」—— 清理没有误删正在写的文件（它持着 `flock`，见 §2.3）。

开局切段（另一个用例）：预置 **2 MiB 的当天段** + 把单文件上限改成 1 MiB → 启动后
`RotatingWriter::new` 立刻把它改成 `qxyncd.log.<今天>.1`（2 MiB），另开新当前段（641 B）——
这正是「昨天写爆、今天重启」时不用等下一次写就止血的行为。

```text
       785 B  2026-10-27 08:39:50  qxyncd.log.2026-10-27

$ qxync log --prune          # 无候选时

$ qxync settings --set log_keep_days=2 --set log_max_total_mb=1   # 经 daemon，热生效
（策略行等其余设置字段略）

```

`--json` 实跑字段（即 `LogsData` 原样）：
`dir` / `total_bytes` / `file_count` / `max_file_mb` / `keep_days` / `max_total_mb` / `pruned` /
`deleted` / `freed_bytes` / `failed` / `in_use` / `files[]`（`files[]` 每项 `name` / `path` /
`size` / `mtime`）。脚本验收直接拿它，不用解析人读输出。

### 6.3 单测清单

`crates/qxync-core/src/logcfg.rs:568-847` 读出的用例名与它钉住的事实：

| 用例 | 钉住什么 |
|---|---|
| `policy_from_settings_maps_mb` | MB→字节换算、默认值 |
| `civil_from_days_epoch_and_known_dates` | 1970-01-01 / 2022-01-08 / **2026-10-27**（与 Python `date` 核对过） |
| `only_qxync_log_names_are_touched` | 纳管范围：`qxyncd.log.*` 命中，`notes.txt` / `qxync.db` / `readme.log` / `.hidden` 不命中 |
| `size_rotation_splits_one_day_into_segments` | **M39 主回归**：3000 B / 1 KiB 上限 → 切成 ≥3 段、出现 `.<n>` 编号段、当前段 ≤ 上限、**总字节不变（不丢内容）** |
| `oversized_existing_file_is_rotated_at_open` | 开局遇到超限旧段（真机 5.17 GB 现场）→ 直接切段，不等下一次写 |
| `prune_by_age_keeps_recent_files` | 按天删：过期的删、近期保留、`notes.txt` 绝不碰 |
| `prune_by_total_size_deletes_oldest_first` | 按总量删：从最旧删起 |
| `prune_keeps_explicit_active_path` | 调用方显式 `keep` 的文件再旧也不删 |
| **`prune_skips_file_locked_by_writer`** | **flock 关键回归**：活动文件 mtime 被改成 90 天前，写入器持锁 → 清理任务仍跳过，且 `in_use` 如实报告被跳过的路径 |
| `prune_deletes_old_unlocked_lone_file` | 反向回归：40 天前、没人持锁的孤儿日志（GUI 早已退出）**必须**被删 —— 保护不能把死文件也保下来 |
| `prune_missing_dir_is_ok` | 目录不存在 = 无事发生，不报错 |
| `settings::tests::log_policy_fields_default_set_and_clamp` | 默认 32/14/256、`--set` 认键、`0` 合法、非整数报错、`u32::MAX` 被夹到上限 |

现场取证（**已做**，只读，2026-10-27）：

* 5.17 GB 文件 = 5 174 393 555 字节 / 52 266 068 行，其中 52 265 459 行（99.998%）是同一条
  `accept 失败: Too many open files`；
* 08:34–08:37 复发：`qxyncd.log.2026-10-27` 44 862 → 707 336 193 字节，之后仍被旧 daemon 以
  「对账失败 / 同步轮询」的节奏缓慢追加（08:41 到 707 375 327 字节、08:46 到 707 376 678 字节），
  内容里没有新版的 100ms 退避文案 ⇒ 跑的是旧二进制；
* 旧 `daily` 的 UTC 换段边界：`.2026-10-26` 末行 23:59:57Z / `.2026-10-27` 首行 00:00:00.755Z；
* **旧二进制不持锁**：用只读 fd 对新旧两个日志文件试 `LOCK_EX|LOCK_NB` 都能加上
  → 升级窗口内 `qxync log --prune` 看不到旧 daemon 的活动文件（§5.3）。
