# qxync v0.6.1 —— 编辑器保存不再卡 1~2 秒，「添加连接」终于有入口

**中文** · [English](#english)

[![License](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](https://github.com/mlzxgzy/qxync/blob/master/LICENSE-MIT)

**升级就是换二进制**：配置、任务、状态库、缓存布局都没有变，`default` 连接零迁移；
回退旧版本也不影响数据（只是新行为随旧二进制一起消失）。

## 一句话

这一版修两件「每天都会碰到」的事：**① 在 FUSE 挂载点里用 Kate / KIO 保存文件不再卡
1~2 秒**（qxync 的 `rename`/`unlink` 以前要等整个上传队列清空才返回）；**② 新建 NAS 连接
的入口补齐**（顶栏、主页、任务表单三处，以前只有设置里那一个按钮）。

## 一、保存不再等「整个上传队列」

**症状**：`echo asdf >> ceshi.txt` 很快，但用 Kate 编辑后按保存，要等 1~2 秒才落盘。

**原因**：编辑器（KIO/Kate）的原子保存是「写 `ceshi.txt.part` → `rename` 覆盖目标」。
qxync 的 FUSE `rename()` / `unlink()` 以前只要目标有本地改动，就先 `drain()` 等**整个**
上传队列清空（最多 60s / 30s）再打服务端。于是保存要排队等：`.part` 自己的上传、
Kate 每几秒写的 `.kate-swp` 上传、同目录其它上传……上传 worker 又是串行的，实测一次
保存 1.5~1.9 秒（本机基线，见下）。而 `echo >>` 是原地写，只入队、不 rename，所以无感。

**现在**：

- 只冻结并等待**相关路径**上的作业；排队中的作业直接改写到新名字
  （`UploadQueue::retarget_pending_under`，状态库主键同步 rekey），不再先传一版老名字；
- 节点新增 `remote_known`（远端到底有没有这个副本）：本地新建、还没上传过的文件
  （KIO 的 `.part`、临时文件）改名 / 删除**完全不碰服务端**，纯本地完成，上传直接落到
  最终名字；远端有老副本时行为不变（先远端改名、再更新本地视图，失败 EIO、队列原样保留）；
- 上传队列新增 **250ms 入队去抖**：同一路径的连续写合并成一版上传，编辑器保存不会再把
  0 字节 / 中间版本推上 NAS；
- 删除从没上传过的文件（关文档时删 swap）也不再「先上传再删除」。

**实测（本机 FUSE 挂载点，旧二进制基线）**：`echo >>` 追加 16.5 ms；原子保存
（create + write + rename）**1568 / 1918 ms**（连续两次保存，队列还在清）；rename 一个
已上传的干净文件 227 ms（一次远端往返）。修好后单测钉死了「只等相关路径」「去抖合并」
「纯本地改名」这些路径；新二进制上线后建议按下面的命令复测一次真实保存耗时。

```bash
python3 - <<'EOF'
import os, time
d = "/path/to/qxync-mount"
for i in range(6):
    t = time.perf_counter()
    part = os.path.join(d, "lag-test.txt.part")
    with open(part, "wb") as f:
        f.write(b"asdf\n" * (i + 1))
    os.replace(part, os.path.join(d, "lag-test.txt"))
    print(f"save {i}: {(time.perf_counter() - t) * 1000:.1f} ms")
EOF
```

**行为变化（升级前请过一眼）**：上传会在「最后一次写之后约 250 ms」才开始（`status` 里的
pending / active 照旧）；大文件拷贝会等写完再传，而不是边写边传。

## 二、「添加连接」不再只有一个入口

v0.6.0 里新建连接只有「设置 → 连接」卡片右上角那一个「＋ 添加 NAS」；主页、任务页都没有
出口，而任务表单的连接下拉只列**已有**连接 —— 想连一台还没配的 NAS 时，界面上根本没有
地方可以点。现在三处都能直达新建表单（切到设置 → 连接、把表单滚进视野、焦点落在
「主机 / NAS 地址」，并留一行日志）：

- 顶栏「当前连接」右边的 **＋**；
- 主页连接卡片的 **＋ 添加连接**；
- 任务表单「NAS 连接」下拉末尾的 **＋ 新建连接…**。

顺带修了两个「看着正常、其实不对」的 GUI 问题：

- **新建表单不再被「当前连接」的异步回包填回**：点「＋ 添加 NAS」清空表单后，
  `loadConnect()` 读回的是**当前连接**，于是「添加 NAS 连接」标题下挂着上一台 NAS 的
  host / path，保存下去就是一条错的连接；现在用 `creatingLink` 区分「展示当前连接」与
  「正在新建」，新建态下这次回包不碰表单。
- **主页「连接设置」不再落到上次看过的设置分区**：上次停在「关于」时点它会落到关于页，
  连接列表根本不出现；现在固定落在「连接」。

- 改名 / 删除队列相关新逻辑新增 6 条单测：路径级等待、排队作业改写 + 主键 rekey、

## 四、升级注意

- 换掉 `qxync` / `qxyncd` / `qxync-gui` 三个二进制，并**重启 daemon**
  （`systemctl --user restart qxyncd`，或 `qxync daemon restart`）。
- AUR（`qxync-bin`）：Release 产物出来之后需要 `updpkgsums` 回填 `sha256sums`，再
  `makepkg --printsrcinfo > .SRCINFO` 推 AUR；没回填前装包会 checksum 失败（不会静默装错）。
  流程见 `packaging/arch/README.md`。
- 状态库 / 配置 / 任务格式无变化，`default` 连接零迁移；非 `default` 连接仍是 v0.6.0 引入的
  新命名空间，回退到 v0.6.0 也没问题。

## English

# qxync v0.6.1 — saves in editors no longer take 1–2 s, and "add connection" finally has entry points

**Upgrading is just swapping binaries**: config, tasks, state store and cache layout are
unchanged (`default` connections need zero migration), and rolling back to v0.6.0 is safe for
your data (the new behaviour simply disappears with the old binary).

## The short version

Two things you hit every day: **① saving a file from Kate / KIO inside the FUSE mount no longer
takes 1–2 seconds** (qxync's `rename`/`unlink` used to wait for the *whole* upload queue to
empty before returning), and **② the "add connection" entry points are complete** (top bar,
home page, task form — previously only the button inside Settings).

## 1. Saving no longer waits for the entire upload queue

**Symptom**: `echo asdf >> ceshi.txt` is instant, but saving from Kate takes 1–2 s before the
file lands.

**Cause**: an editor's atomic save is "write `ceshi.txt.part` → `rename` over the target".
qxync's FUSE `rename()`/`unlink()` used to call `drain()` and wait for the **entire** upload
queue to empty (up to 60 s / 30 s) before talking to the server whenever the target had local
changes. The save therefore queued behind the `.part` upload itself, Kate's `.kate-swp` uploads
written every few seconds, other uploads in the same directory — and the upload worker is
serial. Measured on this machine: **1.5–1.9 s per save**. `echo >>` is an in-place write (enqueue
only, no rename), which is why it felt instant.

**Now**:

- only jobs on the **relevant paths** are frozen and awaited; queued jobs are retargeted to the
  new name (`UploadQueue::retarget_pending_under`, state-store primary key rekeyed) instead of
  uploading the old name first;
- nodes gain `remote_known` (whether the remote actually has this copy): renaming/deleting a
  locally created file that was never uploaded (KIO's `.part`, temp files) **never touches the
  server** — it is handled purely locally and the upload lands under the final name; when the
  remote has an older copy, behaviour is unchanged (rename on the remote first, then update the
  local view; on failure EIO and the queue stays intact);
- a **250 ms enqueue debounce**: consecutive writes to the same path collapse into one upload,
  so saving from an editor no longer pushes 0-byte / intermediate versions to the NAS;
- deleting a file that was never uploaded (closing a document deletes its swap file) no longer
  "uploads first, then deletes" either.

**Measured (this machine's FUSE mount, old binary baseline)**: `echo >>` append 16.5 ms; atomic
save (create + write + rename) **1568 / 1918 ms** (two consecutive saves while the queue was
still draining); renaming an already-uploaded clean file 227 ms (one remote round trip). Unit
tests pin the new paths ("wait only on relevant paths", "debounce coalescing", "purely local
rename"); please re-run the snippet below after installing the new binaries to get the real
save latency:

```bash
python3 - <<'EOF'
import os, time
d = "/path/to/qxync-mount"
for i in range(6):
    t = time.perf_counter()
    part = os.path.join(d, "lag-test.txt.part")
    with open(part, "wb") as f:
        f.write(b"asdf\n" * (i + 1))
    os.replace(part, os.path.join(d, "lag-test.txt"))
    print(f"save {i}: {(time.perf_counter() - t) * 1000:.1f} ms")
EOF
```

**Behaviour change**: uploads now start about 250 ms after the last write (pending / active in
`status` are unchanged); big copies wait until the write finishes instead of streaming while
copying.

## 2. "Add connection" is no longer one hidden button

In v0.6.0 the only way to create a connection was "＋ 添加 NAS" in the Settings → Connections
card. Three entry points now jump straight to the form (switch to Settings → Connections, scroll
the form into view, focus "host / NAS address", and leave a line in the log):

- the **＋** next to the current-connection picker in the top bar;
- **＋ 添加连接** on the home connection card;
- **＋ 新建连接…** at the end of the task form's "NAS connection" dropdown.

Two related GUI bugs fixed as well:

- **the new-connection form is no longer filled in by the current connection's async reply**:
  after "＋ 添加 NAS" cleared the form, the `loadConnect()` reply (which reads the *current*
  connection) put the previous NAS's host / path back into the form, so saving created a wrong
  connection. A `creatingLink` flag now distinguishes "showing the current connection" from
  "creating a new one".
- **"Connection settings" on the home page no longer lands on the last settings tab**: if you
  last looked at "About", clicking it dropped you on About and the connection list never showed.
  It is now pinned to "Connections".

## 4. Upgrade notes

- Replace `qxync` / `qxyncd` / `qxync-gui` and **restart the daemon**
  (`systemctl --user restart qxyncd`, or `qxync daemon restart`).
- AUR (`qxync-bin`): after the Release assets exist, run `updpkgsums` to fill in `sha256sums`,
  then `makepkg --printsrcinfo > .SRCINFO` before pushing to AUR; otherwise installs fail the
  checksum (they never install silently wrong). See `packaging/arch/README.md`.
- State store / config / task format are unchanged, `default` connections need zero migration;
  non-`default` connections keep the v0.6.0 namespace, so rolling back to v0.6.0 is fine too.
