# qxync v0.4.1 —— 服务端错误终于说人话了，外加一条被实测推翻的逆向结论

**中文** · [English](#english)

[![License](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](https://github.com/mlzxgzy/qxync/blob/master/LICENSE-MIT)

**这一版没有破坏性变更**：配置、任务文件、缓存目录布局、命令行参数都不需要改。
升级方式就是换二进制 + 重启 daemon。

## 一句话

服务端明明回了一句 *"Qsync Central is initializing. Please wait a few minutes and try
again."*，客户端却把它**整个丢掉**，只显示「未知状态码」—— 这一版把它透传出来，
并且让「服务端还没就绪」走「等一等」而不是「出错重登」。

另外：逆向报告里被标为"最有价值的可抄资产"的 `get_meta`，**实测不可用**（详见下文）。

## 服务端说了原因，用户只看到「未知状态码」

NAS 返回的失败响应里有一个 `msg` 字段，是服务端专门用来解释失败的。以前 qxync 只读
`status` 数字，**把 `msg` 丢了** —— 于是不管是路径不存在、权限不足还是「服务端正在启动」，
在界面上都长成同一个样子：`status=5 (未知状态码)`。

现在：

```
get_list /home/x: status=5 (路径不存在 / 无权限) — 服务端 msg: Path not found
qbox_get_max_log: status=8 (服务端未就绪…) — 服务端 msg: Qsync Central is initializing. Please wait a few minutes and try again.
```

## 「服务端还没就绪」不该当成出错

逆向确证了一件事：服务端 `qsync_*` 私有接口上**唯一**的业务状态码是 `8`，
含义是「Qsync Central 正在初始化」（`/var/qfunc/qbox.enable` 未就绪 ——
可能正在安装、迁移、恢复、备份还原）。

这个状态**重登没用**，只能等。以前它走普通错误路径：既可能做一次无用重登，
又会污染「同步出错」的计数。

现在按 `msg` 文本识别（不是写死数字，服务端将来换码仍认得出），归入「等一等」：
不计入错误、不触发重登，下一轮自动继续。

顺带修掉一个具体浪费：NAS 在迁移 / 恢复 / 备份还原时，`max_log` 可能短暂偏小，
以前会被误判成「游标回退」而触发**一次全量重扫**。现在读服务端自带的
`is_migrating` / `is_recovering` / `is_backuping_restoring` / `is_booting` 前置跳过。

## 批量大小不再写死

以前 `qbox_get_sync_log` 的批量固定 200 —— 在上限更低的机型上会被服务端截断，
造成「以为拉完了、其实没拉完」。现在按服务端自报的 `server_limit` 夹住（真机实测 256）。

`sync_signal == 2`（服务端要求降速）时，按它给的 `slowdown_seconds` 给出退避建议。
`qxync status` 现在会显示限流、降速与就绪状态。

## ★ `get_meta` 实测不可用 —— 推翻了一条逆向结论

逆向报告把 `get_meta` / `get_meta_profile` 列为本次解包**最有价值的可抄资产**
（「服务端已实现、文档里查不到的私有接口」），并建议按需同步的元数据层优先用它。

**实测结论：两者都不可用。** 真机（QPKG 5.0.0.7 build 20260723）：

| func | `qsyncsrv.cgi` | `filemanager` | `qboxRequest` |
|---|---|---|---|
| `get_meta` | **HTTP 500** | `status: 20` | XML |
| `get_meta_profile` | **`status: 19`**（无数据） | `status: 20` | XML |
| 对照：**瞎编的** func | **`200` 空体** | **`status: 20`** | — |

**500 是 CGI 自己崩了，不是参数名猜错** —— 同一个端点上瞎编的 func 回 `200` 空体，
`get_tree` / `get_list` 也正常，证明分发链路是通的。参数侧已穷举 16 种形态，
包括 7 种路径参数名、`folder_number` 风格、递归与分页开关，**无一例外全部 500**。

所以元数据方案回退到 `get_list` 递归。好消息是这条路没坏，而且实测表明
**耗时几乎全在往返次数上、与条目数关系不大**（11 次请求 / 17 个条目，
单次往返 157–430 ms）—— 这正是 v0.4.0 的 M9「缓存优先 + 映射」在解决的事
（热 `ls` 已从 0.50 s 降到 0.001 s）。

**按需同步本身的可行性没有被推翻**：服务端 `qsyncsrv_metad` 生成的
`{share}/.qsync/meta/` 元数据层仍然真实存在，只是**没有可用的 CGI 出口**。
要用得直读目录（需要 NAS 本地路径访问），留待后续评估。

完整证伪过程与判据见 **[`docs/get_meta-实测证伪.md`](https://github.com/mlzxgzy/qxync/blob/master/docs/get_meta-实测证伪.md)**。
仓库里还留了三个真机测试作**回归护栏**：如果哪天 NAS 升级后 `get_meta` 突然能用了，
测试会红掉并提示重写封装，而不是让人悄悄继续走 `get_list` 而没人知道捷径出现了。

## 升级

无破坏性变更，换二进制 + 重启 daemon 即可：

```bash
qxync daemon stop && qxync daemon start
```

建议顺手把挂载点卸了重挂一次（`qxync mount`）。

# qxync v0.4.1 — server errors finally speak human, plus a reverse-engineering conclusion overturned

**English** · [中文](#top)

**No breaking changes**: configuration, task files, cache layout and CLI arguments are all
unchanged. To upgrade, swap the binaries and restart the daemon.

## One sentence

The NAS replies *"Qsync Central is initializing. Please wait a few minutes and try again."* —
and qxync **threw that away**, showing only "unknown status code". This release surfaces it,
and makes "server not ready yet" mean *wait a bit* rather than *something broke, re-login*.

## The server said why; users only saw "unknown status code"

Server error responses carry a `msg` field whose entire purpose is to explain the failure.
qxync read only the `status` number and **discarded `msg`**, so path-not-found,
permission-denied and server-is-starting all looked identical.

Now:

```
get_list /home/x: status=5 (path missing / no permission) — server msg: Path not found
qbox_get_max_log: status=8 (server not ready) — server msg: Qsync Central is initializing. Please wait a few minutes and try again.
```

## "Server not ready" is not an error

Reverse engineering confirmed that status `8` is the **only** business status on the
`qbox_*` private path, meaning Qsync Central is still initialising
(`/var/qfunc/qbox.enable` not ready — installing, migrating, recovering or restoring a backup).

Re-logging in does **not** help; only waiting does. It is now recognised by `msg` text
(not a hard-coded number, so a future server-side code change still works) and classified as
"wait": no error count, no pointless re-login, and the next round continues automatically.

This also removes a concrete waste: while the NAS is migrating / recovering / restoring,
`max_log` can dip briefly and used to be read as "cursor went backwards", triggering a **full
re-scan**. The engine now short-circuits on the server-reported `is_migrating` /
`is_recovering` / `is_backuping_restoring` / `is_booting`.

## Batch size is no longer hard-coded

`qbox_get_sync_log` used a fixed batch of 200 — truncated by the server on models with a lower
cap, meaning "looks like we drained the log" when we had not. It is now clamped by the
server-reported `server_limit` (measured 256 on-device). When `sync_signal == 2` the
server's `slowdown_seconds` becomes a backoff hint. `qxync status` now reports the rate limit,
slowdown and readiness state.

## ★ `get_meta` is not usable — a reverse-engineering conclusion overturned

The reverse-engineering report listed `get_meta` / `get_meta_profile` as **the most valuable
copyable asset** found ("implemented by the server, absent from the docs"), and recommended
using it for on-demand metadata.

**Measured: neither is usable.** Live NAS (QPKG 5.0.0.7 build 20260723):

| func | `qsyncsrv.cgi` | `filemanager` | `qboxRequest` |
|---|---|---|---|
| `get_meta` | **HTTP 500** | `status: 20` | XML |
| `get_meta_profile` | **`status: 19`** (no data) | `status: 20` | XML |
| control: **made-up** func | **`200` empty** | **`status: 20`** | — |

**The 500 is a CGI crash, not a wrong parameter name** — a made-up func on the same endpoint
returns an empty `200`, and `get_tree` / `get_list` work fine, so dispatch is healthy.
16 parameter forms were tried (7 path-parameter names, the `folder_number` style,
recursion and paging switches) — all 500.

Metadata therefore falls back to recursive `get_list`. That path is fine, and measurement shows
latency is **dominated by round-trip count, not entry count** (11 requests / 17 entries,
157–430 ms per round trip) — exactly what v0.4.0's M9 "cache-first + mapping" addresses
(warm `ls` already dropped from 0.50 s to 0.001 s).

**On-demand sync itself is not ruled out**: the `{share}/.qsync/meta/` layer generated by
`qsyncsrv_metad` still exists; it simply has **no usable CGI surface**. Using it would mean
reading that directory directly (requires local NAS path access), deferred for later.

Full falsification and evidence:
**[`docs/get_meta-实测证伪.md`](https://github.com/mlzxgzy/qxync/blob/master/docs/get_meta-实测证伪.md)**.
Three live tests act as a **regression guard**: if a future NAS upgrade makes `get_meta`
usable, they turn red and prompt a rewrite instead of letting the fallback silently continue.

## Upgrading

No breaking changes — swap binaries and restart the daemon:

```bash
qxync daemon stop && qxync daemon start
```

Remounting once afterwards is recommended (`qxync mount`).
